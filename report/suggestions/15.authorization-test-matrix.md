## What the tests cover today

The server has five suites, and they are better organised than most:

| Suite | Covers |
| --- | --- |
| `v1-archive` | Legacy, superseded |
| `v2-integration` | Auth flows, posts, roles/permissions, users — happy paths plus some failures |
| `v3-migrations` | Migration up/down, schema shape assertions |
| `v4-rate-limits` | Rate limiter behaviour |
| `v5-openapi` | Spec generation |

The client has Vitest unit tests (`navVisibility`, `rolePermissions`, `format`,
`schemas`, `ProtectedRoute`, `AuthPage`, `PostsPage`, `Dialogs`, `FormFields`)
with MSW handlers, plus Playwright e2e (`auth.spec.ts`, `rbac.spec.ts`).

That is a real test suite. The gap is not *coverage of code* — it is **coverage of
the authorization matrix**, which is the one thing an IAM system exists to get
right.

## The gap

There are 4 roles and roughly 30 endpoints. That is ~120 (role, endpoint)
combinations, each with a correct answer of `allowed` or `403`. The current tests
check a sample of the interesting ones, chosen by hand.

Every one of these findings is an authorization matrix cell that no test would
have caught:

| Finding | The uncovered cell |
| --- | --- |
| [02](../vulnerabilities/02.overpermissive-default-user-role.md) | `user` → `GET /api/sessions` → currently **200**, should be **403** |
| [02](../vulnerabilities/02.overpermissive-default-user-role.md) | `user` → `GET /api/audit-logs` → currently **200**, should be **403** |
| [11](../vulnerabilities/11.session-revocation-and-peer-actions-lack-hierarchy-checks.md) | `admin` → `PATCH /api/sessions/:id/revoke` on a **super-admin's** session → currently **200**, should be **403** |
| [20](../vulnerabilities/20.updatepost-and-post-ownership-inconsistencies.md) | `editor` → `PUT /api/posts/:id` on a **super-admin's** post → currently **200**, should be **403** |
| [03](../vulnerabilities/03.deactivated-users-can-still-log-in.md) | deactivated user → `POST /api/auth/login` → currently **200**, should be **401** |
| [01](../vulnerabilities/01.jwt-token-confusion-and-session-revocation-bypass.md) | refresh token in the `access` cookie → currently **200**, should be **401** |

Six real vulnerabilities, all expressible as a single table row each. A matrix
test is not just regression protection — writing it is how you *find* these.

## The design

Table-driven, so adding an endpoint means adding a row.

```ts
// server/tests/v2-integration/authorization-matrix.cases.ts
import assert from "node:assert/strict";
import { test } from "node:test";

type Role = "super-admin" | "admin" | "editor" | "user";
type Expectation = "allow" | "forbid";

type MatrixCase = {
  name: string;
  method: "GET" | "POST" | "PUT" | "PATCH" | "DELETE";
  path: (ctx: Fixtures) => string;
  body?: (ctx: Fixtures) => unknown;
  /** Every role's expected outcome. Roles omitted default to "forbid". */
  expect: Partial<Record<Role, Expectation>>;
};

const MATRIX: MatrixCase[] = [
  // ---- Users -------------------------------------------------------------
  { name: "list users", method: "GET", path: () => "/api/users",
    expect: { "super-admin": "allow", admin: "allow", editor: "allow", user: "forbid" } },

  { name: "create user", method: "POST", path: () => "/api/users",
    body: () => ({ fullname: "New Person", email: uniqueEmail(), password: "correct horse battery", roleName: "user" }),
    expect: { "super-admin": "allow" } },

  { name: "delete another user", method: "DELETE",
    path: (ctx) => `/api/users/${ctx.plainUserId}`,
    expect: { "super-admin": "allow", admin: "allow" } },

  // ---- Sessions: the cells that finding 02 is about ----------------------
  { name: "list all sessions", method: "GET", path: () => "/api/sessions",
    expect: { "super-admin": "allow", admin: "allow" } },       // NOT user, NOT editor

  { name: "list own sessions", method: "GET",
    path: (ctx) => `/api/users/${ctx.selfId}/sessions`,
    expect: { "super-admin": "allow", admin: "allow", editor: "allow", user: "allow" } },

  { name: "list another user's sessions", method: "GET",
    path: (ctx) => `/api/users/${ctx.superAdminId}/sessions`,
    expect: { "super-admin": "allow" } },

  // ---- Audit logs --------------------------------------------------------
  { name: "list audit logs", method: "GET", path: () => "/api/audit-logs",
    expect: { "super-admin": "allow", admin: "allow" } },

  // ---- Posts: the cell that finding 20 is about --------------------------
  { name: "update own post", method: "PUT",
    path: (ctx) => `/api/posts/${ctx.ownPostId}`,
    body: () => ({ title: "Updated title", content: "..." }),
    expect: { "super-admin": "allow", admin: "allow", editor: "allow", user: "allow" } },

  { name: "update a super-admin's post", method: "PUT",
    path: (ctx) => `/api/posts/${ctx.superAdminPostId}`,
    body: () => ({ title: "Rewritten", content: "..." }),
    expect: { "super-admin": "allow" } },                        // NOT editor -- finding 20

  // ... one row per endpoint
];

for (const matrixCase of MATRIX) {
  for (const role of ["super-admin", "admin", "editor", "user"] as const) {
    const expected = matrixCase.expect[role] ?? "forbid";

    test(`${role} ${expected === "allow" ? "CAN" : "CANNOT"} ${matrixCase.name}`, async () => {
      const ctx = await seedFixtures();
      const cookies = await loginAs(role);

      const response = await request({
        method: matrixCase.method,
        path: matrixCase.path(ctx),
        body: matrixCase.body?.(ctx),
        cookies,
      });

      if (expected === "allow") {
        assert.ok(
          response.status < 400,
          `expected ${role} to be allowed, got ${response.status}: ${response.body?.message}`,
        );
      } else {
        assert.equal(
          response.status, 403,
          `expected ${role} to be forbidden, got ${response.status}`,
        );
      }
    });
  }
}
```

Two design choices worth defending:

**Roles omitted default to `forbid`.** This is the critical property. Adding a new
endpoint row means every role is denied unless explicitly allowed, so an
over-permissive endpoint fails the test by default rather than passing by
omission. That is the inverse of how the bugs in this codebase happened.

**Assert `403`, not "any error".** A `404` is not a `403`. Asserting the exact
status catches the case where authorization was skipped and the request failed
for an unrelated reason — which is how you would otherwise get a green test for a
broken check.

### Authentication edge cases as a second table

```ts
// server/tests/v2-integration/authentication.cases.ts
test("a refresh token is rejected as an access token", async () => {
  const { refreshCookie } = await loginAs("super-admin");
  const response = await request({
    method: "GET", path: "/api/users",
    cookies: { access: refreshCookie },          // <-- token confusion, finding 01
  });
  assert.equal(response.status, 401);
});

test("a revoked session's access token stops working", async () => {
  const { accessCookie, sessionId } = await loginAs("admin");
  await revokeSessionAs("super-admin", sessionId);
  const response = await request({ method: "GET", path: "/api/posts", cookies: { access: accessCookie } });
  assert.equal(response.status, 401);           // finding 01
});

test("a deactivated user cannot log in", async () => {
  const userId = await createUserAs("super-admin", { roleName: "user" });
  await deactivateUser(userId);
  const response = await login(userEmail, userPassword);
  assert.equal(response.status, 401);           // finding 03
});

test("changing a password revokes other sessions", async () => {
  const first  = await loginAs("user");
  const second = await loginAs("user");
  await changePasswordUsing(second, oldPassword, newPassword);
  const response = await request({ method: "GET", path: "/api/posts", cookies: first.cookies });
  assert.equal(response.status, 401);           // finding 04
});

test("replaying a rotated refresh token revokes the session family", async () => {
  const { refreshCookie } = await loginAs("user");
  await refreshUsing(refreshCookie);                              // rotates
  const replay = await refreshUsing(refreshCookie);               // stale token
  assert.equal(replay.status, 401);                               // finding 05
  const anySession = await request({ method: "GET", path: "/api/posts", cookies: { access: replay.newAccess } });
  assert.equal(anySession.status, 401);
});
```

**Write these tests now, before the fixes.** They will fail. That failure is the
proof that the vulnerability is real, and turning each one green is how you know
the fix worked. This is the highest-value use of a test suite in a security
context.

### The client gap

`ProtectedRoute.test.tsx` and `navVisibility.test.ts` exist. What is missing is a
test that each **page** denies access without its capability — which is the gap
[Suggestion 10](./10.client-capability-guard-component.md) addresses, and it is
testable the same table-driven way:

```tsx
// client/src/pages/__tests__/capability-guards.test.tsx
const PAGE_CAPABILITIES = [
  { Page: UsersPage,      capability: 'users.view' },
  { Page: RolesPage,      capability: 'roles.view' },
  { Page: AuditLogsPage,  capability: 'auditLogs.view' },
  { Page: MigrationsPage, capability: 'migrations.view' },
] as const

describe.each(PAGE_CAPABILITIES)('$capability', ({ Page, capability }) => {
  it('renders AccessDenied without the capability', () => {
    mockAuthMe({ capabilities: [] })
    render(<Page />)
    expect(screen.getByText(/access denied/i)).toBeInTheDocument()
  })

  it('renders content with the capability', () => {
    mockAuthMe({ capabilities: [capability] })
    render(<Page />)
    expect(screen.queryByText(/access denied/i)).not.toBeInTheDocument()
  })
})
```

## Practical notes

- **Fixtures must be per-test, not shared.** Cases mutate state (deleting users,
  revoking sessions). `--test-concurrency=1` is already set in every test script,
  which is the right call — keep it, and reset the database between cases via
  `tests/support/database.ts`.
- **Watch the rate limiter.** ~120 cases × several requests each will trip
  `RATE_LIMIT_USER_LIMIT=60`. Either flush Redis between cases (you have
  `tests/support/redis.ts`) or raise the limits in the test environment.
- **Keep it in `v2-integration`** rather than a new suite. It is integration
  testing, and it belongs with the flows it complements.

## What you already got right

- **Five versioned test suites with separate runtimes and helpers.**
  `tests/v2-integration/runtime.ts`, `helpers.ts` and per-domain `*.cases.ts`
  files — that is a deliberate, scalable structure, not an afterthought.
- **`--test-concurrency=1`** on every test script. Integration tests sharing a
  database must not run in parallel, and you set that explicitly rather than
  discovering it through flaky failures.
- **`tests/support/database.ts`, `http.ts`, `redis.ts`** — a real test harness
  with infrastructure abstracted behind helpers. Adding the matrix means writing
  cases, not plumbing.
- **You already test rate limiting** (`v4`) and **schema migrations** (`v3`).
  Testing infrastructure behaviour rather than only business logic is a level of
  rigour most projects skip entirely.
- **The client has MSW handlers and a `test-utils.tsx` render wrapper**, so
  component tests get a configured `QueryClientProvider` and router for free.
- **Playwright e2e covering auth and RBAC flows** means the critical paths are
  verified end to end in a real browser. The `rbac.spec.ts` file is exactly the
  right instinct — this suggestion asks for the same idea applied exhaustively
  rather than by sample.

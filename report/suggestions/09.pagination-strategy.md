# 09. Fix the `COUNT(*)` cost and the offset drift in list endpoints

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **4 / 10**                                                            |
| **Side**     | **Both** (server queries; the client's pagination controls follow)    |
| **Effort**   | Small for the quick wins; medium if you adopt keyset pagination       |
| **Files**    | 8 list controllers, [validation.util.ts](../../server/src/utils/validation.util.ts), [PaginationControls.tsx](../../client/src/components/PaginationControls.tsx), [services.ts:158-176](../../client/src/api/services.ts#L158-L176) |

---

## The pattern today

Every list endpoint uses the same shape:

```ts
// server/src/controllers/users/listUsers.ts -- and 7 siblings
const [result, countResult] = await Promise.all([
  pool.query(
    `SELECT u.id, u.fullname, u.email, u.is_active, u.created_at, u.created_by,
            COALESCE(ARRAY_REMOVE(ARRAY_AGG(r.name ORDER BY r.name), NULL), ARRAY[]::text[]) AS role_names
       FROM users u
       LEFT JOIN user_roles ur ON ur.user_id = u.id
       LEFT JOIN roles r ON r.id = ur.role_id
      GROUP BY u.id
      ORDER BY u.created_at DESC, u.id DESC
      LIMIT $1 OFFSET $2`,
    [limit, offset],
  ),
  pool.query<{ total: string }>("SELECT COUNT(*) AS total FROM users"),
]);
```

Three issues, in increasing order of how much they will eventually matter.

### 1. `COUNT(*)` is a full sequential scan, on every page load

PostgreSQL cannot answer `SELECT COUNT(*) FROM users` from an index — MVCC means
it must visit every row to check visibility. At a few thousand rows this is
microseconds. At a million rows in `audit_logs` — which is the table that will
grow without bound, since
[Vulnerability 17](../vulnerabilities/17.no-authentication-audit-trail.md)
proposes adding authentication events to it and nothing prunes it — this becomes
hundreds of milliseconds **on every page view**, and it holds a pool connection
the whole time.

### 2. `OFFSET` drifts and gets slower with depth

`OFFSET 20000` makes PostgreSQL fetch and discard 20,000 rows. And because
`audit_logs` and `user_sessions` receive new rows constantly, ordering by
`created_at DESC` means a row inserted between page 1 and page 2 shifts
everything down — the user sees a record twice and misses another entirely.

### 3. The client's `listAll()` amplifies both

```ts
// client/src/api/services.ts:158
listAll: async () => {
  const pageSize = 100
  const firstPage = await rolePermissionsApi.list({ page: 1, pageSize })
  const remainingPages = Array.from(
    { length: Math.max(firstPage.pagination.totalPages - 1, 0) },
    (_, index) => index + 2,
  )
  const remainingResults = await Promise.all(
    remainingPages.map((page) => rolePermissionsApi.list({ page, pageSize })),
  )
  // ...
}
```

Every page fires **in parallel**, and each one runs its own `COUNT(*)`. For
`role_permissions` this is currently ~40 rows, so one request — fine. But the
pattern is a landmine: applied to a table with 10,000 rows it becomes 100
simultaneous requests, each with a full count, against a pool of 10 connections,
all of which count against the per-user rate limit of 60/minute. That is a
self-inflicted denial of service triggered by opening a page.

## The suggestion

Three tiers. Do tier 1 now; tier 2 when a table gets large; tier 3 only if you
need it.

### Tier 1: cheap wins, do these regardless

**(a) Skip `COUNT(*)` when it cannot change the answer.** On page 1 with a full
page returned, you know there is at least one more page; on a short page, you know
the exact total:

```ts
// server/src/utils/validation.util.ts
const makePaginationMeta = (page: number, pageSize: number, total: number) => ({
  page, pageSize, total,
  totalPages: total === 0 ? 0 : Math.ceil(total / pageSize),
});

/** Derives pagination metadata without a COUNT when the row count settles it. */
const makeInferredPaginationMeta = (page: number, pageSize: number, rowsReturned: number) => {
  const hasMore = rowsReturned === pageSize;
  return {
    page, pageSize,
    hasMore,
    // `total` is unknown without a COUNT; the client should render
    // "Page N" + prev/next rather than "of M pages".
    total: hasMore ? null : (page - 1) * pageSize + rowsReturned,
  };
};
```

This is a **contract change** — `PaginationMetaSchema` gains `hasMore` and makes
`total` nullable — so it flows through the OpenAPI document into
`client/src/api/schema.ts` and into `PaginationControls.tsx`. Worth it: most
admin UIs need "next/previous", not "page 47 of 312".

**(b) Fix `listAll()` to fetch sequentially with a cap.**

```ts
// client/src/api/services.ts
listAll: async () => {
  const pageSize = 100
  const MAX_PAGES = 20                       // 2000 assignments is far beyond realistic
  const assignments: RolePermissionAssignment[] = []

  for (let page = 1; page <= MAX_PAGES; page += 1) {
    const result = await rolePermissionsApi.list({ page, pageSize })
    assignments.push(...result.assignments)
    if (result.assignments.length < pageSize) break
  }

  return { assignments }
}
```

Sequential, bounded, and it stops as soon as a short page proves there is no more.
One line of behaviour change, removes the amplification entirely.

**(c) Add the indexes the `ORDER BY` clauses need.**

```sql
-- migrations/<timestamp>_pagination-indexes.sql
CREATE INDEX idx_users_created_at_id     ON users(created_at DESC, id DESC);
CREATE INDEX idx_posts_created_at_id     ON posts(created_at DESC, id DESC);
CREATE INDEX idx_sessions_created_at_id  ON user_sessions(created_at DESC, id DESC);
CREATE INDEX idx_audit_logs_created_at_id ON audit_logs(created_at DESC, id DESC);
```

Every list controller orders by `(created_at DESC, id DESC)` and none of these
composite indexes exist. Without them, every page is a sort of the whole table.
This is the highest value-per-effort item in the entire suggestion — four lines
for a large win on the tables that grow.

### Tier 2: keyset pagination for the append-only tables

For `audit_logs` and `user_sessions`, where rows arrive constantly and users
scroll deep, replace offset with a cursor:

```ts
// GET /api/audit-logs?limit=20&cursor=eyJjcmVhdGVkQXQiOiIyMDI2LTA4LTA3VDEwOjAwOjAwWiIsImlkIjo0NDcxfQ==
const listAuditLogs = asyncHandler(async (req, res) => {
  const { limit, cursor } = parseKeysetQuery(req.query);

  const result = await pool.query(
    `SELECT al.id, al.actor_id, u.fullname AS actor_fullname, al.action_type,
            al.resource_type, al.resource_id, al.old_values, al.new_values,
            al.metadata, al.created_at
       FROM audit_logs al
       LEFT JOIN users u ON u.id = al.actor_id
      WHERE ($1::timestamptz IS NULL OR (al.created_at, al.id) < ($1, $2))
      ORDER BY al.created_at DESC, al.id DESC
      LIMIT $3`,
    [cursor?.createdAt ?? null, cursor?.id ?? null, limit + 1],
  );

  const hasMore = result.rows.length > limit;
  const rows = hasMore ? result.rows.slice(0, limit) : result.rows;
  const last = rows[rows.length - 1];

  new AppResponse(200, "Audit logs fetched successfully", {
    auditLogs: rows.map(toAuditLog),
    pagination: {
      limit,
      hasMore,
      nextCursor: hasMore && last
        ? encodeCursor({ createdAt: last.created_at, id: last.id })
        : null,
    },
  }).send(res);
});
```

The `(created_at, id) < ($1, $2)` row-value comparison is the key — it uses the
composite index directly, it is stable under concurrent inserts, and its cost is
constant regardless of how deep you scroll. Include `id` as a tiebreaker because
`created_at` is not unique.

Cursors must be **opaque** to the client (base64 the JSON) so the shape can change
without breaking clients, and validated on the way back in — a client-supplied
cursor is untrusted input.

### Tier 3: approximate counts, only if you need a total on a huge table

```sql
SELECT reltuples::bigint AS approximate_total
  FROM pg_class WHERE relname = 'audit_logs';
```

Instant, but only as fresh as the last `ANALYZE`. Acceptable for "about 1.2M
entries"; not for anything the user counts on being exact.

## Recommendation

Do **(c) the indexes** today — four lines, no contract change, pure win. Do
**(b) the `listAll` fix** today — one function, removes a real amplification
hazard. Defer (a) and Tier 2 until either a table crosses ~100k rows or you are
already reshaping the API for
[Suggestion 16](./16.openapi-as-contract-source-of-truth.md), since both change
the response contract and are cheapest to do alongside other contract work.

## Interaction with other findings

- **[Vulnerability 17](../vulnerabilities/17.no-authentication-audit-trail.md)**
  — adds login/logout/denial events to `audit_logs`, which is what makes that
  table grow fast enough for this to matter. **Do the indexes (c) before or with
  that finding**, and add its retention policy at the same time.
- **[Vulnerability 02](../vulnerabilities/02.overpermissive-default-user-role.md)**
  — introduces `WHERE us.user_id = $n` filtering on `listSessions` for
  non-privileged callers. That changes the `COUNT(*)` to a filtered count, which
  is cheaper. **Do 02 first**; this builds on its query shape.
- **[Suggestion 04](./04.service-layer-and-repositories.md)** — pagination logic
  belongs in repositories. If you plan to do that refactor, doing keyset
  pagination first means writing it in controllers and moving it later.
- **[Suggestion 16](./16.openapi-as-contract-source-of-truth.md)** — tier 1(a) and
  tier 2 both change `PaginationMetaSchema`, which regenerates the client types.
  Batch the contract changes.
- **No contradiction** with anything.

## What you already got right

- **`pageSize` is capped at 100** in `parsePaginationQuery`
  (`.max(100).default(20)`). Without that cap, `?pageSize=1000000` is a trivial
  memory-exhaustion vector. You closed it.
- **Data and count queries run in `Promise.all`**, so they overlap rather than
  serialise. Given that both are needed, this is the right way to issue them.
- **`ORDER BY created_at DESC, id DESC`** includes a tiebreaker. Ordering by a
  non-unique column alone gives non-deterministic pagination — rows can appear on
  two pages or neither. You handled it, which is exactly the groundwork keyset
  pagination needs.
- **`makePaginationMeta` is a shared helper**, so all eight endpoints return an
  identical `PaginationMeta` shape. The client has one `PaginationControls`
  component that works everywhere as a result.
- **`total === 0 ? 0 : Math.ceil(total / pageSize)`** — the empty-table case is
  handled explicitly rather than producing `NaN` or `Infinity`.
- **The client uses `keepPreviousData`** on paginated queries, so changing pages
  does not blank the table. Small detail, noticeably better UX.

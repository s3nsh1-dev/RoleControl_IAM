# 01 — Move the coarse permission check into route middleware

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **9 / 10** (impact on maintainability and correctness)                |
| **Side**     | **Server**                                                            |
| **Effort**   | Medium — mechanical, ~20 files, no behaviour change if done carefully |
| **Files**    | all of [server/src/controllers/](../../server/src/controllers/), all of [server/src/routes/](../../server/src/routes/), [helper.ts:40-62](../../server/src/utils/helper.ts#L40-L62) |

## The pattern today

Every controller opens with the same eight lines:

```ts
// server/src/controllers/users/listUsers.ts -- and 19 near-identical siblings
const listUsers = asyncHandler(async (req, res) => {
  if (!req.user || !req.user.uId) {
    throw AppError.unauthorized("User not found");
  }

  const actorId = parsePositiveInt(req.user.uId, "actorId");
  await checkRolePermissions(actorId, "view", "user");
  const { page, pageSize, limit, offset } = parsePaginationQuery(req.query);
  // ... actual work starts here, on line 9
```

Twenty controllers, twenty copies. And they are not quite identical — the
variations are where bugs live:

| Controller | The `!req.user` message | Notes |
| --- | --- | --- |
| `listUsers`, `viewUser`, `createUser`, … | `"User not found"` | |
| `assignRole`, `revokeRole`, `assignPermission` | `"UNAUTHORIZED REQUEST: USER NOT FOUND"` | different wording |
| `updateUser` | `"User not found"` | but names the field `"userId"` in `parsePositiveInt(req.user.uId, "userId")` — a copy-paste slip |
| `createPost` | `"User not found"` | field named `"actor_id"` |
| `assignPermission` | `"UNAUTHORIZED REQUEST: USER NOT FOUND"` | field named `"Actor Id"` |

Three different error messages and four different field labels for the same
check. More importantly: the check that `req.user` exists is **structurally
redundant** — `checkCookieSignature` already runs as router-level middleware on
every one of these routes and throws 401 if the token is absent or invalid. The
twenty `if (!req.user)` blocks are unreachable defensive code that exists because
`Express.Request["user"]` is typed as non-optional in
[express.d.ts](../../server/src/types/express.d.ts), so TypeScript never forced
the question.

## Why this is worth doing

Three concrete payoffs, in order.

**1. A new route cannot forget its permission check.** Right now the only thing
stopping someone from adding `postRouter.route("/drafts").get(listDrafts)` with
no `checkRolePermissions` call inside the handler is discipline. When the
required permission is declared *on the route*, its absence is visible in the
routing table rather than buried on line 7 of a controller.

**2. The route file becomes the authorization documentation.** Today, answering
"which permission does `PUT /api/users/:userId` need?" means opening
`user.route.ts`, following the import, and reading the controller. After this it
is one line in one file:

```ts
userRouter.route("/:userId")
  .get(requirePermission("view", "user"), viewUser)
  .put(updateUser)                                     // self-service: checked in-controller
  .delete(requirePermission("delete", "user"), deleteUser);
```

**3. Controllers shrink by ~30%.** `listUsers` goes from 9 lines of preamble to
1. That is not cosmetic — it is 8 fewer lines per file where a subtle variation
can hide.

## The design

The critical constraint, and the reason this is a *partial* migration rather than
a wholesale one: **middleware runs before the target row is loaded.** It can
answer *"may this role do this verb on this resource type?"* It cannot answer
*"...on this particular row, owned by this particular person?"*

That second question needs `getHighestUserRole(targetUserId)`, which needs a
`targetUserId` that often comes from the database, not the URL. So:

> **Capability checks move to middleware. Ownership and hierarchy checks stay in
> controllers.**

Draw that line explicitly and the design is straightforward.

### The middleware

```ts
// server/src/middleware/requirePermission.middleware.ts
import type { NextFunction, Request, Response } from "express";
import { asyncMiddleware } from "@/utils/asyncMiddleware.ts";
import { checkRolePermissions } from "@/utils/helper.ts";
import { parsePositiveInt } from "@/utils/validation.util.ts";
import type { ACTIONS_TYPES, RESOURCES_TYPES } from "@/types/commonTypes.ts";

/**
 * Coarse capability gate: does the authenticated actor's role set grant
 * `action` on `resource` at all?
 *
 * This deliberately does NOT check ownership or role hierarchy -- those need the
 * target row, which is not loaded yet. Controllers that act on a specific record
 * must still call assertCanManageUser / assertCanActOnPost after loading it.
 * See report/vulnerabilities/11 and 20.
 */
const requirePermission = (action: ACTIONS_TYPES, resource: RESOURCES_TYPES) =>
  asyncMiddleware(async (req: Request, _res: Response, _next: NextFunction) => {
    const actorId = parsePositiveInt(req.user.uId, "actorId");
    await checkRolePermissions(actorId, action, resource);
  });

/** Requires every listed permission. Used by listRolesAndTherePermissions. */
const requireAllPermissions = (
  ...pairs: Array<[ACTIONS_TYPES, RESOURCES_TYPES]>
) =>
  asyncMiddleware(async (req: Request) => {
    const actorId = parsePositiveInt(req.user.uId, "actorId");
    for (const [action, resource] of pairs) {
      await checkRolePermissions(actorId, action, resource);
    }
  });

export { requirePermission, requireAllPermissions };
```

`asyncMiddleware` already handles the "call `next()` unless the handler did"
logic, so this composes cleanly with the existing stack.

### The routes

```ts
// server/src/routes/user.route.ts
import { requirePermission } from "@/middleware/requirePermission.middleware.ts";

const userRouter: Router = Router();
userRouter.use(checkCookieSignature);
userRouter.use(authenticatedRateLimiting);

userRouter
  .route("/")
  .get(requirePermission("view", "user"), listUsers)
  // createUser needs create:user AND assign:role -- both are coarse checks.
  .post(requireAllPermissions(["create", "user"], ["assign", "role"]), createUser);

userRouter
  .route("/:userId")
  .get(requirePermission("view", "user"), viewUser)
  // updateUser is deliberately NOT gated here: a user updating themselves needs
  // no permission at all. The controller applies update:user only when
  // actorId !== targetUserId. Moving it here would break self-service.
  .put(updateUser)
  .delete(requirePermission("delete", "user"), deleteUser);
```

That comment on `.put()` is the most important line in the change. There are
three routes with conditional authorization that **must not** be moved:

| Route | Why it stays in the controller |
| --- | --- |
| `PUT /api/users/:userId` | Self-update requires no permission; updating others requires `update:user` |
| `PUT /api/posts/:postId` | Post owners may always update their own post |
| `POST /api/auth/logout` | No permission model applies |

```ts
  const actorId = parsePositiveInt(req.user.uId, "actorId");
  const { page, pageSize, limit, offset } = parsePaginationQuery(req.query);
  // ... straight to the work
});
```

## Migration plan

Do this in five steps, running `pnpm test:v2` after each.

1. **Add the middleware file.** No behaviour change.
2. **Add `requirePermission` to routes while leaving the controller checks in
   place.** The check now runs twice — harmless, and it proves the middleware
   resolves the same answer. Tests must stay green.
3. **Remove the now-duplicated `checkRolePermissions` calls** from the
   unconditional controllers, one file at a time.
4. **Remove the `if (!req.user)` blocks.** These are unreachable behind
   `checkCookieSignature`. If you want to keep a safety net, put a single
   assertion in `requirePermission` rather than twenty in controllers.
5. **Standardise the remaining `parsePositiveInt(req.user.uId, ...)` label** to
   `"actorId"` everywhere, or extract a tiny helper:
   ```ts
   const getActorId = (req: Request) => parsePositiveInt(req.user.uId, "actorId");
   ```

Step 2 is what makes this safe. Do not skip it.

## Interaction with other findings

- **[Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md)**
  — this suggestion *helps* but does not fix it. Moving the coarse check to
  middleware means it runs before any transaction opens, which removes the
  deadlock for those call sites. But `getHighestUserRole` calls inside
  transactions still need the `db` parameter. **Do Vulnerability 08 first**; it
  is a smaller change and this builds on it.
- **[Vulnerability 02](../vulnerabilities/02.overpermissive-default-user-role.md)**
  — that finding introduces a **non-throwing** `hasRolePermission` for
  "filter rather than reject" cases (`listSessions` showing only your own rows).
  `requirePermission` cannot express that. Those routes must not get the
  middleware. **Design both together** or you will build a middleware that cannot
  accommodate finding 02's fix.
- **[Vulnerability 11](../vulnerabilities/11.session-revocation-and-peer-actions-lack-hierarchy-checks.md)**
  and **[Vulnerability 20](../vulnerabilities/20.updatepost-and-post-ownership-inconsistencies.md)**
  — both add `assertCanManageUser` / `assertCanActOnPost` **inside** controllers.
  That is the boundary this suggestion defines. No conflict; they are the other
  half of the same design.
- **[Vulnerability 19](../vulnerabilities/19.nested-session-routes-run-auth-and-rate-limit-twice.md)**
  — **fix that first.** Attaching more middleware to `userRouter` while the
  nested-mount bug exists means `requirePermission` also runs twice on
  `/api/users/:userId/sessions`, doubling the permission query too.
- **[Suggestion 08](./08.single-validation-middleware.md)** — the same pattern
  applied to validation. Build both as route-level decorators so a route reads
  `validate({ params, body }), requirePermission(...), handler`. Design the
  composition once.

## What you already got right

- **`checkRolePermissions` is a single function**, used identically everywhere.
  There is no scattered `if (role === "admin")` logic anywhere in the codebase.
  That is precisely what makes this a mechanical refactor instead of an
  archaeology project.
- **The permission query itself is correct and efficient** — a three-table join
  with `LIMIT 1`, parameterised, indexed on `user_roles(user_id)` via the primary
  key and `role_permissions(permission_id)`.
- **Router-level middleware is already the established pattern**
  (`router.use(checkCookieSignature)` in all eight routers), so
  `requirePermission` slots into a structure the codebase already understands.
- **`asyncMiddleware` correctly handles the auto-`next()` case** with the
  `nextCalled` / `headersSent` guard. That is a genuinely subtle piece of Express
  plumbing and it is what makes composable async middleware possible here at all.

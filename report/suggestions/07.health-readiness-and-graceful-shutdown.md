## Two gaps

### The liveness endpoint is a placeholder

```ts
// server/src/app.ts:53
app.get("/", (_req: Request, res: Response) => {
  res.send("Hello World");
});
```

This returns 200 whenever the Node process is accepting connections. It says
nothing about whether the process can do useful work. It will return 200 while:

- PostgreSQL is unreachable (every endpoint 500s)
- The connection pool is deadlocked
  ([Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md))
- Redis is down and **every rate limiter is silently disabled**
  ([Vulnerability 07](../vulnerabilities/07.rate-limiters-fail-open.md))

That third case is the important one. There is currently **no way to ask "are the
security controls on right now?"** short of grepping stdout for
`"Bypassing"`.

### The shutdown leaves connections open

```ts
// server/index.ts
const gracefulShutdown = (signal: string) => {
  server.close((err?: Error) => {
    if (err) { console.error(...); process.exit(1); }
    console.log("HTTP server closed.");

    // TODO: Add database connection closure here when implemented
    // e.g., await db.disconnect();

    console.log("Process completely terminated.");
    process.exit(0);
  });

  setTimeout(() => { /* force exit */ }, 10000).unref();
};
```

Your own TODO. `process.exit(0)` fires with the pool still holding up to ten
PostgreSQL connections and an open Redis socket. On a rolling deploy this means:

- **In-flight transactions are killed mid-flight.** `server.close()` waits for
  in-flight *HTTP* requests, so a request that has committed will finish. But one
  that is mid-transaction when the 10-second timer fires gets its connection
  yanked, and PostgreSQL rolls it back — correct, but it surfaces as a 500 to a
  user who was told nothing.
- **PostgreSQL keeps the backends around** until its own TCP timeout, so a fast
  redeploy loop can exhaust `max_connections` with orphans from dead processes.
- **`SHUTDOWN_GRACE_MS` is defined in `envHelper` and never used** — the timeout
  is hardcoded to `10000`.

## The suggestion

### 1. Three endpoints, three questions

```ts
// server/src/routes/health.route.ts
import { Router } from "express";
import { pool } from "@/config/db.connect.ts";
import { redisClient } from "@/config/redis.connect.ts";
import { isRedisRateLimitReady } from "@/utils/rateLimit.util.ts";
import { asyncHandler } from "@/utils/asyncHandler.ts";

const healthRouter: Router = Router();

let isShuttingDown = false;
const beginShutdown = () => { isShuttingDown = true; };

/** Liveness: is the process alive? Never touches dependencies -- a failing
 *  dependency must not cause the orchestrator to restart a healthy process. */
healthRouter.get("/healthz", (_req, res) => {
  res.status(200).json({ status: "ok", uptimeSeconds: Math.floor(process.uptime()) });
});

/** Readiness: should this instance receive traffic? Checks dependencies, and
 *  reports unready during shutdown so the load balancer drains us first. */
healthRouter.get("/readyz", asyncHandler(async (_req, res) => {
  if (isShuttingDown) {
    res.status(503).json({ status: "shutting_down" });
    return;
  }

  const [database, redis] = await Promise.all([
    pool.query("SELECT 1").then(() => "ok" as const).catch(() => "unavailable" as const),
    redisClient.ping().then(() => "ok" as const).catch(() => "unavailable" as const),
  ]);

  // PostgreSQL is required. Redis is not -- the app degrades without it (see
  // vulnerabilities/07), so a Redis outage must not remove every instance from
  // the load balancer at once.
  const ready = database === "ok";

  res.status(ready ? 200 : 503).json({
    status: ready ? "ready" : "not_ready",
    checks: {
      database,
      redis,
      // The line that answers "are the rate limiters actually enforcing?"
      rateLimitersEnforcing: isRedisRateLimitReady(),
    },
  });
}));

/** Diagnostics: operator-facing detail. Authenticated -- this reveals topology. */
healthRouter.get("/statusz", checkCookieSignature, asyncHandler(async (req, res) => {
  await checkRolePermissions(parsePositiveInt(req.user.uId, "actorId"), "view", "migration");

  res.json({
    version: process.env["npm_package_version"] ?? "unknown",
    nodeEnv: env.NODE_ENV,
    uptimeSeconds: Math.floor(process.uptime()),
    memoryMb: Math.round(process.memoryUsage().rss / 1024 / 1024),
    pool: { total: pool.totalCount, idle: pool.idleCount, waiting: pool.waitingCount },
    redis: { status: redisClient.status },
    // Confirms the deployment topology -- see vulnerabilities/22.
    trustProxy: req.app.get("trust proxy"),
    observedClientIp: req.ip,
    forwardedFor: req.get("x-forwarded-for") ?? null,
  });
}));

export { healthRouter, beginShutdown };
```

Three design points that matter:

- **Liveness must not check dependencies.** If `/healthz` returned 503 when
  PostgreSQL was down, Kubernetes would restart every pod — turning a database
  blip into a crash loop that guarantees a slower recovery.
- **`pool.waitingCount` on `/statusz`** is the direct readout for
  [Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md).
  A non-zero, non-decreasing `waitingCount` with `idle: 0` *is* the deadlock.
- **`trustProxy` / `observedClientIp` / `forwardedFor`** make
  [Vulnerability 22](../vulnerabilities/22.trust-proxy-misconfiguration-enables-limit-bypass.md)
  verifiable in a deployed environment without a throwaway debug route.

Mount above the rate limiter so a probe cannot be throttled, and **replace** the
`"Hello World"` route:

```ts
// server/src/app.ts
app.use(healthRouter);        // before app.use("/api", globalRateLimiting)
```

### 2. Finish the shutdown

```ts
// server/index.ts
import app from "./src/app.ts";
import env from "@/utils/envHelper.ts";
import { closeDbPool } from "@/config/db.connect.ts";
import { redisClient } from "@/config/redis.connect.ts";
import { beginShutdown } from "@/routes/health.route.ts";
import { logger } from "@/utils/logger.ts";

const server = app.listen(env.PORT, () => {
  logger.info("Server started", { port: env.PORT, env: env.NODE_ENV });
});

let shuttingDown = false;

const gracefulShutdown = async (signal: string) => {
  if (shuttingDown) return;          // SIGTERM then SIGINT must not run this twice
  shuttingDown = true;

  logger.info("Shutdown initiated", { signal });

  // 1. Fail readiness FIRST, so the load balancer stops sending new requests
  //    while we are still able to finish the ones in flight.
  beginShutdown();
  await new Promise((resolve) => setTimeout(resolve, 2_000));   // drain window

  // 2. Hard deadline. Unref'd so it cannot itself keep the process alive.
  const forceExit = setTimeout(() => {
    logger.error("Shutdown timed out, forcing exit");
    process.exit(1);
  }, env.SHUTDOWN_GRACE_MS).unref();     // <-- the env var, finally used

  try {
    // 3. Stop accepting connections; wait for in-flight requests.
    await new Promise<void>((resolve, reject) => {
      server.close((error) => (error ? reject(error) : resolve()));
    });
    logger.info("HTTP server closed");

    // 4. NOW close dependencies -- after the last request has finished with them.
    await Promise.allSettled([closeDbPool(), redisClient.quit()]);
    logger.info("Connections closed. Shutdown complete.");

    clearTimeout(forceExit);
    process.exit(0);
  } catch (error) {
    logger.error("Error during shutdown", error);
    process.exit(1);
  }
};

process.on("SIGINT",  () => void gracefulShutdown("SIGINT"));
process.on("SIGTERM", () => void gracefulShutdown("SIGTERM"));
```

The ordering is the whole point: **drain, then stop accepting, then close
dependencies.** Closing the pool before `server.close()` resolves would break
requests that are still running. The 2-second readiness window before
`server.close()` is what lets a load balancer notice and stop routing — without
it, a rolling deploy drops the requests already in the balancer's queue.

Also fix the two existing handlers:

```ts
process.on("uncaughtException", (error) => {
  logger.error("Uncaught exception, shutting down", error);
  void gracefulShutdown("uncaughtException");     // was: process.exit(1) immediately
});

process.on("unhandledRejection", (reason) => {
  logger.error("Unhandled rejection, shutting down", reason);
  void gracefulShutdown("unhandledRejection");
});
```

Note the current `uncaughtException` handler calls `process.exit(1)` **directly**,
killing in-flight requests instantly. The rejection handler does call
`server.close()` — inconsistent, and the wrong one is the more aggressive.

## What you already got right

- **`SIGINT` and `SIGTERM` are both handled**, with `server.close()` rather than a
  bare `process.exit`. Most Node projects handle neither and get SIGKILLed with
  requests in flight.
- **The forced-exit timer uses `.unref()`**, so it does not itself keep the event
  loop alive and delay a clean shutdown. That is a genuinely subtle detail and
  getting it right is unusual.
- **`uncaughtException` and `unhandledRejection` are both handled and both exit
  non-zero.** Continuing after an uncaught exception leaves the process in an
  undefined state; you correctly chose to die. The refinement is only *how*.
- **The TODO is in exactly the right place** with the right note
  (`e.g., await db.disconnect()`). You knew what was missing — this suggestion is
  mostly "here is the code for the comment you already wrote."
- **`SHUTDOWN_GRACE_MS` already exists in the environment schema** with a sensible
  default and a description. The configuration surface was designed for this; it
  just needs wiring up.
- **`testDbConnection()`** already does the exact query `/readyz` needs, so the
  readiness check reuses an established pattern rather than inventing one.

# 08. Validate params, query and body in one declarative middleware

| **Files**    | all of [server/src/controllers/](../../server/src/controllers/), all of [server/src/routes/](../../server/src/routes/), [validation.util.ts](../../server/src/utils/validation.util.ts) |

## Three validation mechanisms for three input sources

Right now each part of the request is validated differently, in different places,
producing different error shapes.

**Body** — a Zod schema parsed inside the controller:

```ts
// server/src/controllers/users/createUser.ts
const { fullname, email, password, roleName } = CreateUserRequestSchema.parse(req.body);
// throws ZodError -> errorHandler returns 400 with a `details` array
```

**Path params** — a hand-rolled helper:

```ts
// server/src/controllers/users/deleteUser.ts
const targetUserId = parsePositiveInt(req.params["userId"], "userId");
// throws AppError.badRequest -> 400 with a plain string, NO `details`
```

**Query** — a third helper:

```ts
// server/src/controllers/users/listUsers.ts
const { page, pageSize, limit, offset } = parsePaginationQuery(req.query);
// throws AppError.badRequest("Pagination query must use positive page and pageSize values.")
```

**And sometimes nothing at all:**

```ts
// server/src/controllers/roles/deleteRole.ts
const roleNameParam = req.params["roleName"];
if (!roleNameParam) throw AppError.badRequest("Role name is required");
// -> passed straight into a query. Not validated against ROLES_LIST, not
//    length-checked, despite RoleNameParamsSchema existing in api.contracts.ts.
```

The consequences:

- **The OpenAPI document promises validation that does not happen.**
  `RoleNameParamsSchema` declares `roleName` as `z.enum(ROLES_LIST)` and appears
  in the spec. `updateRole` and `deleteRole` never use it. A client reading the
  contract believes `/api/roles/anything` returns 400; it actually returns 404
  from a database lookup.
- **Clients get two different 400 shapes.** A bad body yields
  `{ message, details: [{ code, path, message }] }`; a bad path param yields
  `{ message }` with no `details`. The client's `ApiClientError` carries `details`
  through, so form-field error mapping works for one and not the other.
- **Validation runs after authorization**, so an invalid request still costs a
  permission query. Minor, but backwards.
- `UserIdParamsSchema`, `PostIdParamsSchema`, `SessionIdParamsSchema`,
  `PermissionIdParamsSchema` and `PaginationQuerySchema` all exist in
  `api.contracts.ts` **and are used only to generate the OpenAPI document.** They
  are never applied at runtime.

## The suggestion

One middleware that applies the schemas you already wrote.

```ts
// server/src/middleware/validate.middleware.ts
import type { NextFunction, Request, Response } from "express";
import { ZodError, type ZodTypeAny } from "zod";

type ValidationSchemas = {
  params?: ZodTypeAny;
  query?: ZodTypeAny;
  body?: ZodTypeAny;
};

declare global {
  namespace Express {
    interface Request {
      validated: { params: unknown; query: unknown; body: unknown };
    }
  }
}

/**
 * Validates the request against the given schemas and stores the parsed,
 * coerced results on `req.validated`.
 *
 * Parsed values are NOT written back to req.params / req.query -- those are
 * getters in Express 5 and assigning to them is unreliable. Controllers read
 * from req.validated, which is correctly typed and already coerced.
 */
const validate = (schemas: ValidationSchemas) =>
  (req: Request, _res: Response, next: NextFunction) => {
    try {
      req.validated = {
        params: schemas.params ? schemas.params.parse(req.params) : req.params,
        query:  schemas.query  ? schemas.query.parse(req.query)   : req.query,
        body:   schemas.body   ? schemas.body.parse(req.body)     : req.body,
      };
      next();
    } catch (error) {
      // Let errorHandler produce the standard ZodError shape with `details`.
      next(error instanceof ZodError ? error : error);
    }
  };

export { validate };
export type { ValidationSchemas };
```

The `req.validated` indirection is deliberate. **Express 5 made `req.query` a
getter**, so the common `req.query = schema.parse(req.query)` trick from Express
4 tutorials silently fails or throws. Writing to a separate property sidesteps
that entirely and has the bonus of being typed.

### Routes become self-documenting

```ts
// server/src/routes/user.route.ts
userRouter
  .route("/")
  .get(
    requirePermission("view", "user"),
    validate({ query: PaginationQuerySchema }),
    listUsers,
  )
  .post(
    requireAllPermissions(["create", "user"], ["assign", "role"]),
    validate({ body: CreateUserRequestSchema }),
    createUser,
  );

userRouter
  .route("/:userId")
  .get(requirePermission("view", "user"), validate({ params: UserIdParamsSchema }), viewUser)
  .put(validate({ params: UserIdParamsSchema, body: UpdateUserRequestSchema }), updateUser)
  .delete(
    requirePermission("delete", "user"),
    validate({ params: UserIdParamsSchema }),
    deleteUser,
  );
```

Every route now states, in one place: what permission it needs, what shape it
accepts, and what it does. That is the same line as the OpenAPI document —
which is the point.

### Controllers get typed input

```ts
// server/src/controllers/users/deleteUser.ts
const deleteUser = asyncHandler(async (req, res) => {
  const actorId = parsePositiveInt(req.user.uId, "actorId");
  const { userId: targetUserId } = req.validated.params as z.infer<typeof UserIdParamsSchema>;
  // targetUserId is already a positive integer -- coerced and validated.
  // ...
});
```

The `as` cast is unfortunate. If you want it fully type-safe, make `validate`
generic and type the handler:

```ts
const validate = <P extends ZodTypeAny, Q extends ZodTypeAny, B extends ZodTypeAny>(
  schemas: { params?: P; query?: Q; body?: B },
) => /* ... returns a middleware that narrows Request */;
```

That is more type gymnastics than it is worth for a project this size. The cast
in one line per controller is a reasonable trade; just be consistent.

### Fill the gaps the schemas already describe

Two routes gain validation they should always have had:

```ts
roleRouter
  .route("/:roleName")
  .put(requirePermission("update", "role"),
       validate({ params: RoleNameParamsSchema, body: UpdateRoleRequestSchema }), updateRole)
  .delete(requirePermission("delete", "role"),
          validate({ params: RoleNameParamsSchema }), deleteRole);
```

Note: `RoleNameParamsSchema` is currently `z.enum(ROLES_LIST)`. If you take
[Suggestion 03](./03.database-driven-role-hierarchy.md), it becomes a regex-
constrained string instead. Either way, the route now enforces what the spec says.

### Keep `parsePositiveInt` for non-request values

`parsePositiveInt(req.user.uId, "actorId")` validates a **JWT claim**, not request
input. That stays — it is a different concern (defending against a malformed
token payload) and belongs where it is. Likewise `api.mappers.ts` uses
`parsePositiveInt` on database rows. Only the `req.params` / `req.query` uses move.

## Migration plan

1. Add `validate.middleware.ts`. No behaviour change.
2. Add `validate(...)` to routes **while leaving the controller parsing in
   place**. Validation runs twice; both must agree. Run `pnpm test:v2`.
3. Convert controllers to read `req.validated`, one resource at a time.
4. Add validation to the two currently-unvalidated role routes. **This is a
   behaviour change** — `PUT /api/roles/not-a-real-role` starts returning 400
   instead of 404. Update tests.
5. Remove `parsePaginationQuery`'s validation half; keep the
   `limit`/`offset`/`makePaginationMeta` derivation, which is genuinely useful.

## Interaction with other findings

- **[Suggestion 01](./01.centralize-authorization-in-middleware.md)** — same
  route-decorator pattern, same file. **Design the middleware ordering together**:
  `requirePermission` before `validate`, or after? Recommendation: **permission
  first**, so an unauthorized caller cannot use validation error messages to probe
  your schemas. Pick one order and apply it everywhere.
- **[Vulnerability 19](../vulnerabilities/19.nested-session-routes-run-auth-and-rate-limit-twice.md)**
  — validation attached at *router* level would double-execute on the nested
  session routes. The per-route attachment above avoids this, but **fix 19 first**
  regardless.
- **[Suggestion 16](./16.openapi-as-contract-source-of-truth.md)** — this closes
  the gap between documented and enforced validation, which is that suggestion's
  central goal. Strongly complementary; this is the runtime half.
- **[Vulnerability 18](../vulnerabilities/18.weak-password-policy.md)** — changes
  the password and fullname schemas. Do that first so you validate against the
  corrected constraints rather than migrating twice.
- **No contradiction** with anything.

## What you already got right

- **The schemas already exist and are already correct.** `UserIdParamsSchema`,
  `PostIdParamsSchema`, `SessionIdParamsSchema`, `PermissionIdParamsSchema`,
  `RoleNameParamsSchema`, `PaginationQuerySchema` — all written, all with proper
  `z.coerce.number().int().positive()` and OpenAPI `param` metadata. This
  suggestion is not "write validation", it is "run the validation you wrote."
- **`errorHandler` already handles `ZodError` as a first-class case** with
  structured `details`, so the middleware needs no error handling of its own —
  it just re-throws and the existing machinery produces the right response.
- **`z.coerce`** is used correctly throughout for query and path values, which
  arrive as strings. That is the detail that makes `z.number()` work on a URL
  segment, and it is applied consistently.
- **`parsePositiveInt` and `parseEmail` are reused across controllers and
  mappers** rather than duplicated inline — the instinct to centralise validation
  helpers is already there. The suggestion is to move the *request* half of that
  up into the routing layer where it composes.
- **`parsePaginationQuery` returning `{ page, pageSize, limit, offset }`** is a
  nice touch: it validates *and* derives the SQL parameters, so no controller
  computes `(page - 1) * pageSize` by hand. Keep that.

## The finding

`ConfirmDialog` and `EditDialog` set the right ARIA attributes but implement none
of the behaviour those attributes promise:

```tsx
// client/src/components/ui/Dialogs.tsx
export function ConfirmDialog({ open, title, description, /* ... */ onConfirm, onClose }) {
  if (!open) return null

  return (
    <div className="modal-backdrop" role="presentation" onMouseDown={onClose}>
      <section
        aria-modal="true"                                  // <-- claims modality
        className="confirm-dialog"
        role="dialog"
        onMouseDown={(event) => event.stopPropagation()}
      >
        <div>
          <h2>{title}</h2>                                  {/* not linked to the dialog */}
          <p>{description}</p>
        </div>
        {/* ... buttons ... */}
      </section>
    </div>
  )
}
```

Five gaps:

**1. No `Escape` to close.** The only ways out are clicking the backdrop or the
Cancel button. `Escape` is the universal dialog dismissal and screen-reader users
in particular expect it.

**2. Focus is never moved into the dialog.** When it opens, focus stays on the
button that triggered it — which is now behind an overlay. A keyboard user
pressing `Tab` walks through the *page behind* the dialog, invisibly.

**3. No focus trap.** `aria-modal="true"` tells assistive technology that content
outside is inert. Nothing enforces it, so `Tab` escapes into the page, and a
screen reader following the DOM order will read content the attribute says does
not exist. That contradiction is worse than omitting the attribute.

**4. Focus is not restored on close.** After confirming a delete, focus returns to
`<body>`. A keyboard user has to `Tab` from the top of the page to get back to
where they were — on a long users table, that is dozens of presses.

**5. `role="dialog"` has no accessible name.** `aria-labelledby` is missing, so a
screen reader announces "dialog" with no indication of what it is for. The `<h2>`
is right there.

### Two smaller items

**The sidebar backdrop.** `AppShell` toggles a `sidebar-open` class on `<body>`
for the mobile drawer. The drawer can be opened and, on a narrow viewport,
overlays the page — with the same focus problems and no `Escape` handler.

**`JsonPreview` in the audit log.** Renders `JSON.stringify(value, null, 2)` in a
`<pre>` with no `max-height`, no scroll container, and no `tabIndex`. A large
`new_values` snapshot produces a very tall block that a keyboard user cannot
scroll independently. (React escapes the content, so there is no XSS concern —
purely a usability one.)

## Why it is worth doing

An IAM admin console is exactly the kind of tool that ends up in a workplace with
accessibility requirements. Beyond compliance, the concrete failure is sharp: the
confirm dialogs guard **destructive, irreversible actions** — delete user, revoke
all sessions, delete role. A keyboard user who cannot tell where focus is, and
whose `Escape` key does nothing, is one stray `Enter` away from deleting a user.

The fix is one hook and about fifteen lines.

## The suggestion

### A reusable dialog hook

```tsx
// client/src/hooks/useDialogFocus.ts
import { useEffect, useRef } from 'react'

const FOCUSABLE =
  'a[href], button:not([disabled]), textarea:not([disabled]), input:not([disabled]), ' +
  'select:not([disabled]), [tabindex]:not([tabindex="-1"])'

/**
 * Makes a dialog behave the way `role="dialog" aria-modal="true"` claims:
 * moves focus in on open, traps Tab inside, closes on Escape, and restores
 * focus to the trigger on close.
 */
export function useDialogFocus(open: boolean, onClose: () => void) {
  const containerRef = useRef<HTMLElement>(null)
  const previouslyFocused = useRef<HTMLElement | null>(null)

  useEffect(() => {
    if (!open) return

    previouslyFocused.current = document.activeElement as HTMLElement | null

    const container = containerRef.current
    const focusable = container?.querySelectorAll<HTMLElement>(FOCUSABLE)
    // Prefer the first control; fall back to the container itself.
    ;(focusable?.[0] ?? container)?.focus()

    const onKeyDown = (event: KeyboardEvent) => {
      if (event.key === 'Escape') {
        event.preventDefault()
        onClose()
        return
      }

      if (event.key !== 'Tab' || !container) return

      const items = Array.from(container.querySelectorAll<HTMLElement>(FOCUSABLE))
      if (items.length === 0) return

      const first = items[0]
      const last = items[items.length - 1]
      const active = document.activeElement

      if (event.shiftKey && active === first) {
        event.preventDefault()
        last.focus()
      } else if (!event.shiftKey && active === last) {
        event.preventDefault()
        first.focus()
      }
    }

    document.addEventListener('keydown', onKeyDown)

    // Prevent the page behind from scrolling while the dialog is open.
    const previousOverflow = document.body.style.overflow
    document.body.style.overflow = 'hidden'

    return () => {
      document.removeEventListener('keydown', onKeyDown)
      document.body.style.overflow = previousOverflow
      previouslyFocused.current?.focus()
    }
  }, [open, onClose])

  return containerRef
}
```

### Applied

```tsx
// client/src/components/ui/Dialogs.tsx
export function ConfirmDialog({
  open, title, description, confirmLabel = 'Confirm', cancelLabel = 'Cancel',
  pending = false, onConfirm, onClose,
}: ConfirmDialogProps) {
  const dialogRef = useDialogFocus(open, onClose)
  const titleId = useId()
  const descriptionId = useId()

  if (!open) return null

  return (
    <div className="modal-backdrop" role="presentation" onMouseDown={onClose}>
      <section
        ref={dialogRef}
        aria-modal="true"
        aria-labelledby={titleId}
        aria-describedby={descriptionId}
        className="confirm-dialog"
        role="dialog"
        tabIndex={-1}
        onMouseDown={(event) => event.stopPropagation()}
      >
        <div>
          <h2 id={titleId}>{title}</h2>
          <p id={descriptionId}>{description}</p>
        </div>
        <div className="button-row dialog-actions">
          <Button type="button" variant="ghost" disabled={pending} onClick={onClose}>
            {cancelLabel}
          </Button>
          <Button type="button" variant="danger" disabled={pending} onClick={onConfirm}>
            {confirmLabel}
          </Button>
        </div>
      </section>
    </div>
  )
}
```

Same treatment for `EditDialog` — note it already has a `<h2>` and a `<form>`, so
it only needs `useDialogFocus`, `aria-labelledby`, and `tabIndex={-1}`.

**One deliberate choice:** the hook focuses the *first* focusable element, which
in `ConfirmDialog` is Cancel. For a destructive confirmation that is correct — the
safe option should be under the cursor. Do not "improve" it by focusing Confirm.

### The `<dialog>` alternative

Modern browsers support `<dialog>` with `showModal()`, which gives focus
trapping, `Escape`, and an inert backdrop natively. It is a bigger change (the
element must be in the DOM to call `showModal()`, so the `if (!open) return null`
pattern has to go) but it removes the hand-rolled trap entirely. Worth
considering if you touch these components substantially; the hook above is the
lower-risk path today.

## What you already got right

- **`role="dialog"` and `aria-modal="true"` are already there.** You knew dialogs
  need ARIA semantics. The behaviour just was not implemented to match — which is
  a much better starting point than a `<div>` with an `onClick`.
- **Backdrop dismissal uses `onMouseDown` with `stopPropagation` on the panel.**
  Using `mousedown` rather than `click` is the correct choice: with `click`, a
  drag that starts inside the dialog and releases on the backdrop would close it,
  which is a genuinely annoying bug. You avoided it.
- **Buttons are `disabled` while a mutation is pending**, preventing double
  submission on destructive actions.
- **`EditDialog` resets the form when `open` flips true**
  (`useEffect(() => { if (open) form.reset(defaultValues) }, [...])`), so a
  reopened dialog does not show the previous record's values. Subtle and easy to
  get wrong.
- **Semantic HTML throughout** — real `<button>` elements (so `Enter` and `Space`
  work for free), `<h2>` headings, `<form onSubmit>` with `handleSubmit` so
  `Enter` submits. Most of the accessibility work is already done by not fighting
  the platform.
- **`ErrorBoundary` renders a usable recovery UI** with a real button rather than
  a blank screen.
- **`useConfirmAction` centralises the confirm-then-act flow**, so every
  destructive action goes through one dialog implementation. That is why this fix
  lands in one file instead of ten.

## The finding

The `QueryClient` is constructed inline in `main.tsx`:

```tsx
// client/src/main.tsx
const queryClient = new QueryClient({
  defaultOptions: {
    queries: { retry: 1, staleTime: 20_000, retryOnMount: false },
    mutations: { retry: 1 },
  },
});

createRoot(document.getElementById("root")!).render(
  <ErrorBoundary>
    <StrictMode>
      <QueryClientProvider client={queryClient}>...</QueryClientProvider>
    </StrictMode>
  </ErrorBoundary>,
);
```

It is never exported, so anything outside the React tree cannot reach it. The
axios interceptor is outside the React tree:

```ts
// client/src/api/client.ts:86
try {
  await refreshSession();
  return api(originalRequest);
} catch {
  useAuthStore.getState().clearAuth();
  window.location.assign("/login");        // <-- no queryClient.clear()
}
```

Compare with the deliberate logout path, which does it right:

```tsx
// client/src/components/layout/AppShell.tsx:49
const logoutMutation = useMutation({
  mutationFn: authApi.logout,
  onSettled: () => {
    clearAuth()
    queryClient.clear()                    // <-- correct
    navigate('/login', { replace: true })
  },
})
```

So: **clicking "Log out" clears the cache. Being logged out by an expired session
does not.**

## Why it matters

Three consequences, in order.

**1. Cached data survives an involuntary logout — in memory, briefly.**
`window.location.assign("/login")` triggers a full page navigation, which
destroys the JavaScript heap and takes the cache with it. So the practical window
is milliseconds and nothing persists to disk. This is a *hygiene* problem rather
than a live leak, and I want to be accurate about that.

But the ordering is fragile: if someone later replaces `window.location.assign`
with `navigate('/login')` — which is the natural React Router refactor, and
strictly better UX because it avoids a full reload — the cache **survives**. At
that moment a shared machine can show the previous user's user list, session
table and audit log after a session expiry, because React Query serves stale data
from cache while the refetch is in flight. The fix costs one line now and
prevents that.

**2. Privilege changes do not invalidate the data they affect.** `UsersPage`
handles this partially:

```tsx
const assignRole = useMutation({
  mutationFn: ({ userId, roleName }) => userRolesApi.assign(userId, { roleName }),
  onSuccess: () => {
    invalidateUsers()
    invalidateAuthMe()          // good -- capabilities may have changed
  },
})
```

That is thoughtful. But `RolePermissionsPage`'s assign/revoke mutations change
what **every** role can do, and `PermissionsPage`'s create/delete change the
permission set globally. Neither invalidates `authMe`. So a super-admin who
revokes `posts.create` from their own role keeps seeing the "Create post" form
until `staleTime: 20_000` elapses and something triggers a refetch. Clicking it
produces a 403 toast.

**3. `retryOnMount: false` has a side effect worth knowing about.** The comment in
`main.tsx` explains the intent well — stop a failed `authMe` from refetching every
time `AppShell` remounts. Correct. But combined with `staleTime: 20_000`, a query
that errored stays errored until manually invalidated or refetched. `QueryErrorState`
provides a retry button, so the escape hatch exists. Just be aware that "it fixed
itself after a while" will not happen.

## The suggestion

### 1. Extract the `QueryClient`

```ts
// client/src/api/queryClient.ts
import { QueryClient } from '@tanstack/react-query'

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      retry: 1,
      staleTime: 20_000,
      // Prevent a failed cached query from refetching just because a new
      // component mounts and observes the same key. An errored ["auth","me"]
      // should not refetch merely because AppShell remounts.
      retryOnMount: false,
    },
    mutations: { retry: 1 },
  },
})

/** Drops every cached response. Call on any transition between identities. */
export const resetQueryCache = () => {
  queryClient.clear()
}
```

Keep the existing comment — it explains a non-obvious choice and is worth
preserving verbatim.

```tsx
// client/src/main.tsx
import { queryClient } from './api/queryClient'
// ...
<QueryClientProvider client={queryClient}>
```

### 2. Clear on involuntary logout

```ts
// client/src/api/client.ts
import { queryClient } from './queryClient'

// ...
} catch {
  useAuthStore.getState().clearAuth();
  queryClient.clear();                    // <-- the fix
  window.location.assign("/login");
}
```

**Watch for a circular import.** `client.ts` imports `queryClient.ts`, and
`queryClient.ts` must not import anything from `client.ts`. As written above it
imports only `@tanstack/react-query`, so this is safe — keep it that way.

### 3. Invalidate `authMe` wherever permissions can change

```tsx
// client/src/pages/RolePermissionsPage.tsx
const invalidateAuthMe = () =>
  queryClient.invalidateQueries({ queryKey: queryKeys.authMe })

const assignPermission = useMutation({
  mutationFn: rolePermissionsApi.assign,
  onSuccess: () => {
    toast.success('Permission assigned')
    queryClient.invalidateQueries({ queryKey: ['role-permissions'] })
    invalidateAuthMe()          // the actor's own capabilities may have changed
  },
})
```

Same for `revokePermission`, and for `PermissionsPage`'s create/remove mutations.

A cleaner framing: any mutation touching `roles`, `permissions`,
`role_permissions` or `user_roles` should invalidate `authMe`. Rather than
remembering at each site, wire it once:

```ts
// client/src/api/queryClient.ts
const PRIVILEGE_QUERY_KEYS = ['roles', 'permissions', 'role-permissions', 'users'] as const

queryClient.getMutationCache().subscribe((event) => {
  if (event.type !== 'updated' || event.mutation?.state.status !== 'success') return
  // Any successful mutation may have changed the actor's effective permissions.
  // Cheap: authMe is one small request and staleTime prevents a storm.
  void queryClient.invalidateQueries({ queryKey: ['auth', 'me'] })
})
```

That is blunt — it refetches `authMe` after *every* successful mutation,
including creating a post. At one small request per mutation, that is an
acceptable trade for never getting it wrong. If you prefer precision, keep the
explicit per-page calls; just apply them consistently.

### 4. Consider `gcTime` for sensitive queries

`audit-logs` and `sessions` responses are the most sensitive things cached. React
Query's default `gcTime` is 5 minutes, so they linger in memory after unmount.
Shortening it for those keys bounds the exposure:

```tsx
const auditLogs = useQuery({
  queryKey: queryKeys.auditLogs(page),
  queryFn: () => auditLogsApi.list({ page, pageSize: DEFAULT_PAGE_SIZE }),
  gcTime: 30_000,
  placeholderData: keepPreviousData,
})
```

Marginal, and it costs a refetch when navigating back. Optional.

## What you already got right

- **`queryClient.clear()` on deliberate logout**, in `onSettled` rather than
  `onSuccess` — so the cache is cleared even if the logout request itself fails.
  That is the correct hook, and choosing it deliberately is not obvious.
- **`invalidateAuthMe()` after role assign/revoke in `UsersPage`.** You already
  identified that changing roles can change the acting user's own capabilities.
  This suggestion extends a pattern you established, not a concept you missed.
- **The `retryOnMount: false` comment in `main.tsx`** is four lines explaining a
  subtle React Query behaviour (observers triggering refetches on mount) and why
  it was disabled. That is exactly what a comment should do — explain a decision
  the code cannot.
- **`queryKeys` is a structured, typed factory** in `constants.ts` with
  `as const` tuples, including parameterised keys like
  `userSessions: (userId, page, pageSize) => [...]`. That is textbook React Query
  key design and it is what makes targeted invalidation possible at all.
- **`keepPreviousData` on paginated queries** so page changes do not blank the
  table, and `placeholderData` used correctly rather than `initialData`.
- **`ErrorBoundary` wraps `StrictMode`**, so a render error in the provider tree
  still produces a usable fallback rather than a white screen.

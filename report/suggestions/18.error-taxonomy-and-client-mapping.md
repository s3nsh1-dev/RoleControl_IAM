# 18. Give errors machine-readable codes so the client can react to them

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |

## The finding

The error envelope carries a human-readable string and nothing a program can
branch on:

```json
{
  "success": false,
  "status": "fail",
  "message": "You do not have permission to delete on user"
}
```

So the client's only options are the HTTP status code and string matching. Today
it uses the status code, which is mostly enough — but the places where it is not
are already visible:

**1. A 401 has three different meanings.**

| Cause | Correct client behaviour |
| --- | --- |
| Access token expired | Refresh silently, retry |
| Access token invalid / malformed | Sign out immediately |
| Session revoked or user deactivated | Sign out immediately, with an explanation |

[client.ts](../../client/src/api/client.ts) treats all three identically — it
attempts a refresh, and if that fails, signs out. That *works*, but it costs a
guaranteed-to-fail round trip for cases 2 and 3, and the user gets no explanation
for case 3 (they were signed out by an administrator, which is worth saying).

**2. A 403 has two different meanings.**

- *"Your role lacks this capability"* → hide the control permanently.
- *"You may not act on this particular target"* (the hierarchy checks from
  [Vulnerability 11](../vulnerabilities/11.session-revocation-and-peer-actions-lack-hierarchy-checks.md))
  → the control is valid, this target is not.

Both surface as a red toast with the raw server sentence.

**3. A 400 from a Zod error and a 400 from `AppError.badRequest` have different
shapes.** The Zod path includes `details: [{ code, path, message }]`; the
`AppError` path does not. So `react-hook-form` field-level error mapping is
possible for body validation and impossible for everything else — which is why
every mutation currently does:

```ts
onError: (error) => toast.error(error.message),
```

A toast for everything, including errors that belong on a specific form field.

**4. Messages are inconsistent in register and tone.** A sample from the codebase:

```
"You do not have permission to delete on post"          // reads like a template
"UNAUTHORIZED REQUEST: USER NOT FOUND"                  // shouting
"Something went wrong while comparing hash strings"     // internal detail
"You cannot delete yourself"                            // good
"Cannot delete the last super-admin"                    // good
"Invalid user session. Please login again. Failed to verify JWT token, Please login again"  // doubled
```

These go straight into user-facing toasts.

## The suggestion

### 1. Add a code to `AppError`

```ts
// server/src/utils/AppError.ts
export const ERROR_CODES = {
  // Authentication
  TOKEN_EXPIRED:        "TOKEN_EXPIRED",
  TOKEN_INVALID:        "TOKEN_INVALID",
  SESSION_REVOKED:      "SESSION_REVOKED",
  ACCOUNT_DEACTIVATED:  "ACCOUNT_DEACTIVATED",
  CREDENTIALS_INVALID:  "CREDENTIALS_INVALID",
  // Authorization
  PERMISSION_DENIED:    "PERMISSION_DENIED",      // your role cannot do this
  HIERARCHY_DENIED:     "HIERARCHY_DENIED",       // not on THIS target
  SELF_ACTION_DENIED:   "SELF_ACTION_DENIED",     // cannot act on yourself
  // Resource
  NOT_FOUND:            "NOT_FOUND",
  ALREADY_EXISTS:       "ALREADY_EXISTS",
  CONSTRAINT_VIOLATION: "CONSTRAINT_VIOLATION",
  SYSTEM_ROLE_PROTECTED:"SYSTEM_ROLE_PROTECTED",  // see vulnerabilities/12
  // Validation and throttling
  VALIDATION_FAILED:    "VALIDATION_FAILED",
  RATE_LIMITED:         "RATE_LIMITED",
  // Fallback
  INTERNAL_ERROR:       "INTERNAL_ERROR",
} as const;

export type ErrorCode = (typeof ERROR_CODES)[keyof typeof ERROR_CODES];

class AppError extends Error {
  public override readonly statusCode: number;
  public readonly isOperational: boolean;
  public readonly status: "fail" | "error";
  public readonly code: ErrorCode;

  constructor(statusCode: number, message: string, code: ErrorCode, isOperational = true) {
    super(message);
    Object.setPrototypeOf(this, new.target.prototype);
    this.statusCode = statusCode;
    this.status = statusCode >= 500 ? "error" : "fail";
    this.code = code;
    this.isOperational = isOperational;
    if (Error.captureStackTrace) Error.captureStackTrace(this, this.constructor);
  }

  static forbidden(message = "Forbidden", code: ErrorCode = ERROR_CODES.PERMISSION_DENIED) {
    return new AppError(403, message, code);
  }
  static unauthorized(message = "Unauthorized", code: ErrorCode = ERROR_CODES.TOKEN_INVALID) {
    return new AppError(401, message, code);
  }
  static notFound(message = "Not Found", code: ErrorCode = ERROR_CODES.NOT_FOUND) {
    return new AppError(404, message, code);
  }
  static badRequest(message = "Bad Request", code: ErrorCode = ERROR_CODES.VALIDATION_FAILED) {
    return new AppError(400, message, code);
  }
  static tooManyRequests(message = "Too many requests") {
    return new AppError(429, message, ERROR_CODES.RATE_LIMITED);
  }
  static internal(message = "Internal Server Error") {
    return new AppError(500, message, ERROR_CODES.INTERNAL_ERROR, false);
  }
}
```

**Every factory has a default code**, so this is backward compatible — existing
`AppError.forbidden("...")` calls keep compiling and get a sensible code. You then
refine the ones that matter:

```ts
// server/src/controllers/users/deleteUser.ts
if (actorId === targetUserId) {
  throw AppError.forbidden("You cannot delete yourself", ERROR_CODES.SELF_ACTION_DENIED);
}
// ...
if (targetHighestRole && !canActorManageRole(actorHighestRole, targetHighestRole)) {
  throw AppError.forbidden("You cannot delete this user", ERROR_CODES.HIERARCHY_DENIED);
}
```

### 2. Emit it

```ts
// server/src/middleware/errorHandler.middleware.ts
return res.status(statusCode).json({
  success: false,
  status,
  code,                                    // <-- new
  message,
  ...(details && { details }),
  ...(exposeStackTraces && trace && { trace }),
});
```

```ts
// server/src/contracts/api.contracts.ts
const ApiErrorSchema = z.object({
  success: z.literal(false),
  status: z.enum(["fail", "error"]),
  code: z.enum(Object.values(ERROR_CODES) as [ErrorCode, ...ErrorCode[]]),
  message: z.string(),
  details: z.array(ApiErrorDetailSchema).optional(),
  trace: z.string().optional(),
}).openapi("ApiError");
```

Regenerate the OpenAPI document and the client types, and `ApiClientError` gets
`code` typed automatically through
[Suggestion 16](./16.openapi-as-contract-source-of-truth.md)'s pipeline.

### 3. Use it on the client

```ts
// client/src/api/client.ts
export class ApiClientError extends Error {
  statusCode: number
  code?: ErrorCode
  details?: ApiErrorBody['details']
  retryAfter?: string
  // ...
}
```

```ts
// the interceptor -- now precise about which 401 this is
if (statusCode === 401 && originalRequest && !originalRequest._retry
    && !isAuthEndpoint(originalRequest.url)) {

  const code = error.response?.data?.code

  // Only an expired token is worth refreshing. The others are terminal.
  if (code === 'TOKEN_EXPIRED') {
    originalRequest._retry = true
    try {
      await refreshSession()
      return await api(originalRequest)
    } catch {
      forceSignOut()
      return Promise.reject(toApiError())
    }
  }

  if (code === 'SESSION_REVOKED' || code === 'ACCOUNT_DEACTIVATED') {
    toast.error(
      code === 'SESSION_REVOKED'
        ? 'Your session was ended by an administrator.'
        : 'Your account has been deactivated.',
    )
    forceSignOut()
    return Promise.reject(toApiError())
  }

  // Unknown or missing code: fall back to the current behaviour.
  originalRequest._retry = true
  try { await refreshSession(); return await api(originalRequest) }
  catch { forceSignOut(); return Promise.reject(toApiError()) }
}
```

The fallback branch matters — it means the client works against a server that has
not adopted codes yet, so the two can be deployed independently.

### 4. Map codes to user-facing copy on the client

```ts
// client/src/api/errorMessages.ts
const MESSAGES: Partial<Record<ErrorCode, string>> = {
  PERMISSION_DENIED:     'Your role does not allow this action.',
  HIERARCHY_DENIED:      'You cannot perform this action on this user.',
  SELF_ACTION_DENIED:    'You cannot perform this action on your own account.',
  ALREADY_EXISTS:        'That record already exists.',
  SYSTEM_ROLE_PROTECTED: 'This is a system role and cannot be modified.',
  RATE_LIMITED:          'Too many requests. Please slow down.',
  INTERNAL_ERROR:        'Something went wrong. Please try again.',
}

export const toUserMessage = (error: unknown) =>
  error instanceof ApiClientError
    ? (error.code && MESSAGES[error.code]) ?? error.message
    : 'Something went wrong'
```

This is where the inconsistent server messages get fixed for users without
rewriting forty `throw` statements: the server sentence stays as developer-facing
detail, and the client renders consistent copy.

### 5. Map `details` onto form fields

```ts
onError: (error) => {
  if (error instanceof ApiClientError && error.details?.length) {
    for (const detail of error.details) {
      const field = detail.path.join('.')
      form.setError(field as never, { message: detail.message })
    }
    return
  }
  toast.error(toUserMessage(error))
}
```

Server-side validation errors now land on the right input instead of in a toast —
which matters most for the cases the client cannot pre-validate, like
"email already taken".

## Scope advice

This is a **4**, not higher, because the current status-code-based handling
mostly works. Adopt it incrementally:

1. Add `code` with defaults. No behaviour change, nothing breaks.
2. Refine codes for the 401 family only — that is where the client gains a real
   improvement (skipping doomed refresh round trips).
3. Add `toUserMessage` and the `details` → form-field mapping.
4. Refine the rest opportunistically as you touch controllers.

Do not stop the world for it.

## Interaction with other findings

- **[Vulnerability 23](../vulnerabilities/23.error-messages-leak-internal-detail.md)**
  discusses `TOKEN_EXPIRED` vs `TOKEN_INVALID` and explicitly defers the decision
  to this suggestion. **This is where it gets decided.** That finding's advice —
  only add the distinction if the client uses it — is satisfied by step 3 above.
- **[Suggestion 12](./12.axios-refresh-interceptor-correctness.md)** edits the
  same interceptor block. **Do 12 first** (it fixes real bugs), then layer codes
  on top.
- **[Vulnerability 01](../vulnerabilities/01.jwt-token-confusion-and-session-revocation-bypass.md)**
  introduces `SESSION_REVOKED` as a real, reachable state — before that fix,
  revoked sessions never produce a 401. The code is only meaningful after it.
- **[Vulnerability 03](../vulnerabilities/03.deactivated-users-can-still-log-in.md)**
  introduces `ACCOUNT_DEACTIVATED` similarly. **But note the constraint from
  [Vulnerability 15](../vulnerabilities/15.login-user-enumeration-via-timing.md):
  the login endpoint must NOT return `ACCOUNT_DEACTIVATED`** — that would
  reintroduce the enumeration oracle the finding closes. Deactivation at *login*
  returns `CREDENTIALS_INVALID`; deactivation detected on an *authenticated
  request* returns `ACCOUNT_DEACTIVATED`. **This is the one genuine contradiction
  risk in this suggestion — get it right.**
- **[Vulnerability 12](../vulnerabilities/12.rbac-self-destruct-via-role-and-permission-deletion.md)**
  introduces `SYSTEM_ROLE_PROTECTED`.
- **[Suggestion 16](./16.openapi-as-contract-source-of-truth.md)** — adding `code`
  to `ApiErrorSchema` regenerates the client types. Batch it with other contract
  changes.

## What you already got right

- **`AppError` is a proper `Error` subclass** with `Object.setPrototypeOf` (needed
  for `instanceof` to work across the ES5 target boundary) and
  `Error.captureStackTrace`. Adding a field is a two-line change because the class
  was built correctly.
- **The `isOperational` flag** already distinguishes "safe to show the user" from
  "generic message only". That is the security-critical half of error taxonomy and
  it is already right; this suggestion adds the ergonomic half.
- **`status` is derived, not stored** (`statusCode >= 500 ? "error" : "fail"`), so
  it cannot contradict the code.
- **Zod errors already produce structured `details`** with `code`, `path` and
  `message` per issue, and `ApiClientError` carries them to the client intact. The
  form-field mapping in step 5 needs no server work — the data is already there,
  just unused.
- **`ApiErrorSchema` is part of the OpenAPI contract**, so the error shape is
  documented and typed on the client. Adding `code` flows through automatically.
- **PostgreSQL error codes are already translated** into safe messages in
  `errorHandler` (`23505` → "Record already exists."). That switch statement is
  the natural place to attach `ALREADY_EXISTS` / `CONSTRAINT_VIOLATION` — the
  mapping logic exists, it just needs a code alongside the string.

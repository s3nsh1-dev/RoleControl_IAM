## The current interceptor

```ts
// client/src/api/client.ts
let refreshPromise: Promise<unknown> | null = null;

const isAuthEndpoint = (url = "") =>
  url.includes("/api/auth/login") || url.includes("/api/auth/refresh");

const refreshSession = () => {
  refreshPromise ??= axios
    .get("/api/auth/refresh", { withCredentials: true })
    .finally(() => { refreshPromise = null; });
  return refreshPromise;
};

api.interceptors.response.use(
  (response) => {
    const envelope = response.data as SuccessEnvelope<unknown>;
    if (envelope?.success === true) return envelope.data;
    return response.data;
  },
  async (error: AxiosError<ApiErrorBody>) => {
    const statusCode = error.response?.status ?? 0;
    const originalRequest = error.config as RetrievableRequest | undefined;
    // ...
    if (statusCode === 401 && originalRequest && !originalRequest._retry
        && !isAuthEndpoint(originalRequest.url)) {
      originalRequest._retry = true;
      try {
        await refreshSession();
        return api(originalRequest);
      } catch {
        useAuthStore.getState().clearAuth();
        window.location.assign("/login");
      }
    }
    // ... 429 toast ...
    return Promise.reject(new ApiClientError(message, statusCode, error.response?.data, retryAfterText));
  },
);
```

The core design — a single shared refresh promise, `_retry` to prevent infinite
loops, `withCredentials` for cookie auth — is right. Four refinements.

## 1. The single-flight guard is correct but the `.finally` timing is subtle

`refreshPromise ??= ...` correctly ensures that ten concurrent 401s trigger **one**
refresh call, and all ten `await` the same promise. Good.

The `.finally(() => { refreshPromise = null })` clears the slot. But `.finally`
runs **before** the awaiting callers' continuations resume. So this sequence is
possible:

1. Requests A and B both 401. A calls `refreshSession()`, creating the promise.
   B gets the same promise.
2. Refresh resolves. `.finally` sets `refreshPromise = null`.
3. A's continuation runs, retries, gets a 401 again (the new token was rejected —
   say the session was revoked server-side between the refresh and the retry).
   A's `_retry` is already true, so it falls through to reject. Fine.
4. But a *new* request C now 401s and calls `refreshSession()`, which starts a
   **second** refresh. Since refresh tokens rotate
   ([refreshToken.ts](../../server/src/controllers/auth/refreshToken.ts)), and
   [Vulnerability 05](../vulnerabilities/05.refresh-token-rotation-without-reuse-detection.md)
   proposes treating a rotated-away token as reuse, this second refresh could be
   read as a **replay** and revoke the entire session family.

That is the sharpest version of the risk, and it only exists once reuse detection
lands. The fix is to hold failures for a short window rather than clearing
instantly.

## 2. The `catch` falls through instead of stopping

```ts
} catch {
  useAuthStore.getState().clearAuth();
  window.location.assign("/login");
}
// execution CONTINUES to the 429 check and the final Promise.reject
```

`window.location.assign` does not halt JavaScript execution — it schedules a
navigation. So after a failed refresh the code still constructs and rejects an
`ApiClientError`, which propagates to React Query, which may render an error state
for the split second before navigation. Harmless in practice, but it means the
`catch` block reads as terminal when it is not.

There is also a redirect loop risk: if the user is already on `/login` and some
background query 401s, `window.location.assign("/login")` reloads the page,
which may refire the query, which 401s again.

## 3. `isAuthEndpoint` misses `/logout`

```ts
const isAuthEndpoint = (url = "") =>
  url.includes("/api/auth/login") || url.includes("/api/auth/refresh");
```

`POST /api/auth/logout` is not listed. Today the server's logout handler returns
200 unconditionally, so this never triggers. But if logout is ever moved behind
`checkCookieSignature` — which is a natural-looking "fix" someone might apply
to [Vulnerability 14](../vulnerabilities/14.auth-router-is-not-actually-protected.md)
without reading why it should not be — a 401 on logout would trigger a refresh,
then a retried logout, then a redirect. Attempting to refresh a session you are
deliberately ending is never right.

## 4. `envelope?.success === true` returns `envelope.data`, which may be `undefined`

```ts
if (envelope?.success === true) return envelope.data;
```

`AppResponse.toJSON` omits `data` entirely when it is `undefined` — which is what
`authApi.logout` returns (`new AppResponse(200, "User logged out successfully")`
with no data). So `authApi.logout()` resolves to `undefined`, typed as `void`.
That happens to be correct here, but it means any endpoint that forgets to send
`data` silently resolves to `undefined` rather than erroring, and the consuming
component gets a `Cannot read properties of undefined` at render time instead of
a clear API error.

## The suggestion

```ts
// client/src/api/client.ts
import { queryClient } from './queryClient'

type RetrievableRequest = InternalAxiosRequestConfig & { _retry?: boolean }

const AUTH_ENDPOINTS = ['/api/auth/login', '/api/auth/refresh', '/api/auth/logout'] as const
const isAuthEndpoint = (url = '') => AUTH_ENDPOINTS.some((endpoint) => url.includes(endpoint))

let refreshPromise: Promise<unknown> | null = null
let refreshFailedUntil = 0

const refreshSession = () => {
  // After a failed refresh, do not retry for a short window. Without this, a
  // burst of concurrent 401s each start their own refresh, and with server-side
  // reuse detection a second refresh using a rotated token looks like a replay
  // and revokes the whole session family.
  if (Date.now() < refreshFailedUntil) {
    return Promise.reject(new Error('Refresh recently failed'))
  }

  refreshPromise ??= axios
    .get('/api/auth/refresh', { withCredentials: true })
    .catch((error) => {
      refreshFailedUntil = Date.now() + 5_000
      throw error
    })
    .finally(() => {
      refreshPromise = null
    })

  return refreshPromise
}

const forceSignOut = () => {
  useAuthStore.getState().clearAuth()
  queryClient.clear()

  // Do not bounce a user who is already on the login screen.
  if (window.location.pathname !== '/login') {
    window.location.assign('/login')
  }
}

api.interceptors.response.use(
  (response) => {
    const envelope = response.data as SuccessEnvelope<unknown>
    if (envelope?.success === true) return envelope.data
    return response.data
  },
  async (error: AxiosError<ApiErrorBody>) => {
    const statusCode = error.response?.status ?? 0
    const originalRequest = error.config as RetrievableRequest | undefined
    const retryAfter = error.response?.headers?.['retry-after']
    const retryAfterText = Array.isArray(retryAfter) ? retryAfter[0] : retryAfter

    const message = error.response?.data?.message ?? error.message ?? 'Request failed'
    const toApiError = () =>
      new ApiClientError(message, statusCode, error.response?.data, retryAfterText)

    if (
      statusCode === 401 &&
      originalRequest &&
      !originalRequest._retry &&
      !isAuthEndpoint(originalRequest.url)
    ) {
      originalRequest._retry = true
      try {
        await refreshSession()
        return await api(originalRequest)
      } catch {
        forceSignOut()
        return Promise.reject(toApiError())   // explicit terminal return
      }
    }

    // A 401 on refresh itself means the session is unrecoverable.
    if (statusCode === 401 && originalRequest?.url?.includes('/api/auth/refresh')) {
      forceSignOut()
      return Promise.reject(toApiError())
    }

    if (statusCode === 429) {
      const suffix = retryAfterText ? ` Try again in ${retryAfterText}s.` : ''
      toast.warning(`${error.response?.data?.message ?? 'Too many requests.'}${suffix}`)
    }

    return Promise.reject(toApiError())
  },
)
```

Changes, each mapped to a numbered issue above:

1. `refreshFailedUntil` — a 5-second cooldown after a failed refresh, so a burst
   of 401s produces one refresh attempt, not N.
2. Explicit `return Promise.reject(...)` after `forceSignOut()`, and a
   `pathname !== '/login'` guard against redirect loops.
3. `/api/auth/logout` added to `AUTH_ENDPOINTS`, defined as a named array so the
   list is visible.
4. `return await api(originalRequest)` rather than `return api(...)` — so a
   rejection from the retry is caught by *this* `catch` rather than escaping.

### On issue 4 (the `undefined` envelope)

The strict fix is to reject when `data` is missing but the caller expects it.
That requires the interceptor to know each endpoint's expectations, which it
cannot. The pragmatic answer: type `authApi.logout` as `request<void>` (already
done) and leave the rest — the OpenAPI-generated types in
[Suggestion 16](./16.openapi-as-contract-source-of-truth.md) are the real
solution, since they make a missing `data` a compile error at the call site.

## A note on what NOT to change

The interceptor returns `envelope.data` rather than the full `AxiosResponse`. That
is unusual and it makes `request<T>()` resolve directly to the payload:

```ts
const users = await usersApi.list({ page: 1, pageSize: 20 })
//    ^ { users: UserListItem[], pagination: PaginationMeta } -- no .data.data
```

Keep it. It removes a layer of unwrapping from every call site and the typing
(`api.request<unknown, T>(config)`) is set up correctly for it. This is a good
decision, not an accident.

  `queryClient` this file imports. **Do 11 first**, and watch for circular

- **[Vulnerability 14](../vulnerabilities/14.auth-router-is-not-actually-protected.md)**
  explains why `/api/auth/logout` must stay unauthenticated. The

  discusses distinguishing `TOKEN_EXPIRED` from `TOKEN_INVALID`. **This file is

  `if (statusCode === 401)` branch becomes
  `if (code === 'TOKEN_EXPIRED')` → refresh, `else` → `forceSignOut()` directly,
  saving a wasted round trip. Decide it here; do not add the server-side codes
  unless this file uses them.

  dependency, larger scope.

## What you already got right

- **The single-flight refresh (`refreshPromise ??=`)** is the correct solution to
  the concurrent-401 stampede, and it is the thing most implementations get
  wrong — either firing N refreshes or building an elaborate subscriber queue.
  Three lines, correct.
- **`_retry` on the request config** prevents the infinite refresh→401→refresh
  loop. Essential and easy to forget.
- **`isAuthEndpoint` excludes login and refresh** so a bad password does not
  trigger a refresh attempt, and a failed refresh does not recurse. The concept is
  right; the list is just one entry short.
- **`ApiClientError` is a proper `Error` subclass** carrying `statusCode`,
  `details` and `retryAfter`. Every consumer gets a typed error with the
  server's structured Zod `details` intact — which is what makes
  field-level form errors possible.
- **`withCredentials: true` with relative URLs.** No token ever touches
  JavaScript; the browser handles the `httpOnly` cookies. Combined with the Vite
  proxy this is same-origin in development and needs no code change for
  production.
- **The 429 handler reads the `Retry-After` header** the server sets in
  `throwRateLimitError` and surfaces it in the toast. The client and server rate-
  limit contract is actually wired end to end, which is rare.

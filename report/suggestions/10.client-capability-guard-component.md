# 10. Replace scattered `can(...)` ternaries with a declarative capability guard

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **6 / 10**                                                            |
| **Side**     | **Client**                                                            |
| **Effort**   | Small — one component, one route helper, ~10 page edits               |
| **Files**    | all of [client/src/pages/](../../client/src/pages/), [AppShell.tsx](../../client/src/components/layout/AppShell.tsx), [useAuth.ts](../../client/src/hooks/useAuth.ts), [constants.ts](../../client/src/constants.ts) |

## The pattern today

Capability gating happens in three different shapes across the app.

**Inline ternaries in pages:**

```tsx
// client/src/pages/UsersPage.tsx
{can('users.create') ? (
  <CreateUserForm form={createUserForm} onSubmit={...} isPending={...} />
) : null}

{can('users.assignRole') || can('users.revokeRole') ? (
  <AssignRevokeRoleForm canAssign={can('users.assignRole')} canRevoke={can('users.revokeRole')} ... />
) : null}
```

**Early returns in pages:**

```tsx
// client/src/pages/SessionsPage.tsx
export function AllSessionsPage() {
  const { can } = useCapabilities()
  if (!can('sessions.view')) return <AccessDenied />
  return <div className="page-stack">...</div>
}
```

**Props drilled into components:**

```tsx
// UsersPage -> UsersTable
canUpdate={can('users.update')}
canDelete={can('users.delete')}
```

**And route registration that ignores capabilities entirely:**

```tsx
// client/src/components/layout/AppShell.tsx
<Routes>
  <Route path="/users" element={<UsersPage />} />
  <Route path="/logs" element={<AuditLogsPage />} />
  <Route path="/migrations" element={<MigrationsPage />} />
  ...
</Routes>
```

Meanwhile `navItems` in `constants.ts` declares capabilities for *some* items:

```ts
{ to: "/logs", label: "Logs", icon: ScrollText, capability: "auditLogs.view" },
{ to: "/migrations", label: "Migrations", icon: Database, capability: "migrations.view" },
{ to: "/users", label: "Users", icon: Users },        // <-- no capability declared
{ to: "/roles", label: "Roles", icon: ShieldCheck },  // <-- no capability declared
```

So the required capability for a page lives in up to three places — the nav item,
the page's early return, and the individual ternaries — and for `/users`,
`/roles`, `/permissions`, `/role-permissions` and `/posts` it lives in **none** of
the first two. Those five pages appear in the sidebar for every user, and if the
user lacks the permission the page renders, fires a query, and displays a
`QueryErrorState` with a 403.

## Why it is worth centralising

To be clear about what this does and does not achieve: **this is UX, not
security.** The server authorizes every request independently and returns 403
regardless of what the client renders. Nothing here protects data.

What it does buy:

1. **Consistency.** A user without `auditLogs.view` gets a clean "you do not have
   access" page. A user without `users.view` gets a red error panel saying
   *"You do not have permission to view on user"*. Same situation, two very
   different experiences, because one route declared its capability and the other
   did not.

2. **One place to look.** *"Which capability does the Roles page need?"* should be
   answerable from one file. Right now it requires opening `RolesPage.tsx` and
   reading every `can()` call.

3. **New pages get it by default.** The five pages missing guards were not an
   oversight in each case — there was simply no mechanism that made adding one
   the obvious thing to do.

4. **Wasted requests disappear.** `AuditLogsPage` currently mounts, `useQuery`
   fires, the server 403s, React Query retries once (`retry: 1` in
   `main.tsx`), and *then* the error renders. Two requests guaranteed to fail.

## The design

### A `<Can>` component for fragments

```tsx
// client/src/components/shared/Can.tsx
import type { ReactNode } from 'react'
import type { CapabilityKey } from '@/api/types'
import { useCapabilities } from '@/hooks/useAuth'

type CanProps = {
  /** Render children when the user has this capability. */
  capability?: CapabilityKey
  /** Render children when the user has ANY of these. */
  anyOf?: readonly CapabilityKey[]
  /** Render children when the user has ALL of these. */
  allOf?: readonly CapabilityKey[]
  /** Rendered instead of children when the check fails. Defaults to nothing. */
  fallback?: ReactNode
  children: ReactNode
}

/**
 * Presentation-only capability gate. The server authorizes every request
 * independently -- this exists so the UI does not offer actions that will fail,
 * NOT as an access control. Never rely on it to protect data.
 */
export function Can({ capability, anyOf, allOf, fallback = null, children }: CanProps) {
  const { can } = useCapabilities()

  const allowed =
    (capability === undefined || can(capability)) &&
    (anyOf === undefined || anyOf.some(can)) &&
    (allOf === undefined || allOf.every(can))

  return <>{allowed ? children : fallback}</>
}
```

The doc comment is load-bearing. Someone will eventually mistake this for
security; say so in the file.

### A capability-aware route

```tsx
// client/src/components/shared/CapabilityRoute.tsx
export function CapabilityRoute({
  capability, anyOf, children,
}: { capability?: CapabilityKey; anyOf?: readonly CapabilityKey[]; children: ReactNode }) {
  return (
    <Can capability={capability} anyOf={anyOf} fallback={<AccessDenied />}>
      {children}
    </Can>
  )
}
```

### One declaration per route

Extend `navItems` so every route names its capability, and derive both the
sidebar and the router from it:

```ts
// client/src/constants.ts
export const navItems: NavItem[] = [
  { to: "/dashboard", label: "Dashboard", icon: Gauge },                             // always visible
  { to: "/users", label: "Users", icon: Users, capability: "users.view" },           // was missing
  { to: "/roles", label: "Roles", icon: ShieldCheck, capability: "roles.view" },     // was missing
  { to: "/permissions", label: "Permissions", icon: KeyRound, capability: "permissions.view" },
  { to: "/role-permissions", label: "Role permissions", icon: Layers3,
    capability: "rolePermissions.view" },
  { to: "/posts", label: "Posts", icon: FileText, capability: "posts.view" },
  { to: "/logs", label: "Logs", icon: ScrollText, capability: "auditLogs.view" },
  { to: "/migrations", label: "Migrations", icon: Database, capability: "migrations.view" },
  { to: "/sessions", label: "Sessions", icon: MonitorSmartphone, children: [ /* unchanged */ ] },
];
```

```tsx
// client/src/components/layout/AppShell.tsx
<Route path="/users" element={
  <CapabilityRoute capability="users.view"><UsersPage /></CapabilityRoute>
} />
<Route path="/logs" element={
  <CapabilityRoute capability="auditLogs.view"><AuditLogsPage /></CapabilityRoute>
} />
```

Better still, drive it from a single map so the nav and the router provably agree:

```tsx
const ROUTES = [
  { path: "/dashboard",        element: <DashboardPage /> },
  { path: "/users",            element: <UsersPage />,           capability: "users.view" },
  { path: "/roles",            element: <RolesPage />,           capability: "roles.view" },
  // ...
] as const satisfies readonly { path: string; element: ReactNode; capability?: CapabilityKey }[]

<Routes>
  <Route index element={<Navigate to="/dashboard" replace />} />
  {ROUTES.map(({ path, element, capability }) => (
    <Route key={path} path={path} element={
      capability ? <CapabilityRoute capability={capability}>{element}</CapabilityRoute> : element
    } />
  ))}
  <Route path="*" element={<Navigate to="/dashboard" replace />} />
</Routes>
```

### Pages after

```tsx
// client/src/pages/UsersPage.tsx -- the route already guarded users.view
<Can capability="users.create">
  <CreateUserForm form={createUserForm} onSubmit={...} isPending={...} />
</Can>

<Can anyOf={['users.assignRole', 'users.revokeRole']}>
  <AssignRevokeRoleForm
    canAssign={can('users.assignRole')}
    canRevoke={can('users.revokeRole')}
    ...
  />
</Can>
```

Note the props on `AssignRevokeRoleForm` stay. That is correct — the component
needs to know *which* of the two buttons to enable, which is finer-grained than
"render or not". `<Can>` handles the render decision; props handle the internal
state. Do not try to push `<Can>` into every button.

### The `sessions.view` naming problem

[Vulnerability 02](../vulnerabilities/02.overpermissive-default-user-role.md)
splits `view:session` into "see my own" and "see everyone's". When that lands,
`CapabilityKey` gains something like `sessions.viewAll`, and
`AllSessionsPage`/`UserSessionsPage` must guard on the new key while a
self-service "my sessions" view uses the old one. **Do not build the route map
before deciding that split**, or you will encode the wrong capability names.

## Interaction with other findings

- **[Vulnerability 02](../vulnerabilities/02.overpermissive-default-user-role.md)**
  changes the capability vocabulary. **Sequence 02 first**, then build this
  against the final `CapabilityKey` enum.
- **[Vulnerability 16](../vulnerabilities/16.client-auth-flag-is-persisted-and-forgeable.md)**
  — `<Can>` must derive from `authMe.data.capabilities` (server-supplied on every
  load), never from anything persisted in `localStorage`. The doc comment above
  states this; keep it.
- **[Suggestion 01](./01.centralize-authorization-in-middleware.md)** is the
  server mirror of this suggestion. Doing both means the required permission for
  an operation is declared once on the route on each side — a nice symmetry, and
  it makes the two easy to cross-check.
- **[Suggestion 11](./11.react-query-cache-hardening.md)** — guarding routes
  prevents queries from firing for users who cannot use them, which reduces the
  cached-403 states that suggestion has to clean up. Complementary.
- **No contradiction** with anything.

## What you already got right

- **Capabilities come from the server on every page load.** `useAuthMe()` fetches
  `GET /api/auth/me`, which returns `roles` and `capabilities` computed live from
  the database. The client never derives an authorization answer itself — it only
  renders one it was given. That is the correct architecture and it is applied
  consistently.
- **`toCapabilityKeys`** on the server maps raw `action:resource` pairs to a
  stable, UI-oriented vocabulary (`users.assignRole` rather than `assign:role`).
  That is a real API design decision — the client is insulated from the internal
  permission representation, so `Suggestion 03`'s hierarchy refactor will not
  break a single component.
- **`useCapabilities` memoises a `Set`** rather than calling `.includes()` on an
  array per check. With ~26 capabilities and dozens of `can()` calls per render,
  that is the right structure.
- **`navVisibility.ts` is already declarative and recursive**, correctly
  collapsing a parent nav group when all its children are hidden, and repointing
  the parent's `to` at the first visible child. That is a genuinely nice piece of
  logic — and it has its own unit test.
- **`AccessDenied` already exists** as a shared component, so the fallback in
  `CapabilityRoute` is not new work. The pieces are all here; they just need one
  place to be assembled.
- **`SessionsPage` cascades through capabilities** to pick a landing sub-page
  (`sessions.view` → `sessions.revoke` → `sessions.delete` → `AccessDenied`).
  Thoughtful UX that this refactor should preserve, not flatten.

## What is configured today

The entire PostgreSQL configuration:

```ts
// server/src/config/db.connect.ts
const pool = new Pool({
  host: env.DB_HOST_NAME,
  port: env.DB_PORT,
  user: env.DB_USER,
  password: env.DB_PASSWORD,
  database: env.DB_NAME,
});
```

Everything else is `node-postgres` defaults. The ones that matter:

| Setting | Default | Consequence |
| --- | --- | --- |
| `max` | 10 | Fine, but undeclared — and it interacts badly with [Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md) |
| `connectionTimeoutMillis` | **0 = wait forever** | An exhausted pool hangs permanently rather than erroring. This is the single worst default. |
| `idleTimeoutMillis` | 10000 | Reasonable |
| `statement_timeout` | none | A runaway query holds a connection indefinitely |
| `idle_in_transaction_session_timeout` | none | A transaction that never commits holds locks forever |
| `ssl` | off | Cannot connect to any managed PostgreSQL (RDS, Neon, Supabase) |
| `application_name` | none | `pg_stat_activity` shows `node` for every connection |

There is also **no `pool.on("error")` handler**. `node-postgres` emits `error` on
idle clients when the backend drops a connection (a failover, a
`pg_terminate_backend`, an idle timeout on the server side). An unhandled `error`
event on an `EventEmitter` **crashes the Node process** — and `index.ts` has a
`process.on("uncaughtException")` that calls `process.exit(1)`. So a routine
database failover takes the API down hard.

Redis is in better shape but has its own gap:

```ts
// server/src/config/redis.connect.ts
const redisOptions: RedisOptions = {
  host: env.REDIS_HOST,
  port: env.REDIS_PORT,
  retryStrategy(times) {
    return Math.min(times * 50, 2000);      // never returns null -> retries forever
  },
};

const redisClient = env.REDIS_URL
  ? new Redis(env.REDIS_URL, { retryStrategy: redisOptions.retryStrategy })
  : new Redis(redisOptions);
```

- **No `commandTimeout`.** `allowSlidingWindow` awaits `redisClient.eval(...)`. If
  Redis accepts the connection but stops responding — a slow `BGSAVE`, memory
  pressure, a network black hole — that `await` never settles, so **every request
  hangs** rather than degrading. The fail-open logic in
  [Vulnerability 07](../vulnerabilities/07.rate-limiters-fail-open.md) only
  triggers on `status !== "ready"` or a thrown error; a hang is neither.
- **`maxRetriesPerRequest` defaults to 20**, so commands queue during an outage
  and then all fire at once on reconnect.
- **`enableOfflineQueue` defaults to true**, so commands issued while
  disconnected buffer in memory unboundedly.
- **No `lazyConnect`**, so importing the module opens a socket — which is why the
  test suites need `tests/support/redis.ts` to clean up.

## Why this matters

The two most likely production incidents both come from this file:

**Incident 1 — permanent hang.** Ten concurrent requests trigger the pool
starvation in [Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md).
With `connectionTimeoutMillis: 0`, every subsequent request queues forever. The
process stays alive, the port stays open, a naive health check passes, and the
service is completely dead. Recovery requires a restart. **One setting** —
`connectionTimeoutMillis: 5000` — turns this from an outage into a burst of 500s
that self-heals.

**Incident 2 — crash on failover.** The managed database fails over. Idle
connections in the pool receive a connection-reset error. `node-postgres` emits
`error`. No listener. Node crashes. `uncaughtException` exits with code 1. The
orchestrator restarts, and if the failover is still in progress, crashes again.

Both are one-line fixes that nobody makes until they have been paged for them.

## The configuration

### PostgreSQL

```ts
// server/src/config/db.connect.ts
import pg from "pg";
import env from "../utils/envHelper.ts";

const { Pool } = pg;

const pool = new Pool({
  host: env.DB_HOST_NAME,
  port: env.DB_PORT,
  user: env.DB_USER,
  password: env.DB_PASSWORD,
  database: env.DB_NAME,

  // Sizing. Rule of thumb: (instances x max) must stay below PostgreSQL's
  // max_connections (default 100), leaving headroom for migrations and psql.
  max: env.DB_POOL_MAX,
  min: 0,

  // Never wait forever for a connection. Without this, pool exhaustion is a
  // permanent hang instead of a recoverable error. See vulnerabilities/08.
  connectionTimeoutMillis: 5_000,
  idleTimeoutMillis: 30_000,

  // Server-side guards, applied per connection.
  statement_timeout: 10_000,                    // no single query runs > 10s
  idle_in_transaction_session_timeout: 15_000,  // PostgreSQL reaps stuck transactions
  query_timeout: 10_000,                        // client-side twin of statement_timeout

  // Shows up in pg_stat_activity -- invaluable when diagnosing lock contention.
  application_name: `rolecontrol-iam-${env.NODE_ENV}`,

  // Managed PostgreSQL requires TLS.
  ...(env.DB_SSL === "true"
    ? { ssl: { rejectUnauthorized: env.DB_SSL_REJECT_UNAUTHORIZED !== "false" } }
    : {}),
});

// REQUIRED: without this listener, an error on an idle client is an unhandled
// 'error' event, which terminates the process. A database failover should
// degrade, not crash.
pool.on("error", (error) => {
  console.error("Unexpected error on an idle PostgreSQL client", error);
});

const testDbConnection = async () => {
  try {
    const client = await pool.connect();
    await client.query("SELECT 1");
    client.release();
    console.log("✅ Database connected successfully");
    return true;
  } catch (error) {
    console.error("❌ Database connection failed:", error);
    return false;
  }
};

const closeDbPool = async () => {
  await pool.end();
};

export { pool, testDbConnection, closeDbPool };
```

Two notes:

- `idle_in_transaction_session_timeout` is the safety net for
  [Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md).
  Even if the application misbehaves, PostgreSQL cleans up after it. Set it
  **higher** than `statement_timeout` so a slow-but-legitimate query is not killed
  mid-transaction.
- `closeDbPool` is what `index.ts`'s `gracefulShutdown` is missing — it has a
  `// TODO: Add database connection closure here` comment on exactly this point.
  See [Suggestion 07](./07.health-readiness-and-graceful-shutdown.md).

### Redis

```ts
// server/src/config/redis.connect.ts
import { Redis, type RedisOptions } from "ioredis";
import env from "@/utils/envHelper.ts";

const redisOptions: RedisOptions = {
  host: env.REDIS_HOST,
  port: env.REDIS_PORT,

  // A hung Redis must not hang the request. Without this, an unresponsive-but-
  // connected Redis makes every rate-limited endpoint block indefinitely -- the
  // fail-open path in vulnerabilities/07 only catches errors, not hangs.
  commandTimeout: 1_000,
  connectTimeout: 5_000,

  // Fail fast instead of queueing 20 retries per command during an outage.
  maxRetriesPerRequest: 1,

  // Do not buffer commands while disconnected. Rate limiting is best-effort;
  // a replayed burst of stale checks after reconnect is worse than skipping them.
  enableOfflineQueue: false,

  // Cap reconnection backoff. Returning a number retries; returning null stops.
  retryStrategy: (times) => Math.min(times * 100, 3_000),

  // Reconnect on the READONLY error a replica returns after a failover.
  reconnectOnError: (error) => error.message.includes("READONLY"),
};

const redisClient = env.REDIS_URL
  ? new Redis(env.REDIS_URL, redisOptions)     // pass the FULL options, not just retryStrategy
  : new Redis(redisOptions);
```

The `env.REDIS_URL` branch currently forwards **only** `retryStrategy`, silently
dropping every other option. Anyone using `REDIS_URL` (which
[server/.env](../../server/.env) does) gets defaults for everything else. Easy to
miss, and it means the settings above would have no effect in your own
development setup.

`enableOfflineQueue: false` is a deliberate choice: with it off, commands issued
while disconnected reject immediately, which `allowSlidingWindow`'s `try/catch`
already handles by returning `null` → the documented degraded path. That is
better than silently queueing.

## Verifying it works

```bash
# 1. connectionTimeoutMillis -- exhaust the pool and confirm you get errors, not a hang.
#    With DB_POOL_MAX=2, fire 10 concurrent requests to a transactional endpoint.
#    Expect: some 500s within ~5s. NOT: requests that never return.

# 2. pool.on('error') -- kill a backend and confirm the process survives.
psql -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity
          WHERE application_name LIKE 'rolecontrol-iam-%';"
# Expect: "Unexpected error on an idle PostgreSQL client" logged, process alive.

# 3. commandTimeout -- simulate a hung Redis.
redis-cli DEBUG SLEEP 5
curl -s -o /dev/null -w '%{time_total}\n' localhost:8000/api/auth/login -X POST \
  -H 'Content-Type: application/json' -d '{"email":"a@b.co","password":"xxxx"}'
# Expect: ~1s (commandTimeout), then the degraded path. NOT: 5s.

# 4. statement_timeout
psql -c "SELECT pg_sleep(15);"   # via the app, expect error 57014 after 10s
```

## Interaction with other findings

- **[Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md)**
  quotes `connectionTimeoutMillis` and `idle_in_transaction_session_timeout` as
  part of its fix. **This suggestion owns the pool configuration.** Do not write
  two versions of it — implement it here and let that finding reference it.
- **[Vulnerability 07](../vulnerabilities/07.rate-limiters-fail-open.md)** — if
  you make the auth limiters fail *closed*, Redis becomes a hard dependency for
  login. `commandTimeout` and `connectTimeout` then determine how quickly a Redis
  problem becomes a login outage. **These two must land together**, or you trade a
  security bug for an availability incident.
- **[Suggestion 07](./07.health-readiness-and-graceful-shutdown.md)** — `pool.end()`
  and `redisClient.quit()` belong in graceful shutdown, and pool/Redis health
  belongs on the readiness endpoint. `closeDbPool` above is the hook.
- **[Suggestion 14](./14.docker-compose-and-reproducible-dev-env.md)** — a compose
  file makes `DB_SSL=false` correct locally and forces the question of what it
  should be in production.
- **[Suggestion 13](./13.environment-config-and-secret-management.md)** — the three
  new environment variables belong in the same config pass and in `.env.example`.

## What you already got right

- **Redis lifecycle listeners are already attached** — `connect`, `ready`,
  `error`, `reconnecting` — with a comment explaining exactly why
  (*"Otherwise, connection issues will fail silently or crash the app
  unexpectedly"*). You understood this hazard for Redis. The suggestion is
  largely "apply the same reasoning to PostgreSQL."
- **`retryStrategy` with capped exponential backoff** rather than a tight
  reconnect loop. Correct shape, just needs the timeout companions.
- **`isRedisRateLimitReady()` checks `redisClient.status === "ready"`** before
  issuing commands, rather than assuming connectivity. That is the right
  defensive pattern and it is why a Redis outage degrades instead of throwing.
- **`REDIS_URL` overriding host/port** is the right precedence for managed Redis,
  and `DATABASE_URL` is separated for the migration tooling that needs a
  connection string. The config surface is well-shaped; it is just under-populated.
- **`testDbConnection()` runs at startup** and logs a clear success/failure. The
  hook for a real readiness check already exists.

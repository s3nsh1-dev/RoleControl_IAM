# 03. Move the role hierarchy into the database and unlock custom roles

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **8 / 10**                                                            |
| **Side**     | **Both** (server owns the model; the client's `RoleName` union changes) |
| **Effort**   | Medium-large — one migration, ~6 server files, regenerated client types |
| **Files**    | [hierarchy.ts](../../server/src/config/hierarchy.ts), [others/constants.ts](../../server/src/others/constants.ts), [helper.ts:17-38](../../server/src/utils/helper.ts#L17-L38), [api.contracts.ts](../../server/src/contracts/api.contracts.ts), [client/src/api/types.ts](../../client/src/api/types.ts) |

---

## The tension

You built a real RBAC engine — `users → user_roles → roles → role_permissions →
permissions`, fully normalised, queried at runtime. Then you constrained it so
tightly that it behaves like a hardcoded four-role system:

```ts
// server/src/others/constants.ts
const ROLES_LIST = ["super-admin", "admin", "user", "editor"] as const;
```

```ts
// server/src/contracts/api.contracts.ts
const RoleNameSchema = z.enum(ROLES_LIST);
const CreateRoleRequestSchema = z.object({
  name: RoleNameSchema,               // <-- you can only "create" one of the four
  description: z.string().trim().min(1).optional(),
});
```

`POST /api/roles` exists, is permission-gated, is audited, runs in a transaction —
and can only ever create a role that the seed script already created. The
endpoint is effectively unreachable in a seeded database, because `roles.name` is
`UNIQUE` and all four names are taken.

Meanwhile the hierarchy lives in a TypeScript literal:

```ts
// server/src/config/hierarchy.ts
const ROLE_RANKS: Record<ROLES_TYPES, number> = {
  user: 1, editor: 2, admin: 3, "super-admin": 4,
};
```

and `canActorManageRole` is a chain of string comparisons:

```ts
// server/src/utils/helper.ts:23
function canActorManageRole(actorHighestRole: ROLES_TYPES, targetRoleName: string): boolean {
  if (!isKnownRoleName(targetRoleName)) return actorHighestRole === "super-admin";
  if (actorHighestRole === "super-admin") return true;
  if (actorHighestRole === "admin") return targetRoleName === "editor" || targetRoleName === "user";
  return false;
}
```

Adding a fifth role today means: edit `ROLES_LIST`, edit `ROLE_RANKS`, add a
branch to `canActorManageRole`, add a permission array to `hierarchy.ts`, add a
`PERMISSION_HIERARCHY.set(...)` line, re-run the seed, regenerate the OpenAPI
document, regenerate `client/src/api/schema.ts`, and update
`client/src/api/types.ts`'s `roleNames` literal. Eight files and a deploy, for
something the data model was designed to handle with one `INSERT`.

## Why this matters beyond ergonomics

This is the root cause of
[Vulnerability 06](../vulnerabilities/06.role-rename-privilege-escalation.md).
Because authority is keyed on `roles.name` (a mutable string) rather than
`roles.id` or a rank column:

- Renaming a role redistributes authority to its existing holders, silently.
- `getUserRoleNames` **filters out** any role not in `ROLE_RANKS`, so a role the
  application does not recognise makes its holders read as roleless. A cosmetic
  rename becomes an outage.

Fixing the hierarchy properly fixes that vulnerability as a side effect, which is
why this ranks 8 rather than 5.

## The design

### 1. Schema

```sql
-- migrations/<timestamp>_role-hierarchy-and-system-flags.sql
-- Up Migration

ALTER TABLE roles ADD COLUMN rank INT NOT NULL DEFAULT 0;
ALTER TABLE roles ADD COLUMN is_system BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE permissions ADD COLUMN is_system BOOLEAN NOT NULL DEFAULT FALSE;

UPDATE roles SET rank = 1 WHERE name = 'user';
UPDATE roles SET rank = 2 WHERE name = 'editor';
UPDATE roles SET rank = 3 WHERE name = 'admin';
UPDATE roles SET rank = 4 WHERE name = 'super-admin';

ALTER TABLE roles ADD CONSTRAINT roles_rank_positive CHECK (rank > 0);

-- 'user' is the implicit base role; 'super-admin' is the recovery anchor.
-- Neither may be deleted or renamed. See report/vulnerabilities/12.
UPDATE roles SET is_system = TRUE WHERE name IN ('user', 'super-admin');

UPDATE permissions SET is_system = TRUE
 WHERE (action, resource) IN (
   ('create','permission'), ('delete','permission'),
   ('assign','permission'), ('revoke','permission'),
   ('create','role'), ('assign','role'), ('revoke','role')
 );

-- Loosen the name constraint: roles are user-definable, so the enum no longer
-- describes the domain. Keep a format constraint instead.
ALTER TABLE roles ADD CONSTRAINT roles_name_format
  CHECK (name ~ '^[a-z][a-z0-9-]{2,49}$');

CREATE INDEX idx_roles_rank ON roles(rank DESC);

-- Down Migration
DROP INDEX IF EXISTS idx_roles_rank;
ALTER TABLE roles DROP CONSTRAINT IF EXISTS roles_name_format;
ALTER TABLE permissions DROP COLUMN IF EXISTS is_system;
ALTER TABLE roles DROP CONSTRAINT IF EXISTS roles_rank_positive;
ALTER TABLE roles DROP COLUMN IF EXISTS is_system;
ALTER TABLE roles DROP COLUMN IF EXISTS rank;
```

Note that `rank` is **not** unique. Two roles at the same rank cannot manage each
other, which is usually what you want for parallel departmental roles
(`finance-admin` and `hr-admin` at rank 3).

### 2. Helpers

```ts
// server/src/utils/helper.ts
type ActorRole = { id: number; name: string; rank: number };

async function getUserRoles(userId: number, db: QueryableDb): Promise<ActorRole[]> {
  const result = await db.query<ActorRole>(
    `SELECT r.id, r.name, r.rank
       FROM user_roles ur JOIN roles r ON r.id = ur.role_id
      WHERE ur.user_id = $1
      ORDER BY r.rank DESC, r.id ASC`,
    [userId],
  );
  return result.rows;      // NO filtering -- unknown role names no longer vanish
}

async function getHighestUserRole(userId: number, db: QueryableDb): Promise<ActorRole | null> {
  return (await getUserRoles(userId, db))[0] ?? null;
}

/** An actor may manage roles strictly below their own rank. */
function canActorManageRole(actor: ActorRole, target: Pick<ActorRole, "rank">): boolean {
  return actor.rank > target.rank;
}
```

`sortRoleBasedOnRanks` and `isKnownRoleName` are deleted — the database does the
ordering, and every role is known.

### 3. Contracts

`RoleNameSchema` stops being an enum:

```ts
// server/src/contracts/api.contracts.ts
const RoleNameSchema = z
  .string()
  .trim()
  .regex(/^[a-z][a-z0-9-]{2,49}$/, "Role name must be lowercase letters, digits and hyphens")
  .openapi("RoleName", { example: "editor" });

const CreateRoleRequestSchema = z.object({
  name: RoleNameSchema,
  rank: z.number().int().positive().max(999),
  description: z.string().trim().min(1).optional(),
}).openapi("CreateRoleRequest");
```

And `createRole` gains one essential guard:

```ts
// server/src/controllers/roles/createRole.ts
const actorRole = await getHighestUserRole(actorId, client);
if (!actorRole) throw AppError.forbidden("Actor does not have an assigned role");
// You cannot create a role at or above your own rank -- otherwise creating a
// role is a privilege escalation primitive.
if (rank >= actorRole.rank) {
  throw AppError.forbidden("You cannot create a role at or above your own rank");
}
```

**That guard is not optional.** Without it, any holder of `create:role` mints a
rank-999 role, assigns it to themselves, and owns the system. It is the single
most important line in this suggestion.

### 4. Capabilities on the client

`CapabilityKeySchema` stays an enum — capabilities are a fixed application
vocabulary derived from `action × resource`, and the client's `can()` checks
depend on them. Only `RoleName` becomes an open string. That keeps
[navVisibility.ts](../../client/src/components/layout/navVisibility.ts) and every
`can('users.create')` call working untouched.

The client changes are small:

```ts
// client/src/api/types.ts
export type RoleName = string          // was: Schemas['RoleName'] (a union)

// roleNames as a static literal must go -- fetch from GET /api/roles instead.
```

Forms that currently render `<select>` from the `roleNames` constant
(`CreateUserForm`, `AssignRevokeRoleForm`, `RolePermissionMutationForm`,
`CreateRoleForm`) must populate from `rolesApi.list()`. That is the bulk of the
client work — four components, and they already have `useQuery` available.

## Cost, honestly

This is the largest change in the report and I would not do it first. It touches
a migration, six server files, four client components, the OpenAPI document, and
the generated types. Budget a day.

**Do it if** you want this project to demonstrate a real RBAC system — the ability
to define roles at runtime is the difference between "I implemented RBAC" and
"I hardcoded four roles and joined some tables."

**Skip it if** the four roles are genuinely the product. In that case take
[Vulnerability 06](../vulnerabilities/06.role-rename-privilege-escalation.md)'s
**Option B** instead (make `roles.name` immutable by removing it from
`UpdateRoleRequestSchema`), which is a three-line fix that closes the security
hole without the refactor. Then also delete `POST /api/roles` and
`DELETE /api/roles/:roleName`, because an endpoint that cannot do anything is
worse than no endpoint.

**Do not do both.** Option B and this suggestion are mutually exclusive designs.

## What you already got right

- **The relational model is correct and complete.** Five tables, proper foreign
  keys, `UNIQUE` on both join tables preventing duplicate grants, cascades in the
  right directions. This suggestion adds two columns to a schema that otherwise
  needs no changes — which is the strongest possible endorsement of the original
  design.
- **Permissions are resolved at request time from the database**, never cached in
  the JWT. That means a revoked permission takes effect on the next request, not
  on the next login. Many RBAC implementations bake roles into the token and
  quietly accept a 20-minute staleness window. Yours does not, and that is the
  harder, more correct choice.
- **`PERMISSION_HIERARCHY` uses composition** (`...userPermissions` spread into
  `editorPermissions`) so the base set cannot drift between roles. Good structure,
  and it maps cleanly onto seeded rows.
- **`db.seed.ts` is fully idempotent** with `ON CONFLICT` on every insert, so
  re-seeding after a schema change is safe. That is what makes this migration
  low-risk to iterate on.
- **`canActorManageRole` already exists as a named concept.** The hierarchy is a
  first-class idea in this codebase rather than scattered conditionals — which is
  why replacing its implementation is a contained change.

# 13. Split configuration by environment and stop defaulting secrets

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **7 / 10**                                                            |
| **Side**     | **Both**                                                              |
| **Effort**   | Small — one file rewritten, one new file, a root `.gitignore`         |
| **Files**    | [envHelper.ts](../../server/src/utils/envHelper.ts), [server/.env](../../server/.env), repository root |

---

## What exists and what is missing

`envHelper.ts` is the strongest piece of infrastructure in this project. A single
Zod schema, 30 keys, every one with a `.describe()`, `z.coerce.number()` where
the environment gives strings, and one exported `env` object. Grep confirms
almost nothing reads `process.env` directly:

```
$ grep -rn "process\.env" server/src --include=*.ts
server/src/utils/envHelper.ts:  const env = envSchema.parse(process.env);
```

That is genuinely better discipline than most production codebases.

What is missing sits around it:

**1. Secrets have defaults.** Covered in detail in
[Vulnerability 09](../vulnerabilities/09.jwt-secret-and-credentials-default-to-placeholders.md):
`JWT_SECRET` falls back to `"placeholder"`, `DB_PASSWORD` to `"password"`. The
`.min(1)` on `JWT_SECRET` never fires because `.default()` supplies a value when
the variable is absent.

**2. Failure is unreadable.** `envSchema.parse(process.env)` throws at module
import. Because the import chain is
`index.ts → app.ts → …  → envHelper.ts`, the error surfaces as an unhandled
`ZodError` with a stack trace pointing at `parse`, not at the missing variable.

**3. There is no `.env.example`.** A new contributor — or you in six months —
discovers the required variables by reading `envHelper.ts`. And because
everything has a default, the app *starts* with none of them set, then fails
mysteriously at the first database query.

**4. There is no root `.gitignore`.** `server/.gitignore` and
`client/.gitignore` cover their own directories. A `.env` at the repository root
— exactly where a `docker-compose.yml` wants one — would be committed. (Verified:
`server/.env` is correctly ignored and has never been committed.)

**5. The client has no environment configuration at all.** No `.env`, no
`import.meta.env` usage. That works because the Vite proxy makes everything
relative. But a production build served from a CDN with the API on a different
host has no way to be told where the API is, without a code change.

## The suggestion

### 1. Environment-aware schema with no secret defaults

```ts
// server/src/utils/envHelper.ts
import dotenv from "dotenv";
import { z } from "zod";
import { JWT_EXPIRES_TIMELINE } from "../others/constants.ts";

// Load .env.<NODE_ENV>.local, then .env.local, then .env -- first wins.
// This lets a developer keep personal overrides out of the shared file.
const nodeEnv = process.env["NODE_ENV"] ?? "development";
for (const file of [`.env.${nodeEnv}.local`, ".env.local", `.env.${nodeEnv}`, ".env"]) {
  dotenv.config({ path: file, override: false });
}

const isProduction = nodeEnv === "production";

/** Required in production; falls back to an obviously-fake value elsewhere. */
const productionRequired = <T extends z.ZodTypeAny>(schema: T, developmentDefault: z.infer<T>) =>
  isProduction ? schema : schema.default(developmentDefault);

const envSchema = z.object({
  NODE_ENV: z.enum(["development", "production", "test"]).default("development"),
  PORT: z.coerce.number().int().positive().default(8000),
  HOST: z.string().default("0.0.0.0"),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  SHUTDOWN_GRACE_MS: z.coerce.number().int().positive().default(10_000),

  // --- Secrets: no production defaults -------------------------------------
  JWT_SECRET: productionRequired(
    z.string().min(32, "JWT_SECRET must be at least 32 characters. Generate with: openssl rand -hex 32"),
    "dev-only-jwt-secret-do-not-use-in-production-0000",
  ),
  DB_PASSWORD: productionRequired(z.string().min(1, "DB_PASSWORD is required"), "postgres"),
  BOOTSTRAP_TOKEN: z.string().min(32).optional()
    .describe("One-time secret enabling super-admin bootstrap. Unset = disabled."),

  // --- Database -------------------------------------------------------------
  DATABASE_URL: z.string().optional(),
  DB_HOST_NAME: z.string().default("localhost"),
  DB_PORT: z.coerce.number().int().positive().default(5432),
  DB_NAME: z.string().default("postgres"),
  DB_USER: z.string().default("postgres"),
  DB_POOL_MAX: z.coerce.number().int().positive().max(100).default(10),
  DB_SSL: z.enum(["true", "false"]).default(isProduction ? "true" : "false"),

  // --- Deployment topology --------------------------------------------------
  TRUST_PROXY: z.string().default("false"),                 // validated per vulnerabilities/22
  CORS_ALLOWED_ORIGINS: z.string().default(""),             // per vulnerabilities/10
  ENABLE_API_DOCS: z.enum(["true", "false"]).default(isProduction ? "false" : "true"),

  // ... auth timings, Redis, rate limits -- unchanged
});

const parsed = envSchema.safeParse(process.env);

if (!parsed.success) {
  console.error("\n❌ Invalid environment configuration:\n");
  for (const issue of parsed.error.issues) {
    console.error(`   ${issue.path.join(".")}: ${issue.message}`);
  }
  console.error("\n   See server/.env.example for the full list.\n");
  process.exit(1);
}

const env = parsed.data;
export default env;
```

Three properties worth calling out:

- **`safeParse` + `process.exit(1)`** turns a stack trace into a readable list of
  what is wrong. This is the change a future you will appreciate most.
- **`productionRequired`** makes the safe behaviour the default and the unsafe one
  impossible — you cannot forget to set `JWT_SECRET` in production, because the
  process refuses to start.
- **Environment-dependent defaults** — `DB_SSL` defaults to `true` in production
  and `false` locally; `ENABLE_API_DOCS` the reverse. The right thing happens
  without anyone remembering.

### 2. A committed `.env.example`

Generate it from the schema so it cannot drift:

```ts
// server/scripts/generate-env-example.ts
// Walks envSchema.shape, emits `# <description>` + `KEY=<default or blank>`.
// Run via `pnpm env:example` and commit the output.
```

Or write it by hand and keep it current:

```dotenv
# server/.env.example -- copy to .env and fill in.
# Generate secrets with: openssl rand -hex 32

NODE_ENV=development
PORT=8000
LOG_LEVEL=info

# --- Secrets. No defaults in production; the process will refuse to start. ---
JWT_SECRET=                    # REQUIRED, min 32 chars
DB_PASSWORD=postgres
BOOTSTRAP_TOKEN=               # set to enable first-super-admin registration, then unset

# --- Database ---
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/postgres
DB_POOL_MAX=10
DB_SSL=false                   # true for any managed PostgreSQL

# --- Deployment topology (see report/vulnerabilities/22) ---
TRUST_PROXY=false              # '1' behind one reverse proxy. NEVER 'true'.
CORS_ALLOWED_ORIGINS=          # comma-separated exact origins, e.g. https://iam.example.com
ENABLE_API_DOCS=true

# --- Auth ---
ACCESS_TOKEN_EXPIRES_IN=20m
REFRESH_TOKEN_EXPIRES_IN=7d
SALT_ROUNDS=12

# --- Redis ---
REDIS_URL=redis://localhost:6379

# --- Rate limiting ---
RATE_LIMIT_LOGIN_IP_LIMIT=20
RATE_LIMIT_LOGIN_IP_WINDOW_MS=900000
RATE_LIMIT_LOGIN_FAIL_LIMIT=5
RATE_LIMIT_LOGIN_FAIL_WINDOW_MS=900000
```

### 4. Client configuration for non-proxied deployments

```ts
// client/src/api/config.ts
/**
 * Empty string keeps every request relative, which is correct behind the Vite
 * dev proxy and behind a production reverse proxy that serves the SPA and the
 * API from one origin. Set VITE_API_BASE_URL only when they are separate --
 * and then CORS_ALLOWED_ORIGINS on the server must list this app's origin.
 */
export const API_BASE_URL = import.meta.env.VITE_API_BASE_URL ?? ''
```

```ts
// client/src/api/client.ts
const api = axios.create({
  baseURL: API_BASE_URL,
  withCredentials: true,
  headers: { 'Content-Type': 'application/json' },
})
```

Zero behaviour change today (empty base URL = relative), and the deployment
option exists when needed. **Remember `import.meta.env` values are baked into the
bundle at build time and are public** — never put a secret there.

### 5. Secret management beyond files

For a real deployment, `.env` files on disk are the floor, not the goal. In
rough order of effort:

| Approach | When |
| --- | --- |
| `.env` file, `chmod 600`, outside the repo | Single VPS |
| Platform environment variables (Railway, Fly, Render, ECS task definitions) | Most deployments — no file on disk |
| A secret manager (AWS Secrets Manager, Vault, Doppler) injected at boot | When you need rotation and an access audit trail |

The schema above works with all three, because it reads `process.env` and does not
care how the values arrived. That is the payoff for having centralised it.

## What you already got right

- **One schema, one exported object, one source of truth.** Zero direct
  `process.env` reads outside this file. That single decision is why six separate
  findings can each add a variable without touching six files, and why this
  suggestion is a rewrite of one file rather than a refactor of thirty.
- **`.describe()` on every key.** The schema is self-documenting, which makes
  generating `.env.example` from it nearly mechanical.
- **`z.coerce.number()` with `.int().positive()`** on every numeric variable. The
  environment gives you strings; you handled that explicitly instead of relying on
  JavaScript's implicit coercion, and you constrained the ranges.
- **`.env` is gitignored in three overlapping patterns** (`.env`, `*.env`,
  `.env.*.local`) and has never been committed — verified against
  `git ls-files` and the full history. You thought about this.
- **`DATABASE_URL` is separated from the discrete `DB_*` variables**, because
  `node-pg-migrate` wants a connection string and the pool wants components.
  Pragmatic, and `buildDatabaseUrl()` in `db.migrate.ts` correctly
  `encodeURIComponent`s the credentials when constructing the fallback — a detail
  that bites people whose password contains an `@`.
- **`JWT_EXPIRES_TIMELINE` as a `z.enum`** rather than a free-form duration
  string, so a typo like `20mm` is caught at boot rather than producing a token
  with a nonsense expiry.

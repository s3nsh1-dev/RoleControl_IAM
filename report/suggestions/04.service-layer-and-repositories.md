# 04. Separate HTTP concerns from SQL with a service and repository layer

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **6 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Effort**   | Large — architectural. Do it incrementally, one resource at a time.   |
| **Files**    | all of [server/src/controllers/](../../server/src/controllers/), [server/src/models/](../../server/src/models/) |

---

## The shape today

Controllers do five jobs each: read the request, authorize, write SQL, audit, and
format the response. `createUser` is 130 lines that includes a five-table
transaction, two authorization layers, three audit writes and the HTTP envelope.

The `models/` directory suggests you intended something different. It contains
seven Zod schemas describing table shapes:

```ts
// server/src/models/user.model.ts
const userModelSchema = z.object({
  id: z.number().int().positive().describe("User Unique ID (numeric primary key)."),
  fullname: z.string().trim().min(3).max(150),
  email: z.string().trim().email(),
  password: z.string().nonempty().min(4),
  is_active: z.boolean().default(true),
  created_at: z.coerce.date(),
  created_by: z.number().int().positive().nullable().optional(),
});
```

Grep for their use:

```
$ grep -rn "userModelSchema\|rolesModelSchema\|postModelSchema" server/src --include=*.ts \
    | grep -v "^server/src/models/"
(no output)
```

**Nothing imports them.** Seven files, roughly 300 lines, entirely dead. The
contracts in `api.contracts.ts` superseded them — that file now owns both request
validation and response shapes — but the models were never removed, so the
codebase carries two parallel descriptions of the same tables and a newcomer
cannot tell which is authoritative.

That is the clearest symptom of the missing layer: there is no home for
"what a user *is*, independent of HTTP", so the concept exists twice and belongs
nowhere.

## Why a layer helps here specifically

Not "because layers are good architecture." Three concrete problems it solves in
*this* codebase:

**1. The same query is written four times.** `getUserRoleNames`,
`getUserEffectivePermissions`, `checkRolePermissions`, and the two inline role
lookups in `deletePost` all join `user_roles → roles` or
`user_roles → role_permissions → permissions`. `deletePost` writes its own:

```ts
// server/src/controllers/post/deletePost.ts:48
const actorRolesQuery = await client.query<{ name: ROLES_TYPES }>(
  `SELECT r.name FROM user_roles ur JOIN roles r ON r.id = ur.role_id WHERE ur.user_id = $1`,
  [actorId],
);
```

That is `getUserRoleNames` inlined, because importing it and passing `client`
felt like more work than retyping it. A repository makes the shared query the
path of least resistance.

**2. Business rules cannot be unit tested.** "An admin cannot delete a
super-admin's post" is a rule. Testing it currently requires a running
PostgreSQL, a seeded RBAC set, a logged-in session and an HTTP request — that is
what `tests/v2-integration` does. Integration tests are valuable and yours are
good, but a rule that needs 200ms and a database to verify will not get the
twenty edge-case tests it deserves. A pure function over a repository interface
gets them in milliseconds.

**3. Changing the response shape means touching SQL.** `toUserSummary` sits in
`api.mappers.ts`, but the `SELECT` column list it depends on is spread across
`listUsers`, `viewUser`, `createUser` and `updateUser`. Add a field to
`UserSummary` and you edit five files, and if you miss one, `toUserSummary` reads
`undefined` and `parsePositiveInt` throws a 400 at runtime.

## The design

Three layers, each with one job.

```
routes/          HTTP surface: paths, middleware, permission declarations
  controllers/   HTTP translation: parse request -> call service -> send response
    services/    Business rules: authorization, invariants, orchestration
      repositories/  SQL: one file per table, returns rows, no rules
```

### Repository: SQL only, no decisions

```ts
// server/src/repositories/user.repository.ts
import type { QueryableDb } from "@/types/commonTypes.ts";

/** Every column the API ever exposes for a user. One list, one place. */
const USER_COLUMNS = "id, fullname, email, is_active, created_at, created_by";

export type UserRow = {
  id: number; fullname: string; email: string;
  is_active: boolean; created_at: Date; created_by: number | null;
};

export const userRepository = {
  findById: async (db: QueryableDb, id: number): Promise<UserRow | null> => {
    const result = await db.query<UserRow>(
      `SELECT ${USER_COLUMNS} FROM users WHERE id = $1`, [id]);
    return result.rows[0] ?? null;
  },

  findByEmailWithPassword: async (db: QueryableDb, email: string) => {
    const result = await db.query<UserRow & { password: string }>(
      `SELECT ${USER_COLUMNS}, password FROM users WHERE email = $1`, [email]);
    return result.rows[0] ?? null;
  },

  lockById: async (db: QueryableDb, id: number): Promise<UserRow | null> => {
    const result = await db.query<UserRow>(
      `SELECT ${USER_COLUMNS} FROM users WHERE id = $1 FOR UPDATE`, [id]);
    return result.rows[0] ?? null;
  },

  listPaginated: async (db: QueryableDb, limit: number, offset: number) => { /* ... */ },
  countAll: async (db: QueryableDb): Promise<number> => { /* ... */ },
  insert: async (db: QueryableDb, input: NewUserInput): Promise<UserRow> => { /* ... */ },
  updateProfile: async (db: QueryableDb, id: number, patch: UserPatch): Promise<UserRow | null> => { /* ... */ },
  deleteById: async (db: QueryableDb, id: number): Promise<UserRow | null> => { /* ... */ },
};
```

Two properties worth noting. `USER_COLUMNS` is defined once, so the "add a field,
miss a query" bug becomes impossible. And **`password` is only reachable through
one deliberately-named method** — `findByEmailWithPassword`. Every other read
cannot leak the hash even if `sanitizeUserRecord` is forgotten. That is a
structural guarantee replacing a discipline-based one.

Every method takes `db: QueryableDb` as its first parameter — no defaults, per
[Suggestion 02](./02.thread-transaction-client-through-helpers.md).

### Service: rules and orchestration, no HTTP

```ts
// server/src/services/user.service.ts
export const userService = {
  async deleteUser(client: PoolClient, actorId: number, targetUserId: number): Promise<UserRow> {
    if (actorId === targetUserId) {
      throw AppError.forbidden("You cannot delete yourself");
    }

    await checkRolePermissions(actorId, "delete", "user", client);

    const target = await userRepository.lockById(client, targetUserId);
    if (!target) throw AppError.notFound("User not found or already deleted");

    await assertCanManageUser(actorId, targetUserId, client, "You cannot delete this user");

    const targetRole = await roleRepository.findHighestForUser(client, targetUserId);
    if (targetRole?.is_system_admin && await roleRepository.countSuperAdmins(client) <= 1) {
      throw AppError.forbidden("Cannot delete the last super-admin");
    }

    const deleted = await userRepository.deleteById(client, targetUserId);
    if (!deleted) throw AppError.notFound("User not found or already deleted");

    await auditDBMutation({
      db: client, actorId, actionType: "delete", resourceType: "user",
      resourceId: deleted.id, oldValues: deleted,
    });

    return deleted;
  },
};
```

Read that top to bottom: it is the *policy* for deleting a user, stated once, in
order, with no SQL and no `res`. That is the artefact worth having.

### Controller: translation only

```ts
// server/src/controllers/users/deleteUser.ts
const deleteUser = asyncHandler(async (req, res) => {
  const actorId = parsePositiveInt(req.user.uId, "actorId");
  const targetUserId = parsePositiveInt(req.params["userId"], "userId");

  const deleted = await withTransaction((client) =>
    userService.deleteUser(client, actorId, targetUserId),
  );

  new AppResponse(200, "User deleted successfully", {
    user: toUserSummary(deleted),
  }).send(res);
});
```

Eighty lines to eight.

## Migration plan

**Do not do this as a big-bang refactor.** Take one resource at a time, in this
order, keeping the integration tests green throughout:

1. **Delete `server/src/models/`.** It is dead code and it is actively confusing.
   Verify with the grep above first. This is a five-minute win that makes
   everything after it clearer.
2. **Build `withTransaction`** ([Suggestion 02](./02.thread-transaction-client-through-helpers.md)).
   Everything else depends on it.
3. **Extract `userRepository`** and convert only the five user controllers.
   `pnpm test:v2` must stay green. This is the proof-of-concept.
4. **Extract `userService`** from those same five controllers.
5. **Repeat for posts, then roles, then permissions, then sessions.** Posts
   second because they are the simplest.
6. **Stop when it stops paying.** `listMigrations` is fifteen lines of one query
   — a repository for it is ceremony. Not every controller needs the full stack;
   the ones with transactions and multi-step rules do.

## When this is the wrong call

Be honest about the trade. This adds indirection, and indirection has a cost:
tracing a request now means opening three files instead of one. For a codebase
this size (30 endpoints, one developer), the win is real but not overwhelming.

Prioritise it **below** the security findings and below
[Suggestion 02](./02.thread-transaction-client-through-helpers.md), which
delivers most of the safety benefit for a tenth of the effort. Do this when you
want the codebase to demonstrate architectural judgement, or when you start
adding features and the copy-paste rate becomes annoying.

## Interaction with other findings

- **[Suggestion 02](./02.thread-transaction-client-through-helpers.md)** is the
  prerequisite. `withTransaction` is what lets a service take a `client` without
  each service inventing its own transaction handling. **Do 02 first.**
- **[Suggestion 01](./01.centralize-authorization-in-middleware.md)** — the coarse
  permission check moves to middleware; the fine-grained checks move into
  services. These are complementary halves of "authorization lives somewhere
  named". No conflict.
- **[Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md)**
  — repositories taking `db` as a required first parameter makes that bug
  structurally impossible. This is its permanent fix.
- **[Vulnerability 21](../vulnerabilities/21.non-transactional-audit-writes.md)**
  — same. A service that receives a `client` cannot accidentally audit on the pool.
- **[Suggestion 09](./09.pagination-strategy.md)** — keyset pagination belongs in
  repositories. Doing 09 first means writing the pagination logic in controllers
  and moving it later.

## What you already got right

- **Controllers are already split one-per-file** (`controllers/users/deleteUser.ts`
  rather than a 900-line `users.controller.ts`), with a barrel file re-exporting
  them. That is the hard organisational work already done — this suggestion adds
  layers beneath a structure that is already navigable.
- **`api.mappers.ts` is a genuine DTO boundary.** Every response goes through an
  explicit mapper, so no database row is ever spread directly into JSON. That is
  the presentation layer of this architecture, already built and already correct.
- **`api.contracts.ts` centralises every request and response schema** and feeds
  the OpenAPI document. The contract layer exists too.
- **`utils/helper.ts` already contains the beginnings of a service layer** —
  `canActorManageRole`, `checkRolePermissions`, `getUserEffectivePermissions`,
  `auditDBMutation`. These are business-rule functions, correctly extracted from
  controllers. The refactor is largely a matter of giving them a home with a name.
- The `QueryableDb` type and the `db` parameter convention mean repositories can
  be written without inventing any new abstraction. You already built the seam.

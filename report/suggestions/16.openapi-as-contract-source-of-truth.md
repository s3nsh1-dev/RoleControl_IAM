## What you built

This is already the best-engineered part of the project, so the suggestion is
about finishing it rather than replacing it.

```
Zod schemas (api.contracts.ts)
        │
        ├──> runtime validation in controllers  (Schema.parse(req.body))
        │
        └──> zod-to-openapi ──> openapi/document.ts ──> openapi.json
                                                            │
                                          openapi-typescript │
                                                            ▼
                                              client/src/api/schema.ts
                                                            │
                                                            ▼
                                              client/src/api/types.ts
```

One definition drives request validation, the published spec, and the client's
types. That is the architecture people write blog posts about and rarely build.

Three gaps remain.

## Gap 1 — the spec can drift silently

`openapi.json` is generated by `pnpm openapi:export` and committed. The client's
`schema.ts` is generated from it by `pnpm generate:types` and committed. **Neither
runs automatically.** Change `UserSummarySchema`, forget both commands, and:

- The server validates and returns the new shape.
- The committed `openapi.json` describes the old shape.
- The client's types describe the old shape, so TypeScript reports no error at
  the call site that is now wrong.

You get a silent contract break that compiles cleanly.

### Fix — make drift a build failure

```json
// server/package.json
"scripts": {
  "openapi:export": "tsx src/openapi/export.ts",
  "openapi:check": "tsx src/openapi/export.ts --check"
}
```

```ts
// server/src/openapi/export.ts
const generated = JSON.stringify(openApiDocument, null, 2);

if (process.argv.includes("--check")) {
  const onDisk = await readFile(outputPath, "utf8").catch(() => "");
  if (onDisk.trim() !== generated.trim()) {
    console.error(
      "openapi.json is out of date. Run `pnpm openapi:export` and commit the result.",
    );
    process.exit(1);
  }
  console.log("openapi.json is up to date.");
  process.exit(0);
}

await writeFile(outputPath, generated);
```

```json
// client/package.json
"scripts": {
  "generate:types": "openapi-typescript ../server/openapi/openapi.json -o src/api/schema.ts",
  "generate:types:check": "openapi-typescript ../server/openapi/openapi.json -o /tmp/schema.check.ts && diff -q src/api/schema.ts /tmp/schema.check.ts"
}
```

Then a pre-commit hook or a CI step runs both `:check` variants. Regeneration
becomes something you cannot forget rather than something you must remember.

## Gap 2 — declared validation that never runs

`api.contracts.ts` defines param and query schemas that appear in the spec and
are **never applied**:

| Schema | Declared in the spec | Enforced at runtime |
| --- | --- | --- |
| `UserIdParamsSchema` | ✅ | ❌ — `parsePositiveInt` is used instead |
| `PostIdParamsSchema` | ✅ | ❌ |
| `SessionIdParamsSchema` | ✅ | ❌ |
| `PermissionIdParamsSchema` | ✅ | ❌ |
| `RoleNameParamsSchema` | ✅ (`z.enum(ROLES_LIST)`) | ❌ — **nothing validates `roleName` at all** |
| `PaginationQuerySchema` | ✅ | ❌ — `parsePaginationQuery` duplicates it |

The `RoleNameParamsSchema` row is the sharpest: the spec promises that
`PUT /api/roles/not-a-role` returns 400. It actually returns 404 from a database
miss. A client written against the contract handles the wrong error.

### Fix

[Suggestion 08](./08.single-validation-middleware.md) — apply these exact schemas
in a `validate({ params, query, body })` middleware. That suggestion is the
runtime half of this one; they should be read together.

## Gap 3 — constraints exist twice and disagree

The generated types carry **shapes**, not **constraints**. `openapi-typescript`
turns `z.string().min(12).max(128)` into `string`. So the client rewrites the
rules by hand in `validation/schemas.ts` — and, as
[Vulnerability 18](../vulnerabilities/18.weak-password-policy.md) documents, they
have already drifted:

| Constraint | Server | Client | Status |
| --- | --- | --- | --- |
| password (register) | `min(4)` | `min(8)` | disagree |
| `fullname` | `min(3).max(150)` | `min(2).max(100)` | **client accepts input the server rejects** |
| post `title` | `min(3).max(255)` | `min(3).max(200)` | disagree |
| post `content` | unbounded | `max(10000)` | disagree |

### Fix — publish the constraints, generate the constants

`zod-to-openapi` already emits `minLength` / `maxLength` / `pattern` into the
JSON Schema. Read them back out at build time:

```ts
// client/scripts/generate-constraints.ts
import spec from '../../server/openapi/openapi.json' with { type: 'json' }

const constraintsFor = (schemaName: string) => {
  const schema = spec.components.schemas[schemaName]
  return Object.fromEntries(
    Object.entries(schema.properties ?? {}).map(([field, def]: [string, any]) => [
      field,
      { min: def.minLength, max: def.maxLength, pattern: def.pattern },
    ]),
  )
}

// Emits client/src/api/constraints.generated.ts
```

```ts
// client/src/validation/schemas.ts
import { CONSTRAINTS } from '@/api/constraints.generated'

const { min: FULLNAME_MIN, max: FULLNAME_MAX } = CONSTRAINTS.AuthRegisterRequest.fullname
const { min: PASSWORD_MIN, max: PASSWORD_MAX } = CONSTRAINTS.AuthRegisterRequest.password

export const registerSchema = z.object({
  fullname: z.string().trim()
    .min(FULLNAME_MIN, `Name must be at least ${FULLNAME_MIN} characters`)
    .max(FULLNAME_MAX, `Name must be ${FULLNAME_MAX} characters or less`),
  email: z.string().trim().email('Enter a valid email address'),
  password: z.string()
    .min(PASSWORD_MIN, `Password must be at least ${PASSWORD_MIN} characters`)
    .max(PASSWORD_MAX, `Password must be ${PASSWORD_MAX} characters or less`),
})
```

The client keeps its own **messages** (which should be user-facing and friendly)
while inheriting the server's **numbers**. Drift becomes impossible.

**If that script feels like too much machinery**, the cheap alternative is a
shared constants file kept in sync by a comment and a test — but a test comparing
the two is most of the work of generating them, so prefer generation.

## Gap 4 — the spec is not validated against reality

`tests/v5-openapi` verifies the document generates. Nothing verifies that actual
responses match it. A mapper that returns `created_at` as a `Date` rather than an
ISO string would pass every existing test.

### Fix — assert responses against the contract in integration tests

```ts
// server/tests/v2-integration/helpers.ts
import { ListUsersResponseSchema } from "@/contracts/api.contracts.ts";

export const assertMatchesContract = <T extends z.ZodTypeAny>(schema: T, body: unknown) => {
  const result = schema.safeParse(body);
  if (!result.success) {
    throw new Error(
      `Response does not match its contract:\n${JSON.stringify(result.error.issues, null, 2)}`,
    );
  }
};
```

```ts
const response = await http.get("/api/users", { cookies });
assertMatchesContract(ListUsersResponseSchema, response.body);
```

One line per test, and it closes the loop: the schema now validates **both**
directions. This is the highest-value item in this suggestion — it is what turns
a documented contract into an enforced one.

## Gap 5 — small contract inaccuracies

Worth a pass while you are in here:

- **`toRole`, `toPermission`, `toUserListItem` return `string`**, but
  `RoleSchema.name` is `RoleNameSchema` (an enum) and `PermissionSchema.action` is
  `PermissionActionSchema`. If a database row ever holds a value outside the enum,
  the response violates its own contract and nothing notices. Gap 4's assertion
  catches this.
- **`AuditLogSchema.resource_id` is `z.number().int().positive()`** but
  [Vulnerability 17](../vulnerabilities/17.no-authentication-audit-trail.md) makes
  it nullable for authentication events. Update together.
- **`ApiErrorSchema` includes `trace: z.string().optional()`** — correct, since
  the error handler does emit it in development. Worth an `.openapi({ description:
  "Present only in non-production environments." })` so nobody builds against it.

## What you already got right

- **The whole pipeline exists and works.** Zod → OpenAPI → TypeScript, with the
  client's `types.ts` re-exporting from generated `schema.ts` under friendly
  aliases. Most teams either hand-write their OpenAPI (and it rots) or skip it
  entirely.
- **`makeSuccessEnvelopeSchema` and `makeMessageEnvelopeSchema`** are schema
  factories, so every endpoint's response envelope is structurally identical and
  defined once. That is why `AppResponse.toJSON` and the client's response
  interceptor can both make a blanket assumption about the shape and be right
  every time.
- **`CapabilityKeySchema` is a curated, UI-facing vocabulary**, distinct from the
  internal `action:resource` representation, mapped by `toCapabilityKeys`. That
  indirection means the internal permission model can change without breaking a
  single client component — a genuinely senior API design decision.
- **Security schemes are registered and attached per-operation**
  (`accessCookieAuth`, `refreshCookieAuth`), so the spec accurately describes the
  auth model rather than declaring one global scheme.
- **Param schemas carry full OpenAPI metadata** — `name`, `in`, `required`,
  `description`, `example` — via `makePositivePathParamSchema`. The spec is
  genuinely usable in Swagger UI, not a skeleton.
- **`client/src/api/types.ts` uses `satisfies readonly RoleName[]`** on the
  `roleNames` constant, so if the generated enum changes, the hand-written array
  fails to compile. That is a deliberate, well-chosen guardrail against exactly
  the drift this suggestion is about — you had the right instinct and applied it
  in the one place you could without more tooling.

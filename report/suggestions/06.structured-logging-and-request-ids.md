# 06. Replace 40 `console.*` calls with a structured logger and a request id

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **7 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Effort**   | Small-medium — one new file, one middleware, ~40 call-site edits      |
| **Files**    | 20+ files across [server/src/](../../server/src/), [errorHandler.middleware.ts](../../server/src/middleware/errorHandler.middleware.ts), [index.ts](../../server/index.ts) |

## What logging looks like today

```
$ grep -rc "console\." server/src | grep -v ":0"
40 occurrences across 14 files
```

A sample of what they emit:

```
Server is running on http://localhost:8000
✅ Database connected successfully
🟢 Redis client is ready to receive commands
Redis is not ready. Bypassing login IP rate limiter.
Login failure rate limiter degraded. Bypassing request.
Rate limiter Redis check failed, bypassing: Error: connect ECONNREFUSED 127.0.0.1:6379
Registration Transaction Error: error: duplicate key value violates unique constraint
```

Three problems, in order of how much they hurt.

**1. There is no request context.** When you see
`"Redis is not ready. Bypassing login IP rate limiter."` you cannot answer: which
request? from which IP? for which account? was that one event or four hundred?
The line that matters most for security —
[the rate-limiter bypass](../vulnerabilities/07.rate-limiters-fail-open.md) — is
also the least actionable.

**2. Unhandled 500s log nothing at all.** `errorHandler` has no logging:

```ts
// server/src/middleware/errorHandler.middleware.ts -- the entire function
const errorHandler = (err, _req, res, _next) => {
  let statusCode = 500;
  // ... classification ...
  return res.status(statusCode).json({ success: false, status, message, ... });
};
```

An unexpected exception — a `TypeError`, a `pg` error with an unmapped code —
returns `"Something went wrong!"` to the client and **writes nothing to stdout**.
In development the stack goes to the *client* in the `trace` field, so the
operator sees it only if they inspect the response. In production it vanishes
entirely. That is the single biggest gap here.

**3. Output is unparseable.** Emoji-prefixed prose cannot be filtered, aggregated,
or alerted on. `grep "Bypassing"` is your entire observability story.

## The suggestion

### 1. A logger with levels and structure

You have two reasonable options. **`pino`** is the standard choice — fast, JSON
output, ~1 dependency. If you would rather add nothing, Node 18+ has enough
built in:

```ts
// server/src/utils/logger.ts -- zero-dependency version
import { AsyncLocalStorage } from "node:async_hooks";
import env from "./envHelper.ts";

type LogLevel = "debug" | "info" | "warn" | "error";
const LEVELS: Record<LogLevel, number> = { debug: 10, info: 20, warn: 30, error: 40 };

const requestContext = new AsyncLocalStorage<{ requestId: string; actorId?: number }>();

const minLevel = LEVELS[env.LOG_LEVEL as LogLevel] ?? LEVELS.info;

const write = (level: LogLevel, message: string, fields: Record<string, unknown> = {}) => {
  if (LEVELS[level] < minLevel) return;

  const entry = {
    level,
    time: new Date().toISOString(),
    message,
    ...requestContext.getStore(),        // requestId + actorId, automatically
    ...fields,
  };

  // JSON in production for log aggregators; readable lines in development.
  if (env.NODE_ENV === "production") {
    process.stdout.write(`${JSON.stringify(entry)}\n`);
  } else {
    const { level: _l, time, message: msg, ...rest } = entry;
    const suffix = Object.keys(rest).length ? ` ${JSON.stringify(rest)}` : "";
    process.stdout.write(`${time} ${level.toUpperCase().padEnd(5)} ${msg}${suffix}\n`);
  }
};

export const logger = {
  debug: (message: string, fields?: Record<string, unknown>) => write("debug", message, fields),
  info:  (message: string, fields?: Record<string, unknown>) => write("info",  message, fields),
  warn:  (message: string, fields?: Record<string, unknown>) => write("warn",  message, fields),
  error: (message: string, error?: unknown, fields?: Record<string, unknown>) =>
    write("error", message, {
      ...fields,
      error: error instanceof Error
        ? { name: error.name, message: error.message, stack: error.stack }
        : error,
    }),
};

export { requestContext };
```

`AsyncLocalStorage` is what makes this worth doing: the request id propagates
through every `await` without being threaded as a parameter, so
`logger.warn("Redis is not ready...")` deep inside a rate limiter automatically
carries the request context.

### 2. Request id middleware

```ts
// server/src/middleware/requestContext.middleware.ts
import { randomUUID } from "node:crypto";
import type { NextFunction, Request, Response } from "express";
import { logger, requestContext } from "@/utils/logger.ts";

const requestContextMiddleware = (req: Request, res: Response, next: NextFunction) => {
  // Honour an upstream id so a trace spans the proxy and the API.
  const incoming = req.get("x-request-id");
  const requestId = incoming && /^[\w-]{1,128}$/.test(incoming) ? incoming : randomUUID();

  res.setHeader("X-Request-Id", requestId);

  requestContext.run({ requestId }, () => {
    const startedAt = process.hrtime.bigint();

    res.on("finish", () => {
      const durationMs = Number(process.hrtime.bigint() - startedAt) / 1e6;
      const level = res.statusCode >= 500 ? "error" : res.statusCode >= 400 ? "warn" : "info";

      logger[level]("request completed", {
        method: req.method,
        path: req.route?.path ?? req.path,   // the route pattern, not the filled-in id
        status: res.statusCode,
        durationMs: Math.round(durationMs * 100) / 100,
        ip: req.ip,
      });
    });

    next();
  });
};
```

Note `req.route?.path` — logging `/api/users/:userId` rather than
`/api/users/4471` keeps ids out of logs and makes aggregation possible.

Mount it first in `app.ts`, before `express.json()`.

Enrich the context once the actor is known:

```ts
// server/src/middleware/checkCookieSignature.middleware.ts -- after req.user is set
const store = requestContext.getStore();
if (store) store.actorId = userPayload.uId;
```

Every subsequent log line in that request now carries `actorId` for free.

### 3. Log unhandled errors (the highest-value change)

```ts
// server/src/middleware/errorHandler.middleware.ts -- before the response
if (statusCode >= 500) {
  logger.error("Unhandled error", err, { method: req.method, path: req.path, statusCode });
} else if (statusCode === 401 || statusCode === 403) {
  // Authorization failures are security signal, not noise.
  logger.warn("Request denied", { method: req.method, path: req.path, statusCode, message });
}
```

`_req` becomes `req` since it is now used. This one block is worth more than the
other two combined.

### 4. Convert the existing call sites

Mechanical, and the meaning improves at each one:

```ts
// before
console.warn("Redis is not ready. Bypassing login IP rate limiter.");
// after -- now filterable, alertable, and attributable to a request
logger.warn("Rate limiter bypassed: Redis unavailable", { limiter: "login-ip", key: ipKey });

// before
console.error("Rate limiter Redis check failed, bypassing:", error);
// after
logger.error("Rate limiter check failed", error, { limiter: "login-ip", key: ipKey });

// before
console.error("Registration Transaction Error:", error);
// after
logger.error("Registration transaction failed", error, { email: hashSha256(email) });
```

That last one matters: **do not log raw email addresses or any request body.**
Hash identifiers the way `buildLoginFailureKey` already does. A log file full of
plaintext emails from an IAM system is a data-protection problem.

### 5. Add `LOG_LEVEL`

```ts
// server/src/utils/envHelper.ts
LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info")
  .describe("Minimum log level to emit"),
```

## What this unlocks

Once every line carries `requestId`, `actorId`, `path` and `status`, questions
that are currently unanswerable become one query:

- *"Show me everything that happened during the request that returned this 500."*
  → filter on `requestId` from the `X-Request-Id` response header.
- *"Was the rate limiter degraded when this account was compromised?"*
  → filter on `message: "Rate limiter bypassed"` within a time window.
- *"Which endpoints are slow?"* → aggregate `durationMs` by `path`.
- *"Is one account generating all the 403s?"* → group `Request denied` by `actorId`.

## Interaction with other findings

- **[Vulnerability 17](../vulnerabilities/17.no-authentication-audit-trail.md)**
  — audit events and application logs are **different things** and both are
  needed. Audit entries are durable, queryable business records in
  `audit_logs`; logs are operational telemetry. The connection: put `requestId`
  into `audit_logs.metadata` so an audit entry can be joined to its log lines
  during an investigation. **Design that metadata field here**, since this
  suggestion defines the id.
- **[Vulnerability 23](../vulnerabilities/23.error-messages-leak-internal-detail.md)**
  — that finding says "log internally, respond generically", using `console.warn`
  as a placeholder. **Write those calls as `logger.warn` directly** so you do not
  convert them twice.
- **[Vulnerability 07](../vulnerabilities/07.rate-limiters-fail-open.md)** — the
  bypass warnings become the primary signal that security controls are degraded.
  This suggestion is what makes that finding's "make the degraded state visible"
  requirement achievable.
- **[Suggestion 07](./07.health-readiness-and-graceful-shutdown.md)** — startup
  and shutdown logging moves to the logger too; the health endpoint is the
  point-in-time complement to the log stream.
- **No contradiction** with anything. This is purely additive.

## What you already got right

- **Errors are logged where they are caught, not swallowed.**
  `compareHashStrings`, `generateHashString`, `authRegistration`,
  `allowSlidingWindow` and `clearRateLimitKey` all log the underlying error before
  translating it. The instinct — preserve the detail, return something safe — is
  correct; the mechanism just needs upgrading.
- **The rate-limiter bypasses are logged at all.** A silent fail-open would be far
  worse than a `console.warn` fail-open. You made a deliberate degradation
  observable, which is exactly right.
- **`registration.ts` logs only non-`AppError` failures**
  (`if (!(error instanceof AppError)) console.error(...)`), so expected business
  rejections do not pollute the error stream. That is a genuinely thoughtful
  distinction that many codebases miss.
- **Startup logging covers the things you need at boot** — port, database
  connectivity, Redis state — and the emoji, whatever else you think of them, make
  a development terminal readable at a glance. Keep them for the development
  formatter; drop them from the JSON path.
- **`index.ts` has handlers for `uncaughtException`, `unhandledRejection`,
  `SIGINT` and `SIGTERM`**, each logging before exiting. The process lifecycle is
  already instrumented; it just needs structure.

# 17. Stop committing generated artifacts (243 coverage files are in git)

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **4 / 10**                                                            |
| **Side**     | **Both** (repository-level)                                            |
| **Effort**   | Tiny — 15 minutes                                                      |
| **Files**    | [client/.gitignore](../../client/.gitignore), repository root, `client/coverage/`, `client/test-results/` |

---

## The finding

```
$ git ls-files | wc -l
585

$ git ls-files | grep -c "^client/coverage/"
243
```

**42% of the tracked files in this repository are a generated Vitest coverage
report.** That includes:

- `client/coverage/lcov-report/**` — HTML with inlined source for every file
- `client/coverage/src/**/*.html` — a page per source file
- `client/coverage/lcov.info`
- Binary assets: `favicon.png`, `sort-arrow-sprite.png`
- `client/test-results/.last-run.json` — Playwright's run state

`client/.gitignore` covers `node_modules`, `dist`, `dist-ssr`, `*.local` and
editor directories. It does not mention `coverage` or `test-results`, because
those directories did not exist when it was written.

There is also no **root** `.gitignore` at all — only `server/.gitignore` and
`client/.gitignore`.

## Why it is worth fixing

Not because 243 files is a lot of bytes. Because of what they do to the workflow:

**1. Every `pnpm test:coverage` run produces a huge, meaningless diff.** Coverage
HTML embeds timestamps and full source snapshots, so re-running the suite touches
hundreds of files. `git status` becomes unreadable, and the habit of
`git add -A` becomes dangerous — that is precisely the mechanism by which a
`.env` eventually gets committed.

**2. It hides real changes in review.** A pull request touching two source files
and 243 coverage files is a pull request nobody reads carefully.

**3. It is stale by construction.** The committed report reflects whenever
someone last ran the command. Anyone reading it gets a number that may be months
out of date, with no indication.

**4. It is a small information disclosure.** `coverage/lcov-report/**` embeds full
source, so if this repository is ever made public, source you thought was in one
place is in two — including any file later deleted from `src/` but still present
in a committed report.

## The fix

### 1. Ignore rules

```gitignore
# /.gitignore  (new file)
node_modules/
dist/
build/
out/

# Test and coverage output
coverage/
test-results/
playwright-report/
blob-report/
.nyc_output/
*.tsbuildinfo

# Environment
.env
.env.*
!.env.example

# OS and editor
.DS_Store
Thumbs.db
*.log
```

```gitignore
# client/.gitignore  -- append
coverage/
test-results/
playwright-report/
blob-report/
```

The root file's `.env` / `.env.*` rules are the important part —
[Suggestion 13](./13.environment-config-and-secret-management.md) and
[Suggestion 14](./14.docker-compose-and-reproducible-dev-env.md) both introduce
root-level environment files that would otherwise be committed.

### 2. Untrack without deleting

```bash
git rm -r --cached client/coverage client/test-results
git commit -m "chore: stop tracking generated coverage and test output"
```

`--cached` removes them from the index but leaves the working directory alone.

### 3. Consider the documentation directories

This one is a judgement call, and I would **leave them as they are**:

| Directory | Files | Verdict |
| --- | --- | --- |
| `server/learning_readme/` | 37 | **Keep.** Design analysis, decision records, implementation plans. Genuinely valuable — `06-refresh-token-analysis.md`, `12-redis-integration-analysis.md`, `24-global-ratelimiting-plan.md` document *why* the code is shaped the way it is. |
| `client/plan_readme/` | 35 | **Keep**, same reasoning. |
| `server/docs/`, `client/docs/` | 12 | **Keep** — reference material. |

Together that is ~84 markdown files, more than the source file count. That reads
as unusual, but for a learning project it is the *point* — the reasoning is the
artefact. Two small improvements:

- Add a top-level `docs/INDEX.md` (or extend the root `README.md`) pointing at
  the four directories and saying what each is for. Right now a reader cannot
  tell that `learning_readme/` is a chronological journal and `docs/` is
  reference.
- Rename `16_frontend_testing_implementation_explainer.mf` → `.md`. The extension
  is a typo and the file does not render on any Git host.

### 4. Publish coverage instead of committing it

If you want coverage visible, the conventional route is a CI step that uploads
`lcov.info` to Codecov or Coveralls and puts a badge in the README. That gives a
live number rather than a snapshot, with no repository weight.

```yaml
# .github/workflows/ci.yml
- run: pnpm --dir client test:coverage
- uses: codecov/codecov-action@v4
  with:
    files: ./client/coverage/lcov.info
```

### 5. While you are here: the `dist` build is broken

Not a hygiene issue, but adjacent and worth knowing. `server/tsconfig.json` sets:

```json
"emitDeclarationOnly": true,
```

So `pnpm build` (`tsc`) emits **only** `.d.ts` files. `server/dist/` contains
`index.d.ts` and `tsconfig.tsbuildinfo` — no JavaScript. That means
`"start": "node dist/index.js"` cannot work today.

Development uses `tsx watch index.ts` and never touches `dist/`, so this has
gone unnoticed. It will surface the moment you containerise
([Suggestion 14](./14.docker-compose-and-reproducible-dev-env.md)). The options:

- **Bundle** with `tsup` or `esbuild` (simplest — handles the `.ts` import
  extensions your source uses, which plain `tsc` output does not resolve at
  runtime under Node's ESM loader).
- **Run `tsx` in production.** Legitimate for a small service; costs startup time
  and adds a runtime dependency.
- **Set `emitDeclarationOnly: false`** and add a path/extension rewriting step —
  your imports use `.ts` extensions (`import app from "./src/app.ts"`) which Node
  cannot resolve after compilation without help.

`dist/` is correctly gitignored in `server/.gitignore`, so nothing is tracked —
this is just a build that does not produce a runnable artifact.

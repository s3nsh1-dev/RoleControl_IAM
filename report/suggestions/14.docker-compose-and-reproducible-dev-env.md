## The current setup story

From the READMEs, running this project requires:

1. A local PostgreSQL on port 5432 with a `postgres` database
2. A local Redis on port 6379
3. `cd server && pnpm install && pnpm migrate:up && pnpm db:seed && pnpm dev`
4. `cd client && pnpm install && pnpm dev`
5. A manual `POST /api/auth/register` to bootstrap the super-admin

Steps 1 and 2 are the problem. They are undocumented as *versions*, they conflict
with whatever else is running on those ports, and `server/.env` hardcodes
`postgres:postgres@localhost:5432/postgres` — using the **default `postgres`
database**, which means `pnpm db:setup` runs
`DROP TABLE IF EXISTS ... CASCADE` against whatever else lives there.

There is also a real asymmetry: `server/learning_readme/` contains
`07_docker_implementation_guide.md` and `08_docker_infographics.md` with
architecture diagrams — the design work is done. It was just never built.

## What this actually buys you

Three things, in order of how much they matter for this project:

**1. `pnpm test:v2` through `test:v5` need a live database and Redis.** Four test
suites, all integration-style, all requiring infrastructure that has to be set up
by hand. That is the main reason a test suite stops being run. A compose file
turns "run the tests" into one command, which is the difference between tests
that run on every change and tests that run twice a year.

**2. The `postgres`-database collision is a real hazard.** Isolated containers
with a dedicated `rolecontrol` database make `db:setup`'s `DROP TABLE` safe.

**3. It is the missing half of the deployment story.** Several findings —
[TRUST_PROXY](../vulnerabilities/22.trust-proxy-misconfiguration-enables-limit-bypass.md),
[CORS](../vulnerabilities/10.no-security-headers-no-cors-policy-and-cookie-flags.md),
[health probes](./07.health-readiness-and-graceful-shutdown.md) — are about
deployment topology and cannot be *tested* without one.

## The design

### `compose.yaml` for development

```yaml
# compose.yaml -- development stack. Application runs on the host; only
# infrastructure is containerised, so hot reload stays instant.
services:
  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: rolecontrol
      POSTGRES_PASSWORD: rolecontrol_dev
      POSTGRES_DB: rolecontrol
    ports:
      - "5433:5432"          # 5433 on the host: never collide with a local install
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U rolecontrol -d rolecontrol"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:8-alpine
    command: ["redis-server", "--save", "", "--appendonly", "no"]
    ports:
      - "6380:6379"          # 6380 on the host, same reasoning
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  postgres-data:
```

Then `server/.env` points at the containers:

```dotenv
DATABASE_URL=postgresql://rolecontrol:rolecontrol_dev@localhost:5433/rolecontrol
REDIS_URL=redis://localhost:6380
```

**Keep the application on the host in development.** Containerising `tsx watch`
means bind-mounting `node_modules`, fighting file-watcher propagation, and a much
slower edit-reload cycle. Infrastructure in containers, code on the host, is the
setup that people actually keep using.

### A second compose file for the full stack

```yaml
# compose.full.yaml -- everything containerised. For testing the deployment
# topology (reverse proxy, TRUST_PROXY, CORS) and for CI.
services:
  postgres:
    extends: { file: compose.yaml, service: postgres }
    ports: []                                   # internal network only

  redis:
    extends: { file: compose.yaml, service: redis }
    ports: []

  api:
    build:
      context: ./server
      target: production
    environment:
      NODE_ENV: production
      DATABASE_URL: postgresql://rolecontrol:rolecontrol_dev@postgres:5432/rolecontrol
      REDIS_URL: redis://redis:6379
      JWT_SECRET: ${JWT_SECRET:?JWT_SECRET must be set}   # fails fast if missing
      TRUST_PROXY: "1"                          # exactly one proxy (nginx) in front
      CORS_ALLOWED_ORIGINS: "http://localhost:8080"
      ENABLE_API_DOCS: "false"
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_healthy }
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://localhost:8000/healthz').then(r=>process.exit(r.ok?0:1))"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 15s

  web:
    build:
      context: ./client
    ports:
      - "8080:80"
    depends_on:
      api: { condition: service_healthy }
```

Two details that matter:

- **`${JWT_SECRET:?...}`** makes compose refuse to start without the secret,
  matching [Vulnerability 09](../vulnerabilities/09.jwt-secret-and-credentials-default-to-placeholders.md)'s
  fail-fast requirement.
- **`TRUST_PROXY: "1"`** — a hop count, never `true`, per
  [Vulnerability 22](../vulnerabilities/22.trust-proxy-misconfiguration-enables-limit-bypass.md).
  This compose file becomes the place where the correct value is *documented by
  being used*.

### `server/Dockerfile`

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine AS base
RUN corepack enable
WORKDIR /app

FROM base AS deps
COPY package.json pnpm-lock.yaml ./
RUN --mount=type=cache,id=pnpm,target=/root/.local/share/pnpm/store \
    pnpm install --frozen-lockfile

FROM base AS build
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN pnpm build

FROM base AS production
ENV NODE_ENV=production
COPY package.json pnpm-lock.yaml ./
RUN --mount=type=cache,id=pnpm,target=/root/.local/share/pnpm/store \
    pnpm install --frozen-lockfile --prod
COPY --from=build /app/dist ./dist
COPY migrations ./migrations

# Never run as root.
USER node
EXPOSE 8000
CMD ["node", "dist/index.js"]
```

**One thing to check before this works:** `tsconfig.json` has
`"emitDeclarationOnly": true`, so `pnpm build` (`tsc`) currently emits **only
`.d.ts` files** — `server/dist/` contains `index.d.ts` and a
`tsconfig.tsbuildinfo`, no JavaScript. The `"start": "node dist/index.js"` script
cannot work today. You will need either `emitDeclarationOnly: false` with proper
`.js` extension rewriting, or a bundler step (`tsx build`, `esbuild`, `tsup`).
Worth discovering now rather than during a deploy.

### `client/Dockerfile`

```dockerfile
FROM node:24-alpine AS build
RUN corepack enable
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

FROM nginx:alpine AS production
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

```nginx
# client/nginx.conf
server {
  listen 80;
  root /usr/share/nginx/html;

  # SPA: unknown paths serve index.html so client-side routing works.
  location / { try_files $uri $uri/ /index.html; }

  # Same-origin API. This is what keeps sameSite=strict cookies working and
  # makes CORS a non-issue -- see report/vulnerabilities/10.
  location /api/ {
    proxy_pass http://api:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

That `location /api/` block is the production equivalent of the Vite dev proxy,
and it is what makes the whole cookie strategy work in production without
changing a line of application code.

### A `Makefile` so nobody memorises this

```makefile
.PHONY: dev db-reset test down

dev:                       ## Start infrastructure and both dev servers
	docker compose up -d --wait
	cd server && pnpm migrate:up && pnpm db:seed
	@echo "Infrastructure ready. Run 'pnpm dev' in server/ and client/."

db-reset:                  ## Wipe and reseed the database
	docker compose down -v
	docker compose up -d --wait
	cd server && pnpm migrate:up && pnpm db:seed

test:                      ## Run every server test suite against clean infrastructure
	docker compose up -d --wait
	cd server && pnpm test:v2 && pnpm test:v3 && pnpm test:v4 && pnpm test:v5

down:
	docker compose down
```

`--wait` blocks until the healthchecks pass, which removes the classic
"connection refused because Postgres was not ready yet" flake from CI.

## Interaction with other findings

- **[Suggestion 13](./13.environment-config-and-secret-management.md)** — the root
  `.gitignore` from that suggestion is a **prerequisite**. Compose invites a
  root-level `.env`, and without the ignore rule it gets committed. **Do 13
  first.**
- **[Suggestion 07](./07.health-readiness-and-graceful-shutdown.md)** — the
  container healthcheck needs `/healthz`. **Do 07 first** or the healthcheck has
  nothing to call.
- **[Vulnerability 10](../vulnerabilities/10.no-security-headers-no-cors-policy-and-cookie-flags.md)**
  — nginx proxying `/api` keeps everything same-origin, which is the deployment
  that makes `sameSite: "strict"` viable. **Decide the CORS policy before writing
  the compose file**, so the two agree.
- **[Vulnerability 22](../vulnerabilities/22.trust-proxy-misconfiguration-enables-limit-bypass.md)**
  — `TRUST_PROXY: "1"` in `compose.full.yaml` is where the correct value gets
  recorded. This is the setup that makes the setting *testable*.
- **[Vulnerability 09](../vulnerabilities/09.jwt-secret-and-credentials-default-to-placeholders.md)**
  — `${JWT_SECRET:?}` enforces the no-default rule at the orchestration layer too.
- **[Suggestion 15](./15.authorization-test-matrix.md)** — a one-command test
  environment is what makes a large authorization matrix practical to run.
- **No contradiction** with anything; this adds files without changing source.

## What you already got right

- **The application is already twelve-factor compliant** in the way that matters:
  all configuration comes from the environment through one validated schema, so
  containerising it requires **zero source changes**. That is not luck — it is
  what `envHelper.ts` bought you.
- **`DATABASE_URL` and `REDIS_URL` override the discrete host/port variables**, so
  pointing at containers is a two-line `.env` edit.
- **Migrations are file-based and versioned** via `node-pg-migrate` with a
  `pgmigrations` table, so a container can run `migrate:up` on start and it is
  idempotent. That is the piece that makes containerised deployment safe.
- **`db.seed.ts` is fully idempotent** (`ON CONFLICT` on every insert), so
  re-seeding a fresh volume is one command and re-running it is harmless.
- **The Docker design work is already written down** in
  `server/learning_readme/07_docker_implementation_guide.md` and
  `08_docker_infographics.md`, with multistage-build and compose-architecture
  diagrams. The thinking is done; this is the implementation of a plan you
  already made.
- **`server/tests/support/database.ts` and `redis.ts`** exist as test harness
  helpers, which means the test suites are already structured to point at
  configurable infrastructure rather than hardcoded connections.

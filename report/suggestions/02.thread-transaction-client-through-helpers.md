# 02 — Replace the hand-rolled transaction boilerplate with a `withTransaction` wrapper

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **8 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Effort**   | Small — one new file, then a mechanical edit across 15 controllers    |
| **Files**    | 15 controllers under [server/src/controllers/](../../server/src/controllers/), [helper.ts](../../server/src/utils/helper.ts), [db.connect.ts](../../server/src/config/db.connect.ts) |

---

## The pattern today

Fifteen controllers repeat this exact seventeen-line skeleton:

```ts
const client = await pool.connect();
try {
  await client.query("BEGIN");

  // ... 20-80 lines of actual work ...

  await client.query("COMMIT");

  new AppResponse(200, "...", { /* ... */ }).send(res);
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

It is correct in all fifteen — which is genuinely impressive, because the
`finally { client.release() }` is the single most commonly forgotten line in
`node-postgres` code and forgetting it leaks a connection permanently. You never
miss it.

But repeated correctness is fragile correctness. The variations that *have* crept
in are exactly where the bugs are:

- **`createPermission` and `removePermission` have no transaction at all**, so
  their audit writes are non-atomic — [Vulnerability 21](../vulnerabilities/21.non-transactional-audit-writes.md).
- **`assignPermission`, `revokePermission`, `assignRole` and `revokeRole` call
  `checkRolePermissions` before `BEGIN`**, on the bare pool, from inside a block
  that has already checked out a client — [Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md).
- **`deletePost`, `createPost`, `updatePost` and `createPostOnBehalf` call it
  *after* `BEGIN`**, which is worse: a second connection is acquired while the
  first holds a `FOR UPDATE` lock. Ten concurrent requests deadlock the pool.
- **`AppResponse(...).send(res)` is inside the `try` in most controllers** but
  after `COMMIT`, so a serialisation error in the response would trigger a
  `ROLLBACK` on an already-committed transaction. That is a no-op in PostgreSQL,
  but it means the `catch` block can run against a finished transaction — a
  latent confusion, not a bug today.

Every one of these is invisible at the call site. There is nothing about
`await checkRolePermissions(actorId, "delete", "post")` that says "this grabs a
different connection."

## The suggestion

Make the transaction a scope, not a sequence of statements.

```ts
// server/src/config/db.transaction.ts
import type { PoolClient } from "pg";
import { pool } from "./db.connect.ts";

/**
 * Runs `work` inside a single transaction on a single pooled connection.
 *
 * The client is passed to the callback and MUST be used for every query inside
 * it -- reaching for the module-level `pool` from within this callback acquires
 * a second connection while the first is held, which deadlocks the pool under
 * concurrency. See report/vulnerabilities/08.
 *
 * Commits on normal return, rolls back and rethrows on any throw, always
 * releases the connection.
 */
const withTransaction = async <T>(
  work: (client: PoolClient) => Promise<T>,
): Promise<T> => {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const result = await work(client);
    await client.query("COMMIT");
    return result;
  } catch (error) {
    try {
      await client.query("ROLLBACK");
    } catch (rollbackError) {
      // A failed rollback usually means the connection is already broken.
      // Log it, but surface the original error -- that is the useful one.
      console.error("ROLLBACK failed after a transaction error", rollbackError);
    }
    throw error;
  } finally {
    client.release();
  }
};

export { withTransaction };
```

Note two improvements over the current hand-rolled version:

1. **The `ROLLBACK` is itself wrapped.** Today, if the connection has already
   died, `await client.query("ROLLBACK")` throws *inside the catch block* and
   replaces the original error with a misleading connection error. That has
   probably already cost you a debugging session.
2. **The response is sent outside the transaction.** By returning a value rather
   than calling `res.send` inside, the commit is complete before any serialisation
   happens.

### A controller after

```ts
// server/src/controllers/roles/deleteRole.ts
const deleteRole = asyncHandler(async (req, res) => {
  const actorId = parsePositiveInt(req.user.uId, "actorId");
  const roleNameParam = req.params["roleName"];
  if (!roleNameParam) throw AppError.badRequest("Role name is required");

  const deletedRole = await withTransaction(async (client) => {
    await checkRolePermissions(actorId, "delete", "role", client);

    const existing = await client.query(
      `SELECT id, name, description, is_system FROM roles WHERE name = $1 FOR UPDATE`,
      [roleNameParam],
    );
    const existingRole = existing.rows[0];
    if (!existingRole) throw AppError.notFound("Role not found");
    if (existingRole.is_system) throw AppError.forbidden("System roles cannot be deleted");

    await assertCanManageRole(actorId, existingRole, client);

    const deleted = await client.query(
      `DELETE FROM roles WHERE id = $1 RETURNING id, name, description`,
      [existingRole.id],
    );
    if ((deleted.rowCount ?? 0) !== 1) throw AppError.notFound("Role not found");

    await auditDBMutation({
      db: client, actorId, actionType: "delete", resourceType: "role",
      resourceId: deleted.rows[0].id, oldValues: existingRole, newValues: null,
    });

    return deleted.rows[0];
  });

  new AppResponse(200, "Role deleted successfully", { role: toRole(deletedRole) }).send(res);
});
```

Seventeen lines of ceremony replaced by one `withTransaction(async (client) => {`
and a `})`. The `res.send` moves outside, where it belongs.

### Making the misuse impossible

The wrapper alone still lets a helper reach for the global pool. Two mechanical
guards close that:

**Guard 1 — make `db` a required parameter on every helper that touches the
database.** Covered in
[Vulnerability 21](../vulnerabilities/21.non-transactional-audit-writes.md)
(remove `db = pool` from `auditDBMutation`) and
[Vulnerability 08](../vulnerabilities/08.pool-starvation-from-permission-checks-inside-transactions.md)
(add `db` to `checkRolePermissions`). With `strict: true` already enabled,
TypeScript then fails the build at any call site that forgets.

**Guard 2 — an ESLint rule banning direct pool access in controllers.**

```js
// client/eslint.config.js has the equivalent for the frontend; add for server
{
  files: ["src/controllers/**/*.ts"],
  rules: {
    "no-restricted-imports": ["error", {
      paths: [{
        name: "@/config/db.connect.ts",
        importNames: ["pool"],
        message:
          "Controllers must not use the pool directly. Use withTransaction(client => ...) " +
          "for mutations, or accept the pool through a repository. See report/suggestions/02.",
      }],
    }],
  },
}
```

Read-only list controllers (`listUsers`, `listPosts`, …) legitimately have no
transaction. Either exempt them, or — better — give them repositories per
[Suggestion 04](./04.service-layer-and-repositories.md) so no controller imports
`pool` at all.

## Migration plan

1. Add `db.transaction.ts`. Zero behaviour change.
2. Convert one controller (`deleteRole` is a good first — medium complexity, well
   covered by `tests/v2-integration`). Run `pnpm test:v2`.
3. Convert the rest in batches of three, testing between batches.
4. Convert `createPermission` and `removePermission` **last** — they currently
   have no transaction, so this is the one genuine behaviour change (their audit
   writes become atomic, which is the fix for
   [Vulnerability 21](../vulnerabilities/21.non-transactional-audit-writes.md)).
5. Add the required-`db` parameters and the lint rule.

## What you already got right

- **Fifteen out of fifteen transactional controllers release the client in a
  `finally`.** Not one leak. That is the hard-won part of `node-postgres`
  discipline and it is uniformly present.
- **`BEGIN` / `COMMIT` / `ROLLBACK` are always paired correctly**, with the
  rollback in a `catch` that rethrows rather than swallowing. The error
  propagation to `asyncHandler` → `errorHandler` is intact everywhere.
- **`SELECT ... FOR UPDATE` is used before mutating a row** in `deletePost`,
  `updatePost`, `updateUser`, `deleteUser`, `deleteRole`, `updateRole`,
  `revokeSession`, `revokeAllUserSessions`, `registration` and
  `enforceSessionRowCapPerUser`. That is deliberate pessimistic locking applied
  consistently, and it is why this codebase has no lost-update bugs.
- **`QueryableDb = Pick<PoolClient | Pool, "query">`** is exactly the right
  structural type for threading a connection through helpers. The abstraction
  already exists; this suggestion just makes it unavoidable.
- **`registration.ts` uses `SELECT ... FOR UPDATE` on the role row to serialise
  concurrent bootstraps.** That is a genuinely sophisticated use of row locking
  as a distributed mutex, and it is correct.

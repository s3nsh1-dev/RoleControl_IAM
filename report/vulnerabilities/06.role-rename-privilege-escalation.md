## The finding

The entire privilege ordering of the system lives in an in-memory map keyed by
string:

```ts
// server/src/config/hierarchy.ts:12
const ROLE_RANKS: Record<ROLES_TYPES, number> = {
  user: 1, editor: 2, admin: 3, "super-admin": 4,
};
```

Every hierarchy decision resolves through it:

```ts
// server/src/utils/helper.ts:17
function isKnownRoleName(roleName: string): roleName is ROLES_TYPES {
  return roleName in ROLE_RANKS;
}

function canActorManageRole(actorHighestRole: ROLES_TYPES, targetRoleName: string): boolean {
  if (!isKnownRoleName(targetRoleName)) return actorHighestRole === "super-admin";
  if (actorHighestRole === "super-admin") return true;
  if (actorHighestRole === "admin") return targetRoleName === "editor" || targetRoleName === "user";
  return false;
}
```

`getUserRoleNames` reads `roles.name` from the database and *filters out anything
not in the map*:

```ts
// server/src/utils/helper.ts:64
return roleResult.rows
  .map((row) => row.name)
  .filter((roleName): roleName is ROLES_TYPES => isKnownRoleName(roleName));
```

Meanwhile `updateRole` lets you rewrite `roles.name`:

```ts
// server/src/controllers/roles/updateRole.ts:56
const updatedRoleResult = await client.query(
  `UPDATE roles SET name = $1, description = $2 WHERE id = $3 RETURNING id, name, description`,
  [name ?? existingRole.name, description ?? existingRole.description, existingRole.id],
);
```

So the database stores a `user_roles → roles.id` relationship, but the
application derives authority from `roles.name`. **Those two identities can be
made to disagree, and when they do, the name wins.**

## Why it matters

A role's name is a label. Its identity is its id. Deriving authority from the
label means anyone who can edit labels can redistribute authority to existing
grantees — without touching a single `user_roles` row, and without producing an
audit entry that looks like a privilege grant.

The audit trail is the nastiest part. Renaming a role writes:

```json
{ "action_type": "update", "resource_type": "role",
  "old_values": {"id": 2, "name": "editor",  "description": "..."},
  "new_values": {"id": 2, "name": "admin",   "description": "..."} }
```

That reads as a harmless metadata edit. It is in fact a bulk privilege grant to
every holder of role id 2, and nothing in the log says so.

There is a second, non-malicious failure mode that is arguably more likely: an
operator renames a role for cosmetic reasons (`editor` → `content-editor`) and
**silently strips every editor of all authority**, because `isKnownRoleName`
filters the unknown name out and `getHighestUserRole` then returns `null`. Every
controller reacts with `AppError.forbidden("Actor does not have an assigned role")`.
A cosmetic rename becomes an outage.

## Exploit walkthrough

The `name` field is constrained to `RoleNameSchema` (`z.enum(ROLES_LIST)`), so you
cannot rename to an arbitrary string through the API — but you *can* rename to
another **known** role name, which is the dangerous direction.

```bash
# Actor: super-admin. Goal: turn every editor into an admin, quietly.
# There are currently 12 users holding role id 2 ("editor").

curl -X PUT localhost:8000/api/roles/editor \
  -b "access=$SUPER_ADMIN" -H 'Content-Type: application/json' \
  -d '{"name":"admin"}'
# -> 200 {"role":{"id":2,"name":"admin","description":"Content editor access"}}
```

Now there are two rows in `roles` named `admin` — id 2 and id 3 — unless the
`UNIQUE (name)` constraint fires first. It does fire (`23505` → 409 "Record
already exists"), so this exact command fails. Chain it:

```bash
# Step 1: park the real admin role under a free name.
curl -X PUT localhost:8000/api/roles/admin -b "access=$SUPER_ADMIN" \
  -H 'Content-Type: application/json' -d '{"name":"user"}'
# fails too -- "user" is taken.
```

So on a **fully seeded** database with all four names occupied, the `UNIQUE`
constraint accidentally blocks the direct attack. That is luck, not design, and
it evaporates the moment any of these is true:

- A role has been deleted (`deleteRole` allows it — see
  [Vulnerability 12](./12.rbac-self-destruct-via-role-and-permission-deletion.md)),
  freeing its name.
- `CreateRoleRequestSchema`'s `z.enum(ROLES_LIST)` is relaxed to allow custom
  roles — which is the obvious next feature for an RBAC product, and is
  [Suggestion 03](../suggestions/03.database-driven-role-hierarchy.md).
- Anyone writes to `roles` outside the API (a migration, a seed script, psql).

Concretely, on a database where `editor` has been deleted:

```bash
curl -X PUT localhost:8000/api/roles/user -b "access=$SUPER_ADMIN" \
  -H 'Content-Type: application/json' -d '{"name":"editor"}'
# -> 200. Every ordinary user in the system is now an "editor" by rank,
#    with update:user / update:post / update:role, and the audit log
#    records it as a role description edit.
```

## The fix

Stop deriving authority from a mutable string. Two options; take the first.

### Option A (recommended) — put rank in the database, key on id

```sql
-- migrations/<timestamp>_add-role-rank.sql
ALTER TABLE roles ADD COLUMN rank INT NOT NULL DEFAULT 0;
UPDATE roles SET rank = 1 WHERE name = 'user';
UPDATE roles SET rank = 2 WHERE name = 'editor';
UPDATE roles SET rank = 3 WHERE name = 'admin';
UPDATE roles SET rank = 4 WHERE name = 'super-admin';
ALTER TABLE roles ADD CONSTRAINT roles_rank_positive CHECK (rank > 0);

-- Protect the roles the bootstrap flow depends on by identity, not by label.
ALTER TABLE roles ADD COLUMN is_system BOOLEAN NOT NULL DEFAULT FALSE;
UPDATE roles SET is_system = TRUE WHERE name IN ('user', 'super-admin');
```

Then the helpers read rank instead of consulting a map:

```ts
// server/src/utils/helper.ts
type ActorRole = { id: number; name: string; rank: number };

async function getUserRoles(userId: number, db: QueryableDb = pool): Promise<ActorRole[]> {
  const result = await db.query<ActorRole>(
    `SELECT r.id, r.name, r.rank
       FROM user_roles ur JOIN roles r ON r.id = ur.role_id
      WHERE ur.user_id = $1
      ORDER BY r.rank DESC`,
    [userId],
  );
  return result.rows;          // note: no filtering. Unknown roles no longer vanish.
}

async function getHighestUserRole(userId: number, db: QueryableDb = pool) {
  return (await getUserRoles(userId, db))[0] ?? null;
}

// "You may manage roles strictly below your own rank."
function canActorManageRole(actor: ActorRole, target: ActorRole): boolean {
  return actor.rank > target.rank;
}
```

Two behaviour changes worth naming explicitly, because they are improvements you
should *want*:

- `getUserRoleNames` no longer silently drops unknown roles. A renamed or custom
  role keeps working. The "cosmetic rename causes an outage" failure disappears.
- `canActorManageRole` becomes `>` rather than `>=`. Today
  `canActorManageRole("super-admin", "super-admin")` returns `true`, which is why
  one super-admin can demote another (see
  [Vulnerability 11](./11.session-revocation-and-peer-actions-lack-hierarchy-checks.md)).
  Strict `>` is the safer default; if you genuinely want super-admins to manage
  peers, make that an explicit special case rather than a side effect of `>=`.

### Option B (minimum viable) — make names immutable

If you are not ready for the schema change, remove `name` from
`UpdateRoleRequestSchema` entirely so `updateRole` can only edit `description`.
The client already does this — `editRoleSchema` in
[schemas.ts](../../client/src/validation/schemas.ts) only contains `description`
— so the server is strictly more permissive than its own UI. Closing that gap
costs three lines and removes the attack. It leaves the *fragility* (name-keyed
authority) in place, so treat it as a stopgap.

### Either way

Block deletion of system roles:

```ts
// server/src/controllers/roles/deleteRole.ts — after loading existingRole
if (existingRole.is_system) {
  throw AppError.forbidden("System roles cannot be deleted");
}
```

## Interaction with other findings

- **[Suggestion 03](../suggestions/03.database-driven-role-hierarchy.md)** is
  Option A written out in full, with the custom-roles feature it unlocks. If you
  are going to do Suggestion 03 at all, do *not* implement Option B first — you
  would be writing code you immediately delete. **This is a genuine either/or:
  pick one.**
- **[Vulnerability 12](./12.rbac-self-destruct-via-role-and-permission-deletion.md)**
  — the `is_system` column introduced here is the same mechanism that fixes role
  deletion there. Shared solution, no conflict.
- **[Vulnerability 11](./11.session-revocation-and-peer-actions-lack-hierarchy-checks.md)**
  — the `>` vs `>=` change above directly affects peer-management behaviour there.
  Decide the semantics once, in this finding, and let 11 inherit it.
- **[Vulnerability 02](./02.overpermissive-default-user-role.md)** — independent.
  That finding changes *which permissions* a role holds; this one changes *how
  role authority is identified*. They touch the same files but not the same lines.

## What you already got right here

- `roles.name` carries a `UNIQUE` constraint. That constraint is currently the
  only thing standing between you and the direct version of this attack. It was
  the right call for data integrity and it happens to have bought you a lot.
- `updateRole` already checks `canActorManageRole` on **both** the existing name
  *and* the requested new name
  ([updateRole.ts:52-55](../../server/src/controllers/roles/updateRole.ts#L52-L55)).
  You anticipated that a rename is a privilege-relevant operation. The check is
  simply reasoning over the wrong identifier.
- Every role mutation runs inside a transaction with `SELECT ... FOR UPDATE` on
  the role row, so adding a rank column introduces no new concurrency hazards.
- Keeping the hierarchy in one file (`config/hierarchy.ts`) rather than scattering
  `if (role === "admin")` across controllers is why this is a contained,
  three-file fix instead of a rewrite.

## The finding

`userPermissions` is the permission set every single account gets, because
`createUser` always assigns the `user` role in addition to the requested one
([createUser.ts:70-72](../../server/src/controllers/users/createUser.ts#L70-L72)):

```ts
// server/src/config/hierarchy.ts:23
const userPermissions: PermissionType[] = [
  { id: 0,  action: "view", resource: "permission" },
  { id: 1,  action: "view", resource: "role" },
  { id: 2,  action: "view", resource: "user" },
  { id: 3,  action: "view", resource: "post" },
  { id: 4,  action: "create", resource: "post" },
  { id: 20, action: "view", resource: "audit_log" },   // <-- everyone
  { id: 21, action: "view", resource: "session" },     // <-- everyone
  { id: 22, action: "view", resource: "migration" },   // <-- everyone
];
```

And every one of those `view` permissions is checked as a **global** capability,
never scoped to the caller. `listSessions` is representative:

```ts
// server/src/controllers/sessions/listSessions.ts:20
await checkRolePermissions(actorId, "view", "session");
// ... then:
//   SELECT us.id, us.user_id, u.fullname, us.expires_at, us.revoked_at,
//          us.device_info, us.created_at
//     FROM user_sessions us JOIN users u ON u.id = us.user_id
//    ORDER BY us.created_at DESC ...
```

There is no `WHERE us.user_id = $actorId`. `actorId` is used to *authorize* the
call and then discarded. The same pattern appears in `listUserSessions` (which
takes an arbitrary `:userId` from the path and never checks the caller may see
that user), `listAuditLogs`, `listUsers` and `viewUser`.

## Why it matters

A brand-new account with no elevated role — the account you would hand to an
intern, or that any self-registered user would hold in a future version of this
app — can, with four `curl` commands, extract:

| Endpoint | What leaks |
| --- | --- |
| `GET /api/users` | Every account's full name, **email address**, active flag, creation time, creator id, and **complete role list**. That last column is a target map: it tells the attacker exactly which accounts are `super-admin`. |
| `GET /api/sessions` | Every user's session: id, owner, **`device_info` (the raw `User-Agent`)**, creation/expiry times, revocation state. Session ids are the input to `PATCH /api/sessions/:sessionId/revoke`. |
| `GET /api/users/:id/sessions` | The same, targeted at any chosen victim. |
| `GET /api/audit-logs` | The **entire mutation history of the system**, including `old_values` / `new_values` row snapshots for every user create/update/delete, every role assignment, and every permission change. |

The audit log is the worst of these. `auditDBMutation` stores full row snapshots,
and while `sanitizeUserRecord` correctly strips `password`, the snapshots still
contain emails, ids, `created_by` chains and the precise timing of every
privilege grant in the system. An audit log is a *security control*; making it
world-readable to every authenticated principal inverts its purpose — it stops
being a record of who did what and becomes reconnaissance-as-a-service.

Combined, this is a complete privilege-escalation planning kit: identify the
super-admins, learn their user agents and login rhythm from session rows, watch
the audit log for who grants what, and pick a target.

## Exploit walkthrough

```bash
# Any account. No elevated role needed. The base "user" role is enough.
curl -s -b "access=$LOW_PRIV_TOKEN" 'http://localhost:8000/api/users?pageSize=100' \
  | jq '.data.users[] | select(.roleNames[] | contains("super-admin"))'
# -> {"id": 1, "fullname": "...", "email": "root@corp.example", "roleNames":["super-admin","user"]}

curl -s -b "access=$LOW_PRIV_TOKEN" 'http://localhost:8000/api/users/1/sessions'
# -> device_info: "Mozilla/5.0 (Macintosh; ...) Chrome/...", created_at, expires_at

curl -s -b "access=$LOW_PRIV_TOKEN" 'http://localhost:8000/api/audit-logs?pageSize=100'
# -> the entire privilege-grant history of the deployment
```

## The fix

Two layers. The permission *set* is wrong, and the permission *check* is the
wrong shape. Fix both, in this order.

### Layer 1 — split "view mine" from "view all"

`view:session` currently means two different things. Make that explicit rather
than implicit:

```ts
// server/src/config/hierarchy.ts
const userPermissions: PermissionType[] = [
  { id: 0, action: "view",   resource: "permission" },
  { id: 1, action: "view",   resource: "role" },
  { id: 3, action: "view",   resource: "post" },
  { id: 4, action: "create", resource: "post" },
  // A base user may see their own sessions and their own record — those are
  // handled by ownership checks below, not by a global "view" grant.
];

const adminPermissions: PermissionType[] = [
  ...userPermissions,
  { id: 2,  action: "view",   resource: "user" },
  { id: 20, action: "view",   resource: "audit_log" },
  { id: 21, action: "view",   resource: "session" },
  { id: 22, action: "view",   resource: "migration" },
  // ... existing admin entries
];
```

Note this moves `view:user` off the base role too. `editor` currently inherits
`userPermissions`, so decide deliberately whether an editor needs the user
directory; if they do, add `view:user` to `editorPermissions` explicitly rather
than by inheritance.

### Layer 2 — make "view your own" a real, scoped path

The permission check answers *"may this actor perform this verb on this resource
type?"*. It cannot answer *"on this particular row?"*. Add that second question
where rows are owned:

```ts
// server/src/controllers/sessions/listUserSessions.ts
const actorId     = parsePositiveInt(req.user.uId, "actorId");
const targetUserId = parsePositiveInt(req.params["userId"], "userId");

if (actorId !== targetUserId) {
  // Reading someone else's sessions is an administrative act.
  await checkRolePermissions(actorId, "view", "session");
}
// self-lookup needs no extra grant
```

And for the unscoped list, filter rather than authorize-and-dump:

```ts
// server/src/controllers/sessions/listSessions.ts
const canSeeAll = await hasRolePermission(actorId, "view", "session"); // non-throwing variant
const where  = canSeeAll ? "" : "WHERE us.user_id = $3";
const params = canSeeAll ? [limit, offset] : [limit, offset, actorId];
```

This needs a **non-throwing** companion to `checkRolePermissions`, because you now
want to *branch* on a permission rather than abort on it:

```ts
// server/src/utils/helper.ts — add alongside checkRolePermissions
async function hasRolePermission(
  actorId: number,
  action: ACTIONS_TYPES,
  resource: RESOURCES_TYPES,
  db: QueryableDb = pool,
): Promise<boolean> {
  const result = await db.query(
    `SELECT 1 FROM user_roles ur
       JOIN role_permissions rp ON rp.role_id = ur.role_id
       JOIN permissions p ON p.id = rp.permission_id
      WHERE ur.user_id = $1 AND p.action = $2 AND p.resource = $3 LIMIT 1`,
    [actorId, action, resource],
  );
  return (result.rowCount ?? 0) > 0;
}

// checkRolePermissions then becomes a thin throwing wrapper over it
```

`GET /api/audit-logs` and `GET /api/system/migrations` have no meaningful
"own rows" concept — for those, Layer 1 alone is the fix.

**Do not fix this by hiding the nav items on the client.** The client already
does the right thing (`navVisibility.ts` filters by capability), and that is
presentation, not enforcement. The data is one `curl` away regardless.

## Interaction with other findings

- **Suggestion 01** (centralised `requirePermission` middleware) must be designed
  with this in mind: a pure `requirePermission("view", "session")` middleware
  cannot express "or it's your own row". Design the middleware to handle the
  coarse gate and leave ownership checks in the controller, or give it an
  optional `ownershipResolver`. If you build the middleware first without this,
  you will have to rework it.
- **Suggestion 03** (database-driven role hierarchy) changes *where* these
  permission sets live but not *what they should contain* — the split above
  survives that refactor unchanged.
- **Vulnerability 11** (session revocation has no hierarchy check) is the
  write-side twin of this read-side problem. Fix both or an attacker just moves
  one endpoint over.
- **Vulnerability 17** (no authentication audit trail) — once the audit log stops
  being world-readable, it becomes safe to put *more* sensitive events in it.
  Sequence this one first.

## What you already got right here

- `sanitizeUserRecord` is applied consistently before anything reaches an audit
  snapshot or a response DTO. Password hashes never leak. That discipline is the
  reason this finding is "8" and not "10".
- Routing every response through explicit mapper functions
  (`toUserSummary`, `toSession`, …) rather than spreading raw DB rows is exactly
  the right instinct — it is why adding a field to a table cannot accidentally
  publish it.
- The permission model itself (`action` × `resource`, joined through
  `role_permissions`) is a clean, textbook RBAC core. The bug is in the *seeded
  data*, not the *engine* — which is a much better place to have a bug.

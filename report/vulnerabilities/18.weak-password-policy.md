## The finding

The server accepts a **four-character** password everywhere:

```ts
// server/src/contracts/api.contracts.ts
const AuthLoginRequestSchema = z.object({
  email: z.string().trim().email(),
  password: z.string().nonempty().min(4),                    // <-- 4
});

const AuthRegisterRequestSchema = z.object({
  fullname: z.string().trim().min(3).max(150),
  email: z.string().trim().email(),
  password: z.string().nonempty().min(4),                    // <-- 4
});

const UpdateUserRequestSchema = z.object({
  // ...
  oldPassword: z.string().min(4).optional(),
  newPassword: z.string().min(4).optional(),                 // <-- 4
});
```

`CreateUserRequestSchema` extends `AuthRegisterRequestSchema`, so admin-created
accounts inherit the same floor.

The client disagrees with itself and with the server:

```ts
// client/src/validation/schemas.ts
export const loginSchema = z.object({
  email: z.string().trim().email('Enter a valid email address'),
  password: z.string().min(4, 'Password must be at least 4 characters'),     // 4
});

export const registerSchema = z.object({
  fullname: z.string().trim().min(2, ...).max(100, ...),                     // 2/100
  email: z.string().trim().email(...),
  password: z.string().min(8, 'Password must be at least 8 characters'),     // 8
});

export const createUserSchema = registerSchema.extend({ roleName: z.enum(roleNames) });
```

So:

| Rule | Client | Server | Consequence |
| --- | --- | --- | --- |
| Password on register / create user | ≥ 8 | ≥ 4 | Client is stricter — the server is the real, weaker policy |
| Password on login | ≥ 4 | ≥ 4 | Consistent |
| Password on password change | *no client form exists* | ≥ 4 | Unenforced from the UI |
| `fullname` length | 2–100 | 3–150 | **Client accepts a 2-char name the server rejects with a 400**, and rejects a 101–150 char name the server would accept |

The `fullname` row is a live bug, not just an inconsistency: type a two-character
name into the create-user form and it passes client validation, then fails
server-side with a Zod error surfaced as a toast.

### Other gaps

- **No maximum length.** `bcrypt` truncates at 72 bytes, so a 500-character
  password is silently equivalent to its first 72 bytes. Not exploitable (the
  truncation is deterministic and the entropy is already far beyond sufficient),
  but it means the system accepts input it does not fully use, and a very large
  body still costs a bcrypt round. Cap it.
- **No composition or breach checks.** `"1234"`, `"pass"`, and `"aaaa"` are all
  accepted. There is no check against known-breached passwords.
- **No policy sharing.** The client and server schemas are written independently
  even though the project already has a mechanism for sharing contract types
  (`openapi-typescript` generating `client/src/api/schema.ts` from
  `server/openapi/openapi.json`). The generated `AuthRegisterRequest` type carries
  the *shape* but not the *constraints*.

## Why it matters

A four-character password from a 62-character alphabet is about 14.8 million
possibilities. At `SALT_ROUNDS=10` an attacker with the hash needs a few hours on
one GPU. Online, against your live endpoint, the numbers depend entirely on the
rate limiter — which is why this finding compounds so badly with
[Vulnerability 07](./07.rate-limiters-fail-open.md):

| Rate limiter state | Attempts/hour | Time to exhaust a 4-char keyspace |
| --- | --- | --- |
| Working (`5` per email+IP / 15 min) | 20 | Infeasible ✅ |
| **Failing open (Redis unavailable)** | ~150,000 (bcrypt-bound, 4 libuv threads) | **~4 days**, unthrottled and unlogged |

And with a realistic password rather than a random one — `"root"`, `"1234"`,
`"admin"` truncated, or the user's initials — it is the first few hundred guesses,
not the full keyspace.

Note what makes this an IAM-specific problem: a weak password on a super-admin
account is not one compromised account, it is the whole tenant. Combined with
[Vulnerability 02](./02.overpermissive-default-user-role.md) telling an attacker
exactly which account holds `super-admin`, there is no search required.

The client/server divergence has its own cost: the server is the authority, and
here it is the *weaker* of the two. Anyone using the API directly — which the
public OpenAPI spec ([Vulnerability 13](./13.unauthenticated-openapi-and-docs-exposure.md))
documents thoroughly — gets the 4-character policy. The 8-character rule is
decoration.

## The fix

### 1. One password schema, defined server-side, reused everywhere

```ts
// server/src/contracts/api.contracts.ts
/**
 * Minimum 12 characters, no composition rules. Length beats complexity
 * (NIST SP 800-63B §5.1.1.2); complexity rules push users toward `P@ssw0rd1`.
 * Maximum 128 to bound work; bcrypt only consumes the first 72 bytes anyway.
 */
const PasswordSchema = z
  .string()
  .min(12, "Password must be at least 12 characters")
  .max(128, "Password must be 128 characters or fewer")
  .openapi("Password", { example: "correct horse battery staple" });

/** Login accepts any non-empty string -- the policy applies at set time, not at
 *  check time, so users whose passwords predate a policy change can still sign in
 *  (and are then prompted to rotate). */
const PasswordAtLoginSchema = z.string().min(1, "Password is required");

const AuthLoginRequestSchema = z.object({
  email: z.string().trim().email(),
  password: PasswordAtLoginSchema,
});

const AuthRegisterRequestSchema = z.object({
  fullname: FullnameSchema,          // see below
  email: z.string().trim().email(),
  password: PasswordSchema,
});

const UpdateUserRequestSchema = z.object({
  fullname: FullnameSchema.optional(),
  email: z.string().trim().email().optional(),
  oldPassword: PasswordAtLoginSchema.optional(),   // verifying, not setting
  newPassword: PasswordSchema.optional(),          // setting -- full policy
}).refine(/* ... */);
```

The login/set asymmetry is deliberate and matters: applying `min(12)` at login
would lock out every existing user the moment you raise the floor.

### 2. Fix the `fullname` mismatch

```ts
// server/src/contracts/api.contracts.ts
const FullnameSchema = z
  .string().trim()
  .min(3, "Full name must be at least 3 characters")
  .max(150, "Full name must be 150 characters or fewer");
```

Then change the client to match **exactly** (`min(3)`, `max(150)`), not
approximately. `users.fullname` is `VARCHAR(150)`, so 150 is the real ceiling —
the client's 100 was arbitrary and the 2-character minimum was simply wrong.

### 3. Make the client mirror the server, mechanically

```ts
// client/src/validation/schemas.ts
/**
 * These MUST match server/src/contracts/api.contracts.ts. The server is
 * authoritative; these exist only so the user sees an error before a round trip.
 */
const PASSWORD_MIN = 12
const PASSWORD_MAX = 128
const FULLNAME_MIN = 3
const FULLNAME_MAX = 150

export const registerSchema = z.object({
  fullname: z.string().trim().min(FULLNAME_MIN, `Name must be at least ${FULLNAME_MIN} characters`)
                            .max(FULLNAME_MAX, `Name must be ${FULLNAME_MAX} characters or less`),
  email: z.string().trim().email('Enter a valid email address'),
  password: z.string().min(PASSWORD_MIN, `Password must be at least ${PASSWORD_MIN} characters`)
                      .max(PASSWORD_MAX, `Password must be ${PASSWORD_MAX} characters or less`),
})

export const loginSchema = z.object({
  email: z.string().trim().email('Enter a valid email address'),
  password: z.string().min(1, 'Password is required'),     // matches the server
})
```

The durable version of this is
[Suggestion 16](../suggestions/16.openapi-as-contract-source-of-truth.md) —
export the constraint values into the OpenAPI document and generate the client
constants, so the two cannot drift again. The constants above are the cheap
version; do them now, do the generated version when you touch the contract
pipeline.

### 4. Add a breached-password check on set

The highest-value addition per line of code, because it catches the passwords
that are *long enough but still guessed first*:

```ts
// server/src/utils/passwordPolicy.ts
import { createHash } from "node:crypto";

/** k-anonymity lookup: only the first 5 SHA-1 characters leave the process. */
const isBreachedPassword = async (password: string): Promise<boolean> => {
  const sha1 = createHash("sha1").update(password).digest("hex").toUpperCase();
  const [prefix, suffix] = [sha1.slice(0, 5), sha1.slice(5)];
  try {
    const response = await fetch(`https://api.pwnedpasswords.com/range/${prefix}`,
      { signal: AbortSignal.timeout(2000) });
    if (!response.ok) return false;                 // fail open: availability > this check
    return (await response.text()).split("\n").some((line) => line.startsWith(suffix));
  } catch {
    return false;                                    // network failure must not block signup
  }
};
```

Fail-open is the right call here, unlike the rate limiter — a breach check is
advisory, a brute-force limiter is a control. Note the difference in reasoning
against [Vulnerability 07](./07.rate-limiters-fail-open.md); it is deliberate.

If an outbound HTTPS call is unacceptable, ship a bundled top-10,000 wordlist
instead. Either beats nothing.

### 5. Consider `SALT_ROUNDS`

`10` is the current default and is on the low end for 2026 hardware; `12` is the
common recommendation and roughly quadruples the attacker's cost. Raising it is
backward-compatible — bcrypt encodes the cost in the hash, so existing passwords
still verify. Re-hash on next successful login if you want to migrate:

```ts
// after a successful compareHashStrings in login.ts
if (bcrypt.getRounds(user.password) < env.SALT_ROUNDS) {
  const upgraded = await generateHashString(unencryptedPassword);
  await pool.query("UPDATE users SET password = $1 WHERE id = $2", [upgraded, user.id]);
}
```

Measure first — `12` is roughly 4× the CPU of `10`, and bcrypt runs on the libuv
threadpool (4 threads by default), so it directly caps your login throughput.

## Interaction with other findings

- **[Vulnerability 07](./07.rate-limiters-fail-open.md)** — the compounding pair.
  A strong password survives a bypassed rate limiter; a working rate limiter
  survives a weak password. Fixing either helps; fixing both is what closes it.
- **[Vulnerability 15](./15.login-user-enumeration-via-timing.md)** — supplies the
  attacker's target list. Independent fix, compounding benefit.
- **[Vulnerability 04](./04.password-change-does-not-revoke-sessions.md)** —
  raising the floor is only useful if changing a password actually ends the
  attacker's sessions. Fix 04 or a forced rotation accomplishes nothing.
- **[Suggestion 16](../suggestions/16.openapi-as-contract-source-of-truth.md)** —
  step 3's constants are a stopgap for what that suggestion solves properly.
  **Do not build a bespoke shared-validation package**; use the OpenAPI pipeline
  that already exists.
- **Deployment note, not a contradiction:** raising `min(4)` → `min(12)` means
  existing accounts have non-conforming passwords. `PasswordAtLoginSchema`
  handles this (login does not enforce the floor), but you will want a
  `password_changed_at` column and a "your password needs updating" prompt to
  actually migrate people. Plan that before shipping the change, or you will have
  a permanent population of weak passwords that the policy claims cannot exist.

## What you already got right here

- **bcrypt with a per-password salt**, via `genSalt` + `hash` rather than a
  global pepper or a fast hash. The algorithm choice is correct and the
  implementation is the standard one.
- **`SALT_ROUNDS` is configurable** through `envHelper`, so raising the cost is a
  config change, not a code change.
- **Passwords never appear in a response or an audit snapshot.**
  `sanitizeUserRecord` is applied at every boundary, and `updateUser` records only
  `metadata: { passwordChanged: true }` rather than any value. That discipline is
  consistent across fifteen controllers.
- **`compareHashStrings` uses `bcrypt.compare`**, which is constant-time with
  respect to the hash. You did not hand-roll a string comparison.
- **The client validates before submitting** with `react-hook-form` +
  `zodResolver` and `mode: 'onBlur'`, giving immediate feedback. The architecture
  for enforcing a good policy is entirely in place — the numbers in it are just
  too low, and out of step with each other.

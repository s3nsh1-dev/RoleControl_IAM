# 09. `JWT_SECRET` silently defaults to `"placeholder"`, and so do the database credentials

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **7 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Category** | Cryptographic failure / security misconfiguration (OWASP A02, A05)    |
| **Files**    | [envHelper.ts:16-50](../../server/src/utils/envHelper.ts#L16-L50), [.env](../../server/.env), [.gitignore](../../server/.gitignore) |

---

## The finding

`envSchema` gives a default to every secret in the system:

```ts
// server/src/utils/envHelper.ts
DB_USER:     z.string().default("postgres").describe("Database user"),
DB_PASSWORD: z.string().default("password").describe("Database password"),
JWT_SECRET:  z.string().min(1).default("placeholder").describe("JWT secret"),
```

`z.string().min(1).default("placeholder")` is worth reading twice. The `min(1)`
looks like a guard, but the `.default()` runs when the variable is *absent* — so
the validation it is paired with can only ever reject an explicitly-set empty
string. An unset `JWT_SECRET` sails through and the application signs every
access and refresh token in the deployment with the literal string
`"placeholder"`.

There is no environment-aware branch. `NODE_ENV=production` gets the same
defaults as development.

### The secondary issue: the committed `.env`

`server/.env` contains what looks like a real 256-bit secret:

```
JWT_SECRET=64dd638268113c5422de8ce4d0e1897af6f9b719bab61869d0100ec390657a1c
DB_PASSWORD=postgres
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/postgres
```

**Good news, verified:** this file is **not** tracked by git.
`git ls-files` returns nothing for it, and `server/.gitignore` covers `.env`,
`*.env`, and the `.env.*.local` variants. The single commit in this repository
(`7d184f4 project migration`) does not contain it. So this is not a leaked-secret
incident — it is a latent one.

Two things still need attention:

1. **There is no root `.gitignore`.** The ignore rules live in `server/.gitignore`
   and `client/.gitignore`. A `.env` created at the repository root — which is
   exactly where a `docker-compose.yml` would want one, per
   [Suggestion 14](../suggestions/14.docker-compose-and-reproducible-dev-env.md)
   — would be committed.
2. **There is no `.env.example`.** A new contributor has no way to know which
   variables exist without reading `envHelper.ts`, and the defaults mean the app
   *appears* to work when they guess wrong.

## Why it matters

`JWT_SECRET` is the root of trust for the entire authorization system. Anyone who
knows it can mint a token for any `uId` with a valid `iss`/`aud`, and
`checkCookieSignature` will accept it as that user. Combined with
[Vulnerability 02](./02.overpermissive-default-user-role.md) (any account can
list every user and see who holds `super-admin`), the attacker knows exactly
which `uId` to forge.

A default of `"placeholder"` is worse than a weak random secret, because it is
*guessable without any information about the target*. It is in this repository's
source. It will be in any fork, any blog post, any Stack Overflow answer derived
from it. An attacker probing an unfamiliar deployment tries a small dictionary of
known framework defaults, and `"placeholder"` is a one-line addition to that
dictionary.

The failure mode is silent and complete:

```bash
# A deployment where the operator forgot JWT_SECRET, or where the secret
# manager failed to inject it and the container started anyway.
node -e '
const jwt = require("jsonwebtoken");
console.log(jwt.sign({ uId: 1, email: "root@corp.example", type: "access" },
  "placeholder",
  { algorithm: "HS256", issuer: "s3nsh1-dev", audience: "RBAC-users", expiresIn: "20m" }));
'
# Paste as the `access` cookie. You are now user 1 -- the bootstrap super-admin,
# because registration.ts always assigns id-1 the super-admin role.
```

`DB_PASSWORD=password` has the same shape of problem with a smaller blast radius,
since the database is usually not internet-reachable.

## The fix

### 1. No defaults for secrets, and refuse to boot without them

```ts
// server/src/utils/envHelper.ts
const isProduction = process.env["NODE_ENV"] === "production";

const secret = (name: string, minLength: number) => {
  const base = z.string().min(
    minLength,
    `${name} must be at least ${minLength} characters. Generate one with: openssl rand -hex 32`,
  );
  // Development gets a stable, obviously-fake value so `pnpm dev` still works
  // with no setup. Production gets nothing -- it must be supplied.
  return isProduction ? base : base.default(`dev-only-${name.toLowerCase()}-not-for-production`);
};

const envSchema = z.object({
  // ...
  JWT_SECRET: secret("JWT_SECRET", 32),
  DB_PASSWORD: isProduction
    ? z.string().min(1, "DB_PASSWORD is required in production")
    : z.string().default("postgres"),
  // ...
});

const parsed = envSchema.safeParse(process.env);
if (!parsed.success) {
  console.error("Invalid environment configuration:");
  for (const issue of parsed.error.issues) {
    console.error(`  ${issue.path.join(".")}: ${issue.message}`);
  }
  process.exit(1);          // fail fast and loudly, before app.listen
}
const env = parsed.data;
export default env;
```

Two deliberate choices here:

- **`safeParse` + explicit exit** instead of the current bare `envSchema.parse()`.
  Today a missing required variable throws a raw `ZodError` at import time, which
  surfaces as an unhandled rejection with a stack trace and no clear message.
  This prints a readable list of what is wrong.
- **`min(32)`**, not `min(1)`. A 32-character (128-bit) floor makes HS256
  brute-forcing infeasible. The value already in your `.env` is 64 hex characters
  and passes.

### 2. Belt and braces: assert at the point of use

```ts
// server/src/utils/jsonWebTokens.ts (module scope)
if (env.NODE_ENV === "production" && /placeholder|dev-only|changeme|secret/i.test(env.JWT_SECRET)) {
  throw new Error("Refusing to start: JWT_SECRET looks like a placeholder value.");
}
```

Cheap, and it catches the case where someone sets `JWT_SECRET=changeme` to get
past the length check.

### 3. Repository hygiene

Add a root `.gitignore`:

```gitignore
# /.gitignore
node_modules/
dist/
.env
.env.*
!.env.example
*.log
.DS_Store
```

And commit a `server/.env.example` with every key present and every value blank
or obviously fake — it doubles as the documentation that currently does not exist:

```dotenv
# Copy to .env and fill in. Generate secrets with: openssl rand -hex 32
NODE_ENV=development
PORT=8000
TRUST_PROXY=false           # see report/vulnerabilities/22
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/postgres
JWT_SECRET=                 # REQUIRED. Minimum 32 chars. No default in production.
ACCESS_TOKEN_EXPIRES_IN=20m
REFRESH_TOKEN_EXPIRES_IN=7d
REDIS_URL=redis://localhost:6379
# ... rate limit knobs
```

### 4. Rotate, since the value is on disk in plaintext

The secret in `server/.env` has never been committed, but it has lived unencrypted
in a working directory. Before this project is ever deployed anywhere real,
generate a fresh one (`openssl rand -hex 32`). Rotating `JWT_SECRET` invalidates
every issued token, which is exactly the desired behaviour and, incidentally, the
only mechanism that currently exists for mass session termination — see
[Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md).

## Interaction with other findings

- **[Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md)**
  — a known secret makes token forgery trivial, and forged tokens carry any `type`
  claim the attacker wants. Finding 01's fix does not help if the secret is known;
  finding 09's fix does not help if forged-but-correctly-typed tokens bypass
  session checks. They are orthogonal and both required.
- **[Suggestion 13](../suggestions/13.environment-config-and-secret-management.md)**
  is the full version of this: config splitting, per-environment files, secret
  manager integration, and startup validation. This finding is its security core;
  if you do Suggestion 13, this comes with it.
- **[Suggestion 14](../suggestions/14.docker-compose-and-reproducible-dev-env.md)**
  — the root `.gitignore` matters most once a root-level compose file and its
  `.env` exist. Sequence the `.gitignore` **before** the compose work.
- **No contradiction** with any other finding. This one is independently
  shippable in about twenty minutes and is the best effort-to-risk ratio on the
  entire list.

## What you already got right here

- **Centralised, schema-validated config.** One `envHelper.ts` that parses
  `process.env` through Zod and exports a typed object, with every consumer
  importing `env` rather than reaching for `process.env`. Grep confirms zero
  direct `process.env` reads outside this file and the migration entry point.
  That is better discipline than most production codebases, and it means this
  entire fix lands in one file.
- **`.describe()` on every key.** The schema is self-documenting; generating
  `.env.example` from it is nearly mechanical.
- **`z.coerce.number()` for numeric variables** with correct `.int().positive()`
  constraints — the environment gives you strings, and you handled that
  explicitly rather than relying on JavaScript coercion.
- **`.env` is genuinely gitignored, in three overlapping patterns.** You thought
  about this. The gap is only the missing root-level file.
- Separating `DATABASE_URL` (for migration tooling) from the discrete
  `DB_HOST/PORT/USER/...` (for the pool) is a pragmatic call that keeps
  `node-pg-migrate` happy without contorting the application config.

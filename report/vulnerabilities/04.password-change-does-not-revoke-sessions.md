# 04. Changing a password (or having it reset by an admin) leaves every stolen session alive

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **7 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Category** | Broken authentication — credential rotation does not invalidate sessions (OWASP A07) |
| **Files**    | [updateUser.ts:74-113](../../server/src/controllers/users/updateUser.ts#L74-L113) |

---

## The finding

`updateUser` handles password changes correctly as far as *setting* the password
goes:

```ts
// server/src/controllers/users/updateUser.ts:74
let passwordToStore = existingUser.password;
if (newPassword) {
  if (actorId === targetUserId) {
    if (!oldPassword) throw AppError.badRequest("Old password is required to change your password");
    const verifyPassword = await compareHashStrings(oldPassword, existingUser.password);
    if (!verifyPassword) throw AppError.unauthorized("Incorrect password");
  }
  passwordToStore = await generateHashString(newPassword);
}

const updatedUser = await client.query(
  `UPDATE users SET fullname = $1, email = $2, password = $3 WHERE id = $4 RETURNING *`, ...);
```

The transaction commits, an audit entry is written with
`metadata: { passwordChanged: true }`, and the request returns 200.

Nothing touches `user_sessions`.

The same is true for the email change on the line above — changing the account's
identifier does not invalidate anything either.

## Why it matters

"Change your password" is what a user does *because* they think they have been
compromised. It is the one action where the user's mental model is unambiguous:
*this ends the attacker's access.* In this system it does not.

Two concrete scenarios:

**Self-service.** A user suspects their session was stolen on a shared machine.
They log in and change their password. The attacker's `access` cookie keeps
working for up to 20 minutes; the attacker's `refresh` cookie keeps working for
**7 days**, and each refresh mints a fresh 20-minute access token. The password
change accomplished nothing except locking the attacker out of the *login form*
— which they never needed.

**Administrative reset.** Note that when an admin resets someone else's password
(`actorId !== targetUserId`), `oldPassword` is not required — which is correct
behaviour for an admin reset. But it means the highest-urgency case, "reset this
compromised account's credentials right now", is also the case where sessions
most need killing, and it kills none.

This is compounded by [Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md):
even the explicit "Revoke session" button does not stop an access token. So today
there is *no* action available to an operator or a user that terminates an active
compromise, short of deleting the account or rotating `JWT_SECRET` for the whole
deployment.

## Exploit walkthrough

1. Attacker holds a victim's `refresh` cookie.
2. Victim changes their password via the UI. 200 OK, green toast, "User updated".
3. Attacker, 30 minutes later:
   ```bash
   curl -s -b "refresh=$STOLEN_REFRESH" http://localhost:8000/api/auth/refresh
   # -> 200 OK: {"success":true,"message":"Tokens refreshed successfully", ...}
   #    Set-Cookie: access=<new>; refresh=<new rotated>
   ```
   The session row still exists, is not revoked, has not expired, and its
   `refresh_token_hash` still matches. Rotation hands the attacker a *fresh*
   7-day window.
4. Repeat indefinitely. The victim's password is now irrelevant to the attacker's
   access.

## The fix

Add one helper, call it from every credential-invalidating path, inside the
existing transaction.

### The helper

```ts
// server/src/utils/session.util.ts — alongside enforceSessionRowCapPerUser
const revokeAllSessionsForUser = async (
  db: QueryableDb,
  userId: number,
  options: { exceptSessionId?: number } = {},
): Promise<number[]> => {
  const revoked = await db.query<{ id: number }>(
    `UPDATE user_sessions
        SET revoked_at = NOW(),
            expires_at = NOW(),
            refresh_token_hash = 'REVOKED'
      WHERE user_id = $1
        AND revoked_at IS NULL
        AND ($2::int IS NULL OR id <> $2)
      RETURNING id`,
    [userId, options.exceptSessionId ?? null],
  );
  return revoked.rows.map((row) => row.id);
};
```

This deliberately mirrors the `UPDATE` already in
[revokeAllUserSessions.ts:38-46](../../server/src/controllers/sessions/revokeAllUserSessions.ts#L38-L46)
— that controller should be refactored to call this helper too, so there is one
definition of "revoke a session" in the codebase rather than two that can drift.

### Wire it into `updateUser`

```ts
// server/src/controllers/users/updateUser.ts — after the UPDATE users ... query
const credentialsChanged =
  Boolean(newPassword) || (email !== undefined && email !== existingUser.email);

let revokedSessionIds: number[] = [];
if (credentialsChanged) {
  revokedSessionIds = await revokeAllSessionsForUser(client, targetUserId, {
    // A user changing their own password should stay logged in on the device
    // they are currently using. An admin resetting someone else's password
    // should kill everything.
    exceptSessionId: actorId === targetUserId ? req.user.sId : undefined,
  });
}

await auditDBMutation({
  db: client,
  actorId,
  actionType: "update",
  resourceType: "user",
  resourceId: targetUserId,
  oldValues: safeExistingUser,
  newValues: safeUpdatedUser,
  metadata: {
    ...(newPassword ? { passwordChanged: true } : {}),
    ...(credentialsChanged ? { revokedSessionIds } : {}),
  },
});
```

`req.user.sId` is available only once
[Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md)'s
fix adds `sId` to the access-token payload. Until then, pass no exception and
require the user to log in again — slightly worse UX, correct security. Do not
skip the revocation while waiting for finding 01.

### Same treatment for deactivation

When [Vulnerability 03](./03.deactivated-users-can-still-log-in.md)'s `isActive`
field lands, `isActive === false` must call the same helper with no exception.

## The ordering trap

Doing this fix *alone* buys you almost nothing, because revoking a session does
not currently stop an access token. The dependency runs:

```
Vulnerability 01 (session state is checked on every request)
        │
        └──> makes revocation actually work
                    │
                    ├──> Vulnerability 04 (this one) becomes effective
                    ├──> Vulnerability 03 deactivation becomes effective
                    └──> Vulnerability 05 reuse-detection becomes effective
```

Land 01 first, or land them in the same pass. If you land this one in isolation
you will have written correct code that does nothing, which is the worst kind of
security work — it creates the belief that the problem is solved.

## Interaction with other findings

- **Vulnerability 01** — hard prerequisite, as described above. Also supplies the
  `req.user.sId` this fix wants for the "keep my current device" behaviour.
- **Vulnerability 03** — shares `revokeAllSessionsForUser` verbatim.
- **Vulnerability 05** — reuse detection also revokes the session family; it
  should call the same helper so all revocation goes through one code path.
- **Vulnerability 21** (non-transactional audit writes) — note this fix keeps the
  revocation and the audit entry inside the same `client` transaction, which is
  the pattern finding 21 asks you to apply everywhere. Consistent, no conflict.
- **Suggestion 19** (session/device management UX) — once revocation on password
  change works, the client should surface "you were signed out of N other
  devices" rather than silently dropping sessions.

## What you already got right here

- The self-service path correctly demands `oldPassword` and verifies it with
  `compareHashStrings` before accepting `newPassword`. Plenty of tutorials skip
  the re-authentication step entirely.
- Distinguishing "I am changing my own password" from "an admin is resetting
  someone's password" (`actorId === targetUserId`) is exactly the right
  distinction, and you drew it in the right place.
- `oldPassword && !newPassword` is explicitly rejected rather than silently
  ignored — a nice touch that prevents a confusing partial-update.
- The whole update runs in a transaction with `SELECT ... FOR UPDATE` on the
  target row, so the session revocation slots in with no new concurrency
  reasoning required. The structure was already ready for this fix.

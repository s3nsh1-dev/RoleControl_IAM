## The finding

`users.is_active` exists in the schema, is set to `TRUE` on insert, is selected in
`listUsers` and `viewUser`, is part of the `UserSummary` API contract, and is
rendered in the users table on the client.

It is never read by a single authorization or authentication decision.

Grep the whole server for it:

```
src/config/db.setup.ts:28        is_active BOOLEAN NOT NULL DEFAULT TRUE,
src/contracts/api.mappers.ts:55  is_active: Boolean(user["is_active"]),
src/contracts/api.contracts.ts   is_active: z.boolean(),
src/controllers/users/listUsers.ts:28   u.is_active,
src/controllers/users/viewUser.ts:19    SELECT id, fullname, email, is_active, ...
src/controllers/auth/registration.ts:78 INSERT INTO users (..., is_active, ...)
src/controllers/users/createUser.ts:55  INSERT INTO users (..., is_active, ...)
src/models/user.model.ts:26      is_active: z.boolean().default(true)
```

Every hit is a write, a `SELECT` for display, or a type declaration. Zero hits in
`login.ts`, `refreshToken.ts`, or `checkCookieSignature.middleware.ts`.

The login path is:

```ts
// server/src/controllers/auth/login.ts:74
const userInfo = await pool.query("SELECT * FROM users WHERE email = $1", [normalizedEmail]);
if (userInfo.rows.length === 0) { /* ...fail... */ }
const user = userInfo.rows[0];

const isPasswordValid = await compareHashStrings(unencryptedPassword, user.password);
if (!isPasswordValid) { /* ...fail... */ }

// -> straight to session creation. user.is_active is right there in `user`, unused.
```

There is also **no endpoint that can set `is_active` to false.** `updateUser`
accepts `fullname`, `email`, `oldPassword`, `newPassword` and nothing else. So
today the field is not just unenforced — it is unreachable.

## Why it matters

Deactivation is the standard, reversible, audit-friendly way to cut off access:
an employee is suspended pending investigation, a contractor's engagement ends, a
service account is retired. The alternative — `DELETE FROM users` — is
destructive, cascades to `user_roles`, `posts` and `user_sessions`
(`ON DELETE CASCADE`), and nulls out `audit_logs.actor_id` (`ON DELETE SET NULL`),
**destroying the attribution on that user's entire audit history**. That is a
terrible trade to be forced into.

So the practical impact is:

1. There is no way to suspend an account. An operator who needs to must delete it
   and accept the loss of audit attribution, or revoke sessions (which
   [Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md)
   shows does not work either).
2. The UI actively lies. The users table shows an `is_active` column. An operator
   seeing `false` there would reasonably conclude that account cannot log in.
   Nothing in the system makes that true. A security control that *appears* to
   work but does not is worse than an absent one, because it stops people from
   looking for a real solution.

## Exploit walkthrough

There is no clever exploit here — that is the point. If a future `PATCH
/api/users/:id/deactivate` is added (or someone runs
`UPDATE users SET is_active = false WHERE id = 42` directly against the database
during an incident), the deactivated user simply logs in:

```bash
curl -X POST http://localhost:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"suspended@corp.example","password":"..."}'
# -> 200 OK, fresh access + refresh cookies, full role set intact
```

## The fix

Enforce at three points — issue, renew, and use.

### 1. Login

```ts
// server/src/controllers/auth/login.ts — after the password check
if (!user.is_active) {
  // Deliberately the same message and the same failure-counter path as a bad
  // password: do not let an attacker probe which accounts are suspended.
  await registerFailedLoginAttempt();
  throw AppError.unauthorized(INVALID_LOGIN_MESSAGE);
}
```

Placing it *after* `compareHashStrings` is intentional — it keeps the timing
profile identical to a wrong-password attempt (see
[Vulnerability 15](./15.login-user-enumeration-via-timing.md)).

### 2. Refresh

```ts
// server/src/controllers/auth/refreshToken.ts — replace the existing user lookup
const findUser = await pool.query(
  "SELECT id, email, fullname FROM users WHERE id = $1 AND is_active = TRUE",
  [userId],
);
if (!findUser.rowCount) {
  throw AppError.unauthorized("Session is no longer valid. Please login again.");
}
```

### 3. Every authenticated request

This is the one that actually matters, and it is the **same query** already
prescribed in [Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md):

```ts
// server/src/middleware/checkCookieSignature.middleware.ts
const session = await pool.query(
  `SELECT us.id FROM user_sessions us
     JOIN users u ON u.id = us.user_id
    WHERE us.id = $1 AND us.user_id = $2
      AND us.revoked_at IS NULL AND us.expires_at > NOW()
      AND u.is_active = TRUE`,          // <-- this clause is finding 03
  [userPayload.sId, userPayload.uId],
);
```

Without step 3, deactivation only takes effect at the next refresh — up to 20
minutes of continued access, or 7 days via the token-confusion path.

### 4. Give operators a way to actually set it

Extend `UpdateUserRequestSchema` and gate it behind the existing hierarchy check:

```ts
// server/src/contracts/api.contracts.ts
const UpdateUserRequestSchema = z.object({
  fullname:    z.string().trim().min(3).max(150).optional(),
  email:       z.string().trim().email().optional(),
  oldPassword: z.string().min(4).optional(),
  newPassword: z.string().min(4).optional(),
  isActive:    z.boolean().optional(),          // new
}).refine(v => Object.values(v).some(x => x !== undefined),
          { message: "At least one field is required to update a user" });
```

In `updateUser`, reject self-deactivation (`actorId === targetUserId`) the same
way `deleteUser` rejects self-deletion, and **revoke the target's sessions in the
same transaction** when `isActive` flips to `false` — see
[Vulnerability 04](./04.password-change-does-not-revoke-sessions.md) for the
shared helper both paths should call.

## Interaction with other findings

- **Vulnerability 01** — step 3 above is literally one clause of that finding's
  fix. Implement them as one change; splitting them means touching the same
  middleware twice.
- **Vulnerability 04** — deactivation and password-change both need
  "kill this user's live sessions". Write that helper once.
- **Vulnerability 15** — the placement of the `is_active` check (after bcrypt,
  same error message) is chosen to *not* reintroduce an enumeration oracle.
  If you move the check before `compareHashStrings` "for efficiency", you undo
  finding 15's fix. This is the one place these two findings could contradict
  each other; the ordering above resolves it.
- **Suggestion 15** (authorization test matrix) — "deactivated user cannot log in"
  and "deactivated user's in-flight access token stops working" are two of the
  highest-value test cases you could add.

## What you already got right here

- The column is `NOT NULL DEFAULT TRUE`, so there is no tri-state
  `NULL`-means-what ambiguity to reason about. When you add the check, it will
  behave predictably for every existing row.
- It is threaded correctly through the mapper and OpenAPI contract, so the
  moment you enforce it, the client already knows how to display it — no
  contract change needed on that side.
- Modelling deactivation as a flag rather than a `deleted_at` soft-delete is the
  right call for an IAM system, where you want to keep audit attribution intact.
  The design is sound; only the enforcement is missing.

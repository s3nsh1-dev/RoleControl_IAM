# 05. Refresh tokens rotate but stolen-token reuse is never detected

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **7 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Category** | Broken authentication — session fixation / token theft persistence (OWASP A07) |
| **Files**    | [refreshToken.ts:104-135](../../server/src/controllers/auth/refreshToken.ts#L104-L135) |

## The finding

The rotation itself is well built. The update is a compare-and-swap:

```ts
// server/src/controllers/auth/refreshToken.ts:117
const updateRefreshToken = await pool.query(
  `UPDATE user_sessions
      SET refresh_token_hash = $1, expires_at = $2
    WHERE id = $3 AND user_id = $4 AND refresh_token_hash = $5
    RETURNING *`,
  [newRefreshTokenHash, refreshExpirationDate, sessionId, userId, userSession.refresh_token_hash],
);
if (!updateRefreshToken.rowCount || updateRefreshToken.rowCount !== 1) {
  throw AppError.badRequest("Failed to update refresh token");
}
```

The `AND refresh_token_hash = $5` clause means two concurrent refreshes cannot
both succeed. That is genuinely good — it is the hard part, and you got it right.

The problem is what happens on the losing side of that race. When the CAS fails,
the code throws `400 Bad Request` and **stops**. It does not ask the obvious
question: *why did someone present a refresh token that was already rotated away?*

There is exactly one benign answer (a duplicated in-flight request) and one
alarming answer (**someone else has a copy of this token**). The code treats both
identically, and treats neither as a security event.

## Why it matters

Rotation without reuse detection is a *detection* mechanism with the detector
removed. The whole reason to rotate is that rotation makes theft **observable**:
once a token is used twice, exactly one of the two holders is an impostor, and
you cannot tell which — so you must invalidate the family and force a fresh
login. That is the standard answer (OAuth 2 Security BCP, §4.13.2).

Right now, the two possible steal-and-race outcomes are:

| Who refreshes first | Result |
| --- | --- |
| **Attacker first** | Attacker gets a fresh 7-day token pair. The victim's next refresh fails with a confusing `400 Failed to update refresh token`. The victim's client (see below) does **not** clear auth on a 400 — it surfaces a generic error. The victim shrugs, logs in again, gets a *second* session, and the attacker's session continues untouched. |
| **Victim first** | Attacker's stale token fails with 400. Attacker simply stops refreshing and rides out the remaining ~20 minutes of the access token they already hold — or, per [Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md), keeps using the stale refresh token *as* an access token for the full 7 days, because that path never touches `user_sessions` at all. |

In both branches the attacker keeps access and nobody is alerted. The 400 is also
the wrong status: it tells the client "your request was malformed" when the truth
is "your credential is no longer valid, re-authenticate". The client's axios
interceptor only reacts to `401`
([client.ts:76-92](../../client/src/api/client.ts#L76-L92)), so a 400 here does
not trigger the logout-and-redirect path.

## Exploit walkthrough

```bash
# t=0  Attacker has copied the victim's refresh cookie.
#      Both parties now hold the identical token R0.

# t=1  Attacker refreshes first.
curl -s -b "refresh=$R0" localhost:8000/api/auth/refresh
# -> 200. Session row's hash is now bcrypt(sha256(R1)). Attacker holds R1.

# t=2  Victim's client auto-refreshes with R0.
# -> 400 {"success":false,"status":"fail","message":"Failed to update refresh token"}
#    Client shows a generic error. No logout. No alert. No audit entry.
#    The session row is untouched and still belongs to the attacker's R1.

# t=3  Victim logs in again out of confusion.
#      enforceSessionRowCapPerUser caps at 2 rows, so this may even evict
#      an unrelated legitimate session while leaving the attacker's alive.

# t=4..t=7d  Attacker refreshes R1 -> R2 -> R3 ... indefinitely.
```

## The fix

Treat a CAS miss as what it is: proof that two parties hold the same credential.

```ts
// server/src/controllers/auth/refreshToken.ts
// Run the whole refresh inside a transaction so detection and revocation are atomic.
const client = await pool.connect();
try {
  await client.query("BEGIN");

  const sessionResult = await client.query(
    `SELECT id, user_id, refresh_token_hash, expires_at, revoked_at
       FROM user_sessions
      WHERE id = $1 AND user_id = $2
      FOR UPDATE`,                       // serialise concurrent refreshes on this row
    [sessionId, userId],
  );
  const userSession = sessionResult.rows[0];
  if (!userSession) throw AppError.unauthorized("Session is no longer valid. Please login again.");

  // --- Reuse detection -------------------------------------------------
  // A revoked session being presented again, or a token that does not match the
  // current hash, both mean this credential has been replayed.
  const tokenMatches =
    userSession.revoked_at === null &&
    (await compareTokenHash(oldRefreshToken, userSession.refresh_token_hash));

  if (!tokenMatches) {
    // We cannot tell the legitimate holder from the thief. Kill the family.
    const revokedIds = await revokeAllSessionsForUser(client, userId);

    await auditDBMutation({
      db: client,
      actorId: userId,
      actionType: "revoke",
      resourceType: "session",
      resourceId: sessionId,
      metadata: {
        reason: "refresh_token_reuse_detected",
        revokedSessionIds: revokedIds,
        ip: getTrustedClientIp(req),
        userAgent: req.get("user-agent") ?? null,
      },
    });

    await client.query("COMMIT");
    clearAuthCookies(res);
    throw AppError.unauthorized("Session is no longer valid. Please login again.");
  }
  // ---------------------------------------------------------------------

  if (userSession.expires_at < new Date()) {
    throw AppError.unauthorized("Session expired");
  }

  // ... mint + persist the new pair as before, but on `client` not `pool` ...
  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

Four things changed, each load-bearing:

1. **`FOR UPDATE`** replaces the optimistic CAS. Concurrent refreshes now block
   rather than race, so a genuine double-submit from one client serialises
   instead of tripping the detector. Keep the `AND refresh_token_hash = $5`
   clause on the `UPDATE` as a belt-and-braces check if you like — it becomes
   redundant but harmless.
2. **Mismatch ⇒ revoke the whole family**, via the shared
   `revokeAllSessionsForUser` helper from
   [Vulnerability 04](./04.password-change-does-not-revoke-sessions.md).
3. **Audit the event.** This is the highest-signal security event your system can
   produce and it currently produces nothing. See
   [Vulnerability 17](./17.no-authentication-audit-trail.md).
4. **`401`, not `400`.** This makes the client's existing interceptor do the right
   thing — clear auth, redirect to `/login` — with no client change required.

### The idempotency caveat you must decide on

Strict reuse detection will occasionally log out an honest user: two browser tabs
refreshing simultaneously, or a mobile client retrying on a flaky network. The
`FOR UPDATE` above fixes the *simultaneous* case (the second request blocks, then
sees the new hash — which is still a mismatch). If false logouts prove annoying,
the standard mitigation is a short grace window:

```sql
ALTER TABLE user_sessions ADD COLUMN previous_token_hash VARCHAR(255);
ALTER TABLE user_sessions ADD COLUMN previous_token_expires_at TIMESTAMPTZ;
```

On rotation, store the old hash with a ~10 second expiry. A token matching
`previous_token_hash` *within* that window is a benign retry — return the
already-issued current token instead of rotating again. A match *outside* the
window, or a match against neither, is reuse. Pick one behaviour and document it;
do not leave it ambiguous.

## Interaction with other findings

- **Vulnerability 01** is a hard prerequisite. Without session-state checking on
  every request, revoking the family still leaves the thief's *access* token —
  and their stale refresh token used as an access token — fully working. Reuse
  detection with no enforcement is theatre.
- **Vulnerability 04** — shares `revokeAllSessionsForUser`. Write it once.
- **Vulnerability 17** — the reuse-detection audit entry is the flagship example
  of the authentication events that finding asks for.
- **Vulnerability 19** (double rate-limit consumption) — unrelated, but note this
  fix adds a transaction to the refresh path, so if you also fix
  [Vulnerability 08](./08.pool-starvation-from-permission-checks-inside-transactions.md)
  (pool starvation) make sure the refresh transaction does not call any helper
  that grabs a second pool connection. It currently does not; keep it that way.
- **Contradiction to watch:** the `MAX_SESSION_ROWS_PER_USER = 2` cap in
  [login.ts:33](../../server/src/controllers/auth/login.ts#L33) interacts badly
  with family revocation — after a reuse event the user logs in again and may
  evict a legitimate third-device session. See
  [Suggestion 19](../suggestions/19.session-cap-and-device-management.md); raise
  the cap and make eviction explicit rather than silent.

## What you already got right here

- **Rotation on every refresh.** Many projects issue a long-lived refresh token
  once and never rotate. You rotate, which is the prerequisite for detection.
- **The compare-and-swap `WHERE` clause.** This is the piece people get wrong. You
  independently arrived at an optimistic-concurrency guard that makes double-spend
  impossible. The fix above only upgrades it to pessimistic locking so you can
  *react* to the collision rather than just survive it.
- **Hashed storage with a sha256 pre-hash before bcrypt**
  ([encryptStrings.ts:31-40](../../server/src/utils/encryptStrings.ts#L31-L40)).
  The pre-hash sidesteps bcrypt's 72-byte truncation on long JWTs — that is a
  subtle detail and you handled it correctly.
- The session row is checked for `revoked_at` and `expires_at` *before* the token
  comparison. The ordering is right; it just needs the mismatch branch to do more.

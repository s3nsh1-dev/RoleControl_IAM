# 16. The client's `isAuthenticated` flag lives in `localStorage` and can be forged

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **4 / 10**                                                            |
| **Side**     | **Client**                                                            |
| **Category** | Client-side trust boundary confusion (defence-in-depth, not a direct breach) |
| **Files**    | [store/auth.ts](../../client/src/store/auth.ts), [ProtectedRoute.tsx](../../client/src/components/ProtectedRoute.tsx), [client.ts:86-91](../../client/src/api/client.ts#L86-L91) |

## The finding

The auth store persists a boolean to `localStorage`:

```ts
// client/src/store/auth.ts
export const useAuthStore = create<AuthState>()(
  persist(
    (set) => ({
      isAuthenticated: false,
      setAuthenticated: (isAuthenticated = true) => set({ isAuthenticated }),
      clearAuth: () => set({ isAuthenticated: false }),
    }),
    { name: 'rbac-auth-session', partialize: (s) => ({ isAuthenticated: s.isAuthenticated }) },
  ),
);
```

Anyone can set it:

```js
// devtools console, on any origin serving this app
localStorage.setItem('rbac-auth-session',
  JSON.stringify({ state: { isAuthenticated: true }, version: 0 }));
```

## Why this is only a 4, and what the real issue is

I want to be exact about this one, because it is easy to write it up as
"client-side auth bypass" and be wrong.

**It is not a bypass.** `ProtectedRoute` — the component that actually decides
whether the app shell renders — does **not** read `isAuthenticated`:

```ts
// client/src/components/ProtectedRoute.tsx
const authMe = useAuthMe();                       // server call: GET /api/auth/me
const isUnauthorized = authMe.error instanceof ApiClientError && authMe.error.statusCode === 401;

useEffect(() => { if (authMe.data) setAuthenticated(); }, [authMe.data, setAuthenticated]);
useEffect(() => { if (isUnauthorized) clearAuth(); }, [clearAuth, isUnauthorized]);

if (authMe.isLoading)   return <SkeletonRows rows={3} />;
if (isUnauthorized)     return <Navigate to="/login" replace />;
if (authMe.isError)     return <QueryErrorState ... />;
if (!authMe.data)       return <Navigate to="/login" replace />;
return children;
```

The gate is `authMe.data` — the server's answer. The store is written *to* by
this component and never read by it. Forging the flag renders nothing and grants
nothing; `GET /api/auth/me` still returns 401 and the redirect still fires. The
same is true of capabilities: `useCapabilities` derives `can()` from
`authMe.data.capabilities`, which comes from the server on every load, so no
button can be unlocked by editing storage either.

**So what is the actual problem?** The store is a **vestigial parallel source of
truth** that has no readers but three writers, and it is persisted across
sessions. That combination is a bug waiting to be introduced:

1. **It survives logout in one path.** `AppShell`'s logout mutation calls
   `clearAuth()` in `onSettled`, so the normal path is clean. But the axios
   interceptor's failure branch does:

   ```ts
   // client/src/api/client.ts:88
   } catch {
     useAuthStore.getState().clearAuth();
     window.location.assign("/login");
   }
   ```

   `window.location.assign` triggers a full page navigation. Zustand's `persist`
   middleware writes to `localStorage` synchronously on `set`, so this specific
   ordering does happen to flush — but it is a race that depends on
   implementation details of the persistence layer, not on anything guaranteed.

2. **It is a stale-value trap for the next feature.** The natural next step for
   any developer is *"show a skeleton instead of a flash of the login page on
   reload — we already have `isAuthenticated` persisted, use that."* At that
   moment the forgeable flag becomes load-bearing for what renders, and the
   finding graduates from 4 to a genuine (if still cosmetic) bypass. The value of
   fixing it now is that it removes the trap.

3. **It is a small privacy leak on shared machines.** `rbac-auth-session:
   {"state":{"isAuthenticated":true}}` persists in the browser profile after the
   cookies have expired, telling anyone who opens devtools that this machine was
   used to sign into an IAM console.

4. **Nothing verifies the persisted shape.** A malformed or hand-edited
   `rbac-auth-session` value is fed straight into the store. Today the resulting
   `undefined` is harmless; with a reader it would not be.

## The fix

The honest fix is to delete the persistence, because the state it persists is
already authoritatively available from the server on every page load.

### Option A (recommended): stop persisting

```ts
// client/src/store/auth.ts
import { create } from 'zustand'

type AuthState = {
  isAuthenticated: boolean
  setAuthenticated: (isAuthenticated?: boolean) => void
  clearAuth: () => void
}

/**
 * In-memory only. The authoritative answer to "is this user signed in" is the
 * server's response to GET /api/auth/me, which ProtectedRoute consumes directly.
 * This store exists so non-routing components can react to sign-out without
 * subscribing to the query; it must never be persisted, because a value the
 * user can edit must never influence what renders.
 */
export const useAuthStore = create<AuthState>((set) => ({
  isAuthenticated: false,
  setAuthenticated: (isAuthenticated = true) => set({ isAuthenticated }),
  clearAuth: () => set({ isAuthenticated: false }),
}))
```

Three lines removed, plus a comment that stops someone re-adding it. Behaviour is
identical — verify by checking that `ProtectedRoute.test.tsx` and
`AppShell.test.tsx` still pass, since neither asserts on persistence.

### Option B: if you want the reload UX, do it without trusting the client

The reason someone would want persistence is to avoid a flash of the login screen
while `/api/auth/me` is in flight. Solve that properly with React Query's
persistence, seeding the cache with the *server's* last answer and letting the
network call revalidate it:

```ts
// client/src/main.tsx
const queryClient = new QueryClient({
  defaultOptions: {
    queries: { retry: 1, staleTime: 20_000, retryOnMount: false },
    mutations: { retry: 1 },
  },
})
```

The important property either way: **the cached value must be treated as a
rendering hint that the server immediately overrides, never as a gate.** If you
adopt Option B, `ProtectedRoute` must still block on `authMe.data`; the cache only
changes *what is shown during the loading state*.

### Also: clear the cache thoroughly on logout

`AppShell` already calls `queryClient.clear()` in `onSettled`, which is right. The
interceptor's 401 path does not:

```ts
// client/src/api/client.ts
} catch {
  useAuthStore.getState().clearAuth();
  queryClient.clear();              // <-- add: drop cached user/session/audit data
  window.location.assign("/login");
}
```

This needs the `queryClient` to be importable outside React — export the instance
from a module rather than constructing it inline in `main.tsx`. See
[Suggestion 11](../suggestions/11.react-query-cache-hardening.md).

## What you already got right here

- **`ProtectedRoute` gates on the server's answer, not on local state.** This is
  the single decision that keeps this finding at a 4. Many React dashboards gate
  on a persisted `isLoggedIn` boolean and are genuinely bypassable in the UI.
  Yours is not.
- **No token is ever stored client-side.** The only credentials are `httpOnly`
  cookies the JavaScript cannot read. `grep -rn "localStorage" client/src`
  returns exactly two files: this store and the theme hook. That is a
  deliberately small storage footprint.
- **`partialize`** correctly restricts what gets persisted to a single field
  rather than serialising the whole store. If persistence is kept, this is the
  right way to do it.
- **Capabilities come from the server on every load** and drive both nav
  visibility (`navVisibility.ts`) and per-page guards (`AccessDenied`). The client
  never invents an authorization answer — it only renders one the server gave it.
  That is the correct division of responsibility and it is consistent across
  every page.
- The 401 interceptor calls `clearAuth()` before redirecting, so the flag does
  not survive a server-side session expiry in the normal case. The gap is a
  narrow ordering concern, not a missing intent.

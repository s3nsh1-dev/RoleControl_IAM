# 13. `/api/docs` and `/api/openapi.json` are public and sit in front of every rate limiter

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **5 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Category** | Information disclosure / security misconfiguration (OWASP A05)        |
| **Files**    | [app.ts:53-72](../../server/src/app.ts#L53-L72)                        |

---

## The finding

Look carefully at the middleware order in `app.ts`:

```ts
// server/src/app.ts:53
app.get("/", (_req, res) => { res.send("Hello World"); });          // public

app.get("/api/openapi.json", (_req, res) => { res.json(openApiDocument); });  // public

app.use("/api/docs", swaggerUi.serve, swaggerUi.setup(openApiDocument, {
  explorer: true,
  swaggerOptions: { persistAuthorization: true, displayRequestDuration: true },
  customSiteTitle: "RoleControl IAM API Docs",
}));                                                                 // public

app.use("/api/auth", authExemptRouter);        // login + refresh, own limiters
app.use("/api", globalRateLimiting);           // <-- everything ABOVE bypasses this
app.use("/api/auth", authProtectedRouter);
app.use("/api/users", userRouter);
// ... etc
```

Three consequences follow from that ordering:

1. **No authentication.** Neither the JSON document nor the Swagger UI page is
   behind `checkCookieSignature`.
2. **No rate limiting.** `globalRateLimiting` is mounted at line 72, *after* the
   docs routes. Requests to `/api/openapi.json` and `/api/docs` never touch it —
   nor do they touch any per-IP or per-user limiter, because those live on the
   routers mounted below.
3. **`/` returns `"Hello World"`**, unauthenticated and unlimited, which is a
   free unauthenticated liveness probe for anyone scanning.

`openApiDocument` is built at import time from the Zod contracts, so it is a
complete, accurate description of all ~30 endpoints — paths, methods, path and
query parameter shapes, request body schemas, response schemas, the
`accessCookieAuth` / `refreshCookieAuth` security scheme definitions, and the
full `CapabilityKey` enum.

## Why it matters

The severity here is moderate and I want to be precise about why, because it is
easy to overstate.

**What this is not:** publishing an API specification is not itself a
vulnerability. Every public API does it. Obscurity is not a control, and if the
endpoints below are correctly authorized then knowing their shapes buys an
attacker very little.

**What this actually costs you, in order of importance:**

1. **The unlimited endpoints are the real problem.** `/api/openapi.json`
   serialises a large object graph to JSON on every request, with no caching, no
   `ETag`, and no rate limit whatsoever. That is a cheap amplification target: a
   single machine can pin CPU on the API process with a plain `while true; do
   curl` loop, and no counter anywhere will register it. The same applies to the
   Swagger UI asset serving. This is the part worth fixing first.

2. **It hands over the internal capability model.** The
   [`CapabilityKey` enum](../../server/src/contracts/api.contracts.ts) enumerates
   every privilege the system recognises — `users.delete`, `sessions.revoke`,
   `rolePermissions.assign`, `posts.createOnBehalf` — as does the
   `PermissionAction` × `PermissionResource` matrix. Combined with
   [Vulnerability 02](./02.overpermissive-default-user-role.md), an attacker with
   any low-privilege account has both the map (from the spec) and the territory
   (from the over-permissive reads). Neither alone is fatal; together they remove
   all the guesswork.

3. **It advertises the undocumented parts of the design.** The spec shows
   `POST /api/auth/register` with its bootstrap semantics, exposing that this
   deployment has a self-registration door whose availability depends on database
   state — see [Vulnerability 14](./14.auth-router-is-not-actually-protected.md).

4. **Swagger UI is unmonitored third-party attack surface.** It is a large
   JavaScript bundle rendering schema content, served with no CSP
   ([Vulnerability 10](./10.no-security-headers-no-cors-policy-and-cookie-flags.md)),
   at a path nobody watches. `persistAuthorization: true` also tells the browser
   to persist credentials entered into the "Authorize" dialog into `localStorage`
   — harmless for cookie auth, but a footgun if a bearer scheme is ever added.

## Exploit walkthrough

```bash
# No credentials. Full API surface.
curl -s localhost:8000/api/openapi.json | jq -r '.paths | keys[]'
# /api/audit-logs
# /api/auth/login
# /api/auth/logout
# /api/auth/me
# /api/auth/refresh
# /api/auth/register
# /api/permissions
# ... every route

curl -s localhost:8000/api/openapi.json \
  | jq -r '.components.schemas.CapabilityKey.enum[]'
# users.view, users.create, users.delete, sessions.revoke, sessions.delete, ...

# And the unlimited part -- note the absence of any 429:
for i in $(seq 1 2000); do curl -s -o /dev/null localhost:8000/api/openapi.json; done
# 2000/2000 succeed. The global limiter (100/min/IP) is mounted below this route.
```

## The fix

Three changes, in order of value.

### 1. Move the rate limiter above the docs (the important one)

```ts
// server/src/app.ts
app.use(express.json({ limit: "100kb" }));
app.use(express.urlencoded({ extended: true, limit: "100kb" }));
app.use(cookieParser());

// Rate limiting comes FIRST, so nothing under /api can bypass it.
app.use("/api", globalRateLimiting);

// Auth routes keep their own stricter limiters on top of the global one.
app.use("/api/auth", authExemptRouter);
app.use("/api/auth", authProtectedRouter);
// ... the rest
```

Be aware this is a behaviour change: `/api/auth/login` and `/api/auth/refresh`
currently sit *above* `globalRateLimiting` and so are exempt from the 100/min/IP
budget. Moving the limiter up means a login now consumes a global token in
addition to its own login-specific token. That is almost certainly what you want
— a login flood should count against the global budget — but check
`RATE_LIMIT_GLOBAL_IP_LIMIT=100` is high enough not to interfere with normal
usage, and update the v4 rate-limit tests accordingly.

### 2. Gate the docs by environment, and authenticate them in production

```ts
// server/src/utils/envHelper.ts
ENABLE_API_DOCS: z
  .enum(["true", "false"])
  .default("true")
  .describe("Serve Swagger UI and the OpenAPI document"),
```

```ts
// server/src/app.ts
const docsEnabled =
  env.ENABLE_API_DOCS === "true" && env.NODE_ENV !== "production";

if (docsEnabled) {
  app.get("/api/openapi.json", (_req, res) => {
    res.setHeader("Cache-Control", "public, max-age=300");
    res.json(openApiDocument);
  });
  app.use("/api/docs", swaggerUi.serve, swaggerUi.setup(openApiDocument, {
    explorer: true,
    swaggerOptions: { persistAuthorization: false, displayRequestDuration: true },
    customSiteTitle: "RoleControl IAM API Docs",
  }));
}
```

If you want the docs in production — a reasonable choice for an internal admin
tool — put them behind the existing auth middleware instead of disabling them:

```ts
app.use("/api/docs", checkCookieSignature, authenticatedRateLimiting,
  swaggerUi.serve, swaggerUi.setup(openApiDocument, { /* ... */ }));
```

Note `persistAuthorization: false` — with cookie auth it does nothing useful, and
it removes a future footgun.

### 3. Replace `"Hello World"` with a real health endpoint

```ts
app.get("/healthz", (_req, res) => {
  res.json({ status: "ok", uptime: process.uptime() });
});
```

Serves the same "is it up" purpose, is the conventional path load balancers
expect, and is the natural place to surface the "rate limiters are degraded"
signal from [Vulnerability 07](./07.rate-limiters-fail-open.md). Full design in
[Suggestion 07](../suggestions/07.health-readiness-and-graceful-shutdown.md).

## Interaction with other findings

- **[Vulnerability 07](./07.rate-limiters-fail-open.md)** — change 1 here puts
  *more* traffic through the limiter, which makes that finding's fail-open
  behaviour matter more. Fix both; ordering is flexible but do not do 13 alone
  and conclude rate limiting is now airtight.
- **[Vulnerability 10](./10.no-security-headers-no-cors-policy-and-cookie-flags.md)**
  — the CSP defined there is what constrains Swagger UI if you keep it. If you
  disable docs in production per change 2, the CSP's `'unsafe-inline'` style
  allowance can be dropped, which is strictly better. **Decide change 2 before
  writing the CSP** so you do not loosen it unnecessarily.
- **[Suggestion 07](../suggestions/07.health-readiness-and-graceful-shutdown.md)**
  — change 3 is the seed of that suggestion. Implement it there in full rather
  than twice.
- **[Suggestion 16](../suggestions/16.openapi-as-contract-source-of-truth.md)** —
  that suggestion makes the OpenAPI document *more* central, not less. It does
  not conflict: the client consumes the spec at **build** time via
  `openapi-typescript` against the checked-in `server/openapi/openapi.json`, not
  at runtime over HTTP. Disabling the runtime endpoint in production breaks
  nothing in the client build.

## What you already got right here

- **The spec is generated, not hand-written.** `zod-to-openapi` derives it from
  the same Zod schemas the controllers validate against, so the documentation
  cannot drift from the implementation. That is the correct architecture and it
  is why [Suggestion 16](../suggestions/16.openapi-as-contract-source-of-truth.md)
  is an easy win rather than a rewrite.
- **Security schemes are declared per-route.** `protectedRouteSecurity` and
  `refreshRouteSecurity` are attached to the right operations, and the exempt
  routes correctly carry none. The spec accurately describes the auth model.
- **`server/openapi/openapi.json` is exported to disk** via `openapi:export`, and
  the client generates types from that file. The runtime endpoint is a
  convenience, not a dependency — which is precisely why it is safe to turn off.
- The docs route is mounted before the routers rather than tangled among them,
  so this fix is a matter of moving three lines.

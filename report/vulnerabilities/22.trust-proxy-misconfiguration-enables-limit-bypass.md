# 22. `TRUST_PROXY` is a free-text string with no validation, and getting it wrong breaks every IP-keyed limiter

## The finding

`parseTrustProxy` accepts anything and falls through to passing the raw string to
Express:

```ts
// server/src/app.ts:22
const parseTrustProxy = (value: string) => {
  const normalizedValue = value.trim().toLowerCase();
  if (normalizedValue === "true")  return true;
  if (normalizedValue === "false") return false;

  const numericValue = Number(normalizedValue);
  if (Number.isInteger(numericValue) && numericValue >= 0) return numericValue;

  return value;                       // <-- anything else, unvalidated
};

app.set("trust proxy", parseTrustProxy(env.TRUST_PROXY));
```

The schema is equally permissive:

```ts
// server/src/utils/envHelper.ts:58
TRUST_PROXY: z.string().default("false").describe("Express trust proxy setting"),
```

Three IP-keyed rate limiters depend on the result being right:

```ts
// server/src/utils/rateLimit.util.ts:70
const getTrustedClientIp = (req: Request) => {
  if (!req.ip) throw AppError.badRequest("User IP not found");
  return normalizeIpForRateLimit(req.ip);
};
```

`req.ip` is *derived* from `trust proxy`. With `trust proxy` enabled, Express
takes the client address from the `X-Forwarded-For` header — a value the client
fully controls.

**The current default is `false`, which is the safe value.** This finding is not
"you are vulnerable today"; it is "the one deployment change every production
rollout requires is the change that silently breaks these controls, and nothing
in the code will tell you."

## Why it matters

Two failure modes, and every deployment lands in one of them.

### Failure mode A: `TRUST_PROXY=false` behind a proxy (the availability failure)

TLS termination means an nginx, Caddy, ALB, or Cloudflare in front. Every request
then arrives at Express from the proxy's address. With `trust proxy` false,
`req.ip` is that single address for **all** traffic, so:

- `rate:global:ip:10.0.0.5` — one bucket for the entire internet.
- `RATE_LIMIT_GLOBAL_IP_LIMIT=100` per minute becomes a **global** cap of 100
  requests per minute across all users.
- `rate:login:ip:10.0.0.5` — 20 logins per 15 minutes for everyone combined.

The application is effectively offline under any real traffic, and the symptom
(`429 Too many requests`) points at the rate limiter rather than at the proxy
configuration.

### Failure mode B: `TRUST_PROXY=true` (the security failure)

`true` means "trust the leftmost entry in `X-Forwarded-For`, however many hops
claim to exist." Express walks the chain and, with `true`, will accept a
client-supplied value. Every IP-keyed limiter becomes keyed on an
attacker-chosen string:

```bash
# One request per "IP", unlimited attempts, from a single machine.
for i in $(seq 1 100000); do
  curl -s -X POST https://target/api/auth/login \
    -H "X-Forwarded-For: 203.0.113.$((RANDOM % 254 + 1))" \
    -H 'Content-Type: application/json' \
    -d '{"email":"admin@corp.example","password":"guess'"$i"'"}'
done
```

Three of the four protections evaporate:

| Limiter | Key | Bypassable with a forged header? |
| --- | --- | --- |
| `rate:global:ip:<ip>` | client IP | ✅ Yes |
| `rate:login:ip:<ip>` | client IP | ✅ Yes |
| `rate:refresh:ip:<ip>` | client IP | ✅ Yes |
| `rate:login:fail:email-ip:<sha256(email\|ip)>` | email **+** IP | ✅ Yes — the IP is half the key |
| `rate:user:<uId>` | authenticated user id | ❌ No — keyed on the JWT |

Note the last row. The per-user limiter is the only one that cannot be spoofed,
and it only applies *after* authentication. Every pre-auth control is IP-keyed.

Combined with [Vulnerability 18](./18.weak-password-policy.md) (4-character
minimum) and [Vulnerability 15](./15.login-user-enumeration-via-timing.md)
(target list), a spoofable limiter is the last thing standing between an attacker
and unlimited online guessing.

### The third mode: an invalid value fails silently

`TRUST_PROXY=yes`, `TRUST_PROXY=1,2`, or a typo like `TRUST_PROXt` reaches
`return value` and is handed to Express, which interprets an unrecognised string
as a subnet specifier. An unparseable one may throw at startup or, worse, produce
undefined trust behaviour. Nothing validates it and nothing logs the effective
setting.

## The fix

### 1. Validate the value and default to the safe one

```ts
// server/src/utils/envHelper.ts
const TRUST_PROXY_PRESETS = ["false", "true", "loopback", "linklocal", "uniquelocal"] as const;

TRUST_PROXY: z
  .string()
  .default("false")
  .refine(
    (value) => {
      const v = value.trim().toLowerCase();
      if ((TRUST_PROXY_PRESETS as readonly string[]).includes(v)) return true;
      if (/^\d+$/.test(v)) return true;                             // hop count
      // Comma-separated IPs or CIDR blocks.
      return v.split(",").every((entry) =>
        /^[0-9a-f.:]+(\/\d{1,3})?$/i.test(entry.trim()));
    },
    {
      message:
        "TRUST_PROXY must be 'false', a hop count (e.g. '1'), a preset " +
        "('loopback' | 'linklocal' | 'uniquelocal'), or a comma-separated list of proxy IPs/CIDRs.",
    },
  )
  .describe("Express trust proxy setting. Use the smallest value that is correct for your topology."),
```

### 2. Reject `true` in production

`true` is never the right answer for a deployment. It means "trust an unbounded
chain", which is precisely what an attacker exploits.

```ts
// server/src/app.ts
const trustProxySetting = parseTrustProxy(env.TRUST_PROXY);

if (env.NODE_ENV === "production" && trustProxySetting === true) {
  throw new Error(
    "TRUST_PROXY=true is unsafe in production: it trusts a client-supplied " +
    "X-Forwarded-For chain of any length, letting callers forge their IP and " +
    "bypass every IP-keyed rate limiter. Set it to the exact number of proxies " +
    "in front of this service (usually '1'), or to their IP addresses.",
  );
}

app.set("trust proxy", trustProxySetting);
console.log(`[startup] trust proxy = ${JSON.stringify(trustProxySetting)}`);
```

Refusing to boot is deliberate. A misconfigured trust setting is not a warning —
it disables your pre-auth defences, and a warning in a log nobody reads is
indistinguishable from silence.

### 3. Pick the right value per topology

| Deployment | Correct value | Why |
| --- | --- | --- |
| Local development, direct to Node | `false` | No proxy exists |
| One nginx / Caddy on the same host | `1` | Trust exactly one hop |
| ALB → nginx → Node | `2` | Trust exactly two |
| Cloudflare → origin | The Cloudflare IP ranges, or `1` **plus** an origin firewall that only accepts Cloudflare | A hop count alone is spoofable if the origin is directly reachable |
| Kubernetes with an ingress controller | `1`, or the ingress pod CIDR | |

A **hop count** is far safer than `true`: Express takes the address that many
positions from the right of `X-Forwarded-For`, so a client prepending fake
entries on the left cannot influence it. This is the single most important
detail in this finding.

### 4. Verify after deployment, do not assume

```ts
// A temporary debug route, or a field on the health endpoint from Suggestion 07.
app.get("/api/whoami", (req, res) => {
  res.json({
    ip: req.ip,
    ips: req.ips,                                    // the parsed X-Forwarded-For chain
    xForwardedFor: req.get("x-forwarded-for") ?? null,
    trustProxy: app.get("trust proxy"),
  });
});
```

Then check both cases:

```bash
curl -s https://target/api/whoami | jq
# ip must be YOUR real address, not the proxy's

curl -s https://target/api/whoami -H 'X-Forwarded-For: 1.2.3.4' | jq
# ip must STILL be your real address. If it returns 1.2.3.4, the setting is
# too permissive and every IP-keyed limiter is bypassable.
```

Remove the route (or gate it behind auth) before going live.

### 5. Consider a non-IP fallback key

IP-based limiting is inherently fragile — CGNAT, mobile carriers, IPv6 rotation,
and corporate egress all confound it in both directions. The failed-login limiter
already keys on `sha256(email|ip)`; consider adding an **email-only** bucket with
a looser limit as a second layer, so an attacker who defeats the IP dimension
still hits a per-account ceiling:

```ts
// A per-account bucket that no header can forge.
`rate:login:fail:email:${hashSha256(normalizedEmail)}`   // e.g. 25 / hour
```

This is the highest-value hardening in this finding, because it survives *any*
IP-layer failure — including a genuinely distributed attack, which no
IP-keyed limiter stops.

## Interaction with other findings

- **[Vulnerability 10](./10.no-security-headers-no-cors-policy-and-cookie-flags.md)**
  — HSTS implies TLS termination implies a reverse proxy implies `TRUST_PROXY`
  must change. **These two must be done in the same change.** Adding HSTS without
  fixing `TRUST_PROXY` puts you in failure mode A (self-inflicted outage); adding
  a proxy and reflexively setting `true` puts you in failure mode B.
- **[Vulnerability 07](./07.rate-limiters-fail-open.md)** — the other way to
  defeat the same limiters, by removing the check rather than forging the key.
  Fixing fail-open does nothing if the key is spoofable, and vice versa. **Both
  are required; neither substitutes for the other.**
- **[Vulnerability 18](./18.weak-password-policy.md)** and
  **[Vulnerability 15](./15.login-user-enumeration-via-timing.md)** — the same
  compounding chain: target list + weak passwords + unlimited attempts.
- **[Suggestion 07](../suggestions/07.health-readiness-and-graceful-shutdown.md)**
  — the health endpoint is the right permanent home for step 4's diagnostics
  (effective `trust proxy`, observed `req.ip`), rather than a temporary route
  someone forgets to remove.
- **[Suggestion 14](../suggestions/14.docker-compose-and-reproducible-dev-env.md)**
  — a compose file that puts nginx in front of the API makes this immediately
  live. Set `TRUST_PROXY=1` in that compose file and document why.

## What you already got right here

- **The default is `false`.** The safe value is the one you get by doing nothing,
  which is the correct direction for a security-relevant default. Plenty of
  projects default to `true` because it "just works" behind a proxy.
- **It is configurable at all.** Many Express applications hardcode
  `app.set("trust proxy", true)` and never think about it again. You recognised
  this as a deployment-topology concern and pushed it into configuration.
- **`parseTrustProxy` handles the three legitimate shapes** — boolean, hop count,
  and pass-through for subnet strings — with the numeric branch correctly
  requiring a non-negative integer. The logic is right; only the validation and
  the production guard are missing.
- **`normalizeIpForRateLimit` strips the `::ffff:` IPv4-mapped IPv6 prefix**, so
  the same client does not get two separate rate-limit buckets depending on
  whether Node reports `192.0.2.1` or `::ffff:192.0.2.1`. That is a real,
  easy-to-miss bug in hand-rolled IP limiters and you handled it.
- **`getTrustedClientIp` throws rather than falling back to a placeholder** when
  `req.ip` is absent. Failing loudly beats silently bucketing everyone under
  `"unknown"`.

## The finding

Every RBAC mutation endpoint is willing to destroy the grant that authorized it.
The schema's cascades then propagate the damage:

```sql
-- server/src/config/db.setup.ts
CREATE TABLE role_permissions (
  role_id       INT NOT NULL REFERENCES roles(id)       ON DELETE CASCADE,
  permission_id INT NOT NULL REFERENCES permissions(id) ON DELETE CASCADE,
  UNIQUE (role_id, permission_id)
);
CREATE TABLE user_roles (
  user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role_id INT NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  UNIQUE (user_id, role_id)
);
```

Four routes to an unrecoverable state:

**1. `DELETE /api/permissions/:permissionId`** — deletes a `permissions` row.
`ON DELETE CASCADE` removes it from **every** role simultaneously. There is no
check on which permission is being deleted.

```ts
// server/src/controllers/permission/removePermission.ts:30
await checkRolePermissions(actorId, "delete", "permission");
const permissionId = parsePositiveInt(req.params["permissionId"], "permissionId");
const deletedPermission = await pool.query(
  `DELETE FROM permissions WHERE id = $1 RETURNING ...`, [permissionId]);
// If permissionId is the row for (assign, permission) or (create, permission),
// the ability to ever restore it just went with it.
```

**2. `DELETE /api/role-permissions`** — revokes one `(role, permission)` grant.
Revoking `assign:permission` from `super-admin` removes the only means of
granting it back.

**3. `DELETE /api/roles/:roleName`** — deletes a role. `canActorManageRole`
permits a super-admin to delete any role, including `super-admin` itself. The
cascade strips the role from every holder in the same statement.

**4. `DELETE /api/user-roles/:userId`** — `revokeRole` blocks self-revocation
(`actorId === userId`) but has **no last-super-admin guard**, unlike `deleteUser`
which does have one ([deleteUser.ts:46-56](../../server/src/controllers/users/deleteUser.ts#L46-L56)).

And the recovery path is closed too. `registration.ts` is the bootstrap door, and
it locks itself:

```ts
// server/src/controllers/auth/registration.ts:59
const godExists = await client.query(
  `SELECT 1 FROM user_roles WHERE role_id = $1 LIMIT 1`, [superAdminRole.rows[0].id]);
if ((godExists.rowCount ?? 0) > 0) {
  throw AppError.forbidden("Registration is locked. App already initialized with a super-admin.");
}
```

Note the asymmetry: it checks `user_roles`, so it *does* reopen if the last
super-admin **assignment** disappears. But it also requires the `super-admin`
**role row** to exist:

```ts
if ((superAdminRole.rowCount ?? 0) !== 1 || (defaultUserRole.rowCount ?? 0) !== 1) {
  throw AppError.notFound("Default 'user' or 'super-admin' role not found in database");
}
```

So `DELETE /api/roles/super-admin` produces a state where nobody has the role,
**and** registration refuses to run because the role row is gone. There is no API
path back. Recovery requires `psql`.

## Why it matters

Three distinct outcomes, in increasing severity:

| Action | Result | Recoverable via API? |
| --- | --- | --- |
| Revoke `assign:permission` from `super-admin` | No one can grant any permission to any role, ever | ❌ |
| Delete the `(create, permission)` row | No one can create permissions; deleted ones cannot return | ❌ |
| Delete the `user` role | Every user loses the base permission set; `getUserRoleNames` filters the now-unknown name out and everyone reads as roleless | ❌ |
| **Delete the `super-admin` role** | Every super-admin silently demoted; registration refuses to bootstrap because the role row is missing | ❌ **Total lockout** |

This is not primarily an attacker scenario — a super-admin is already the top of
the trust chain. It is an **operator-error** scenario, and those are more likely.
The permissions page in the client is a plain table with a delete button per row.
There is nothing in the UI or the API that distinguishes "delete the
`view:migration` permission, which is fine" from "delete the `assign:permission`
permission, which ends the system". One misclick and the deployment needs a DBA.

The cascade is what makes it irreversible rather than merely bad. `DELETE FROM
permissions WHERE id = 8` looks like it touches one row; it silently deletes
every `role_permissions` row referencing it, and those rows are not recorded
anywhere — the audit entry only captures the deleted `permissions` row, not the
grants that went with it.

## Exploit walkthrough

```bash
# One request. Actor is a legitimate super-admin. No attack required.
curl -X DELETE localhost:8000/api/roles/super-admin -b "access=$SUPER_ADMIN"
# -> 200 {"success":true,"message":"Role deleted successfully",
#         "data":{"role":{"id":4,"name":"super-admin","description":"Full system access"}}}

# Every super-admin has been demoted by cascade. Verify:
curl -s -b "access=$SUPER_ADMIN" localhost:8000/api/users
# -> 403 "You do not have permission to view on user"

# Try to bootstrap a new super-admin:
curl -X POST localhost:8000/api/auth/register -H 'Content-Type: application/json' \
  -d '{"fullname":"Recovery","email":"recovery@corp.example","password":"..."}'
# -> 404 "Default 'user' or 'super-admin' role not found in database"

# There is no third option. Open psql.
```

## The fix

Protect the invariants in the **database** (so direct SQL and future code paths
are covered) and in the **application** (so the error message is useful).

### 1. Mark system-critical rows as undeletable

```sql
-- migrations/<timestamp>_protect-system-rbac.sql
-- Up Migration
ALTER TABLE roles       ADD COLUMN is_system BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE permissions ADD COLUMN is_system BOOLEAN NOT NULL DEFAULT FALSE;

UPDATE roles SET is_system = TRUE WHERE name IN ('user', 'super-admin');

-- The permissions without which the RBAC system cannot administer itself.
UPDATE permissions SET is_system = TRUE
 WHERE (action, resource) IN (
   ('create', 'permission'), ('delete', 'permission'),
   ('assign', 'permission'), ('revoke', 'permission'),
   ('create', 'role'),       ('assign', 'role'),      ('revoke', 'role'),
   ('view',   'user')
 );

-- Belt and braces: a trigger, so psql and future code paths are covered too.
CREATE OR REPLACE FUNCTION reject_system_row_delete() RETURNS TRIGGER AS $$
BEGIN
  IF OLD.is_system THEN
    RAISE EXCEPTION 'Cannot delete system row (id=%)', OLD.id
      USING ERRCODE = '23514';        -- check_violation; errorHandler maps it to 400
  END IF;
  RETURN OLD;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER roles_protect_system BEFORE DELETE ON roles
  FOR EACH ROW EXECUTE FUNCTION reject_system_row_delete();
CREATE TRIGGER permissions_protect_system BEFORE DELETE ON permissions
  FOR EACH ROW EXECUTE FUNCTION reject_system_row_delete();

-- Down Migration
DROP TRIGGER IF EXISTS permissions_protect_system ON permissions;
DROP TRIGGER IF EXISTS roles_protect_system ON roles;
DROP FUNCTION IF EXISTS reject_system_row_delete();
ALTER TABLE permissions DROP COLUMN is_system;
ALTER TABLE roles       DROP COLUMN is_system;
```

The `ERRCODE = '23514'` is chosen deliberately —
[errorHandler.middleware.ts](../../server/src/middleware/errorHandler.middleware.ts)
already maps `23514` to `400 "Input violates a database rule."`, so even without
the application check the failure is a clean 400 rather than a 500.

### 2. Reject in the controllers, with a message that explains why

```ts
// server/src/controllers/permission/removePermission.ts
const target = await pool.query(
  "SELECT id, action, resource, description, is_system FROM permissions WHERE id = $1",
  [permissionId],
);
if ((target.rowCount ?? 0) === 0) throw AppError.notFound("Permission not found");
if (target.rows[0].is_system) {
  throw AppError.forbidden(
    "This permission is required for the RBAC system to administer itself and cannot be deleted.",
  );
}
```

Same guard in `deleteRole` (on `roles.is_system`) and in `revokePermission` —
that last one must check the *pair*, not the permission alone:

```ts
// server/src/controllers/role_permissions/revokePermission.ts
if (roleExists.rows[0].is_system && permissionExists.rows[0].is_system) {
  throw AppError.forbidden(
    "This grant is required for the RBAC system to administer itself and cannot be revoked.",
  );
}
```

### 3. Add the missing last-super-admin guard to `revokeRole`

Copy the invariant that already exists in `deleteUser`:

```ts
// server/src/controllers/user_roles/revokeRole.ts -- before the DELETE
if (targetRoleExists.rows[0].name === "super-admin") {
  const remaining = await client.query<{ count: number }>(
    `SELECT COUNT(*)::int AS count
       FROM user_roles ur JOIN roles r ON r.id = ur.role_id
      WHERE r.name = 'super-admin'`,
  );
  if ((remaining.rows[0]?.count ?? 0) <= 1) {
    throw AppError.forbidden("Cannot revoke the role from the last super-admin");
  }
}
```

### 4. Give the bootstrap door a real key

Even with the guards, a deployment can end up with zero super-admins (the last one
is deleted while another exists, then that one is deleted — the guard is
per-request and the count check handles it, but consider migrations, restores,
manual SQL). Make recovery possible without `psql`:

```ts
// server/src/controllers/auth/registration.ts
// Re-open bootstrap only when explicitly authorised out-of-band.
if ((godExists.rowCount ?? 0) > 0) {
  throw AppError.forbidden("Registration is locked. App already initialized with a super-admin.");
}
if (env.BOOTSTRAP_TOKEN && req.get("x-bootstrap-token") !== env.BOOTSTRAP_TOKEN) {
  throw AppError.forbidden("Registration is locked.");
}
```

Plus a `pnpm run rbac:repair` script that re-runs `seedReferenceRbac()` and
re-grants `super-admin` to a named user. `db.seed.ts` is already idempotent
(`ON CONFLICT ... DO UPDATE` / `DO NOTHING`), so it is safe to run against a
damaged database — that is a real asset here.

### 5. Make the client warn

The permissions and roles tables should render system rows with the delete action
disabled and a tooltip, using the `is_system` flag added to the API contract.
Client-side only; the server is authoritative. But it stops the misclick, which
is the actual threat.

## Interaction with other findings

- **[Vulnerability 06](./06.role-rename-privilege-escalation.md)** introduces
  `roles.is_system` for the same reason. **Write that column once, in one
  migration.** If you do 06 first, step 1 here shrinks to just the `permissions`
  half.
- **[Suggestion 03](../suggestions/03.database-driven-role-hierarchy.md)** adds
  `roles.rank` in the same table. Bundle all three columns
  (`rank`, `is_system` on roles; `is_system` on permissions) into one migration
  rather than three.
- **[Vulnerability 21](./21.non-transactional-audit-writes.md)** —
  `removePermission` currently deletes and audits on the bare pool with no
  transaction, so a failed audit leaves an orphaned deletion. The guard added
  here should go in alongside wrapping that controller in a transaction.
- **[Vulnerability 14](./14.auth-router-is-not-actually-protected.md)** — the
  bootstrap-reopening behaviour of `registration.ts` is analysed there from the
  attacker's side. The `BOOTSTRAP_TOKEN` in step 4 addresses both findings; make
  sure you implement it once, consistently.
- **No contradiction** with [Vulnerability 02](./02.overpermissive-default-user-role.md),
  which *removes* permissions from the base role. Just make sure the permissions
  you mark `is_system` are the administrative ones, not the ones finding 02 moves
  around.

## What you already got right here

- **The seed script is idempotent.** `ON CONFLICT (name) DO UPDATE` for roles,
  `ON CONFLICT (action, resource) DO UPDATE` for permissions, and
  `ON CONFLICT (role_id, permission_id) DO NOTHING` for grants. That is what
  makes step 4's repair script a two-line addition rather than a project. Most
  seed scripts assume an empty database and explode on a second run.
- **`deleteUser`'s last-super-admin guard already exists.** You identified this
  exact class of invariant and implemented it correctly in one place — the fix
  here is largely "apply the thing you already thought of to the other three
  doors".
- **`ON DELETE CASCADE` on the join tables is the right choice.** Orphaned
  `user_roles` rows pointing at deleted roles would be far worse. The cascade is
  correct; what is missing is a guard on *which* parents may be deleted.
- **`ON DELETE SET NULL` on `audit_logs.actor_id`** rather than cascade — so
  deleting a user preserves their audit history with a null actor instead of
  erasing the evidence. That is a deliberate, security-aware schema decision.
- The bootstrap lock uses `SELECT ... FOR UPDATE` on the `super-admin` role row
  to serialise concurrent registrations. That is a correct solution to a real
  race that most bootstrap flows have and never notice.

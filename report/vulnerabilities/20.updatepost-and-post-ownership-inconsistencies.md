# 20 — Post authorization is inconsistent: `update` ignores ownership rank, `delete` enforces it

## The finding

Three post controllers make three different decisions about the same question.

**`deletePost` — full hierarchy reasoning:**

```ts
// server/src/controllers/post/deletePost.ts:44
await checkRolePermissions(actorId, "delete", "post");

const actorRoles = /* SELECT r.name FROM user_roles ... WHERE ur.user_id = actorId */;
const ownerRoles = /* SELECT r.name FROM user_roles ... WHERE ur.user_id = owner_id */;
const highestActorRole = sortRoleBasedOnRanks(actorRoles)[0];
const highestOwnerRole = sortRoleBasedOnRanks(ownerRoles)[0];

if (highestActorRole === "admin" && highestOwnerRole === "super-admin") {
  throw AppError.forbidden("Admin cannot delete a post owned by a super-admin");
}
```

**`updatePost` — capability check only:**

```ts
// server/src/controllers/post/updatePost.ts:38
if (actorId !== existingPost.owner_id) {
  await checkRolePermissions(actorId, "update", "post");
}
// -> no owner role lookup, no hierarchy comparison. Done.
```

**`createPostOnBehalf` — no target reasoning at all:**

```ts
// server/src/controllers/post/createPostOnBehalf.ts:37
await checkRolePermissions(actorId, "createOnBehalf", "post");
// -> only super-admin holds this, so the gap is currently unreachable.
//    But the pattern is "capability implies unrestricted target choice".
```

Who holds `update:post`? From [hierarchy.ts](../../server/src/config/hierarchy.ts):
`editor` (id 6) and `super-admin` (id 17). Notably **not** `admin`.

So the current reachable consequence is: **an `editor` can rewrite any post in the
system, including posts owned by a super-admin.** Meanwhile an `admin` — a
strictly higher rank — cannot delete a super-admin's post, because `deletePost`
explicitly forbids it.

That is backwards. The lower-ranked role has broader authority over
higher-ranked users' content than the higher-ranked role does.

### Two smaller inconsistencies in the same area

**Ownership on delete is not checked at all.** `deletePost` requires
`delete:post`, which only `admin` and `super-admin` hold. So a `user` or `editor`
cannot delete **their own** post. That is almost certainly not intended — the
usual model is "owners may always delete their own content" — and it is
inconsistent with `updatePost`, which *does* grant owners an implicit bypass
(`if (actorId !== existingPost.owner_id)`).

**`behalf_of` is not surfaced as authorship.** When a super-admin creates a post
on behalf of user 7, the row gets `owner_id = 7, behalf_of = <actor>`. The
`check_behalf_not_self` constraint prevents self-attribution, which is good. But
`updatePost` and `deletePost` never consider `behalf_of` — so the ghost-writer
cannot edit their own draft after creating it (they are not the owner), and the
nominal owner can edit content they did not write with no indication it was
ghost-written. Whether that is right depends on your intent; right now no
controller states an intent.

## Why it matters

Impact is content integrity, not privilege escalation — nobody gains a role or
reads a secret through this. That is why it ranks 5 rather than higher.

What makes it worth fixing is that **the inconsistency itself is the
vulnerability**. `deletePost` ends with a comment block spelling out its rules:

```ts
/**
 * conditions
 * 1. an admin not delete the post of a super-admin but any super-admin can delete any post
 * 2. an admin can also delete the post of himself and other admins
 */
```

The rule was reasoned about, written down, and implemented — in one file. A
reader of `updatePost` has no way to know whether the missing check is a
deliberate difference ("edits are less sensitive than deletions") or an
oversight. When authorization rules differ between sibling operations without a
stated reason, every future change to either one is a guess, and the next
controller someone adds will copy whichever file they opened first.

The concrete scenario: an editor account is compromised (or an editor goes rogue).
They cannot escalate, cannot read sessions after
[Vulnerability 02](./02.overpermissive-default-user-role.md) is fixed, and cannot
delete anything. But they can silently rewrite the content of every post in the
system, including posts attributed to super-admins. The audit log captures it —
`old_values` / `new_values` are recorded correctly — so it is detectable after the
fact. It should simply not be permitted.

## Exploit walkthrough

```bash
# Actor: an editor. Target: a post owned by user 1 (the bootstrap super-admin).
curl -s -b "access=$EDITOR" localhost:8000/api/posts \
  | jq '.data.posts[] | select(.owner_id == 1) | {id, title, owner_fullname}'
# { "id": 3, "title": "Q3 security policy", "owner_fullname": "Root Admin" }

curl -X PUT localhost:8000/api/posts/3 -b "access=$EDITOR" \
  -H 'Content-Type: application/json' \
  -d '{"title":"Q3 security policy","content":"Policy rescinded. See attached."}'
# -> 200 {"success":true,"message":"Post updated successfully", ...}
# The post still shows owner_fullname "Root Admin". The rewrite is attributed
# to the super-admin in every listing; only the audit log knows otherwise.

# The same editor cannot delete it -- they lack delete:post:
curl -X DELETE localhost:8000/api/posts/3 -b "access=$EDITOR"
# -> 403 "You do not have permission to delete on post"
```

## The fix

Decide the ownership model once, write it down, and apply it identically in all
three controllers.

### 1. State the model

Recommended semantics, chosen to match what `deletePost`'s comment already implies:

> - The **owner** may always update and delete their own post.
> - A **non-owner** needs the relevant capability (`update:post` / `delete:post`)
>   **and** must outrank the owner.
> - `behalf_of` does not confer edit rights; the owner is the owner.

### 2. Extract one guard

```ts
// server/src/utils/helper.ts
/**
 * Authorizes an action on a post. Owners always pass. Non-owners need the
 * capability AND must outrank the owner -- an editor may not rewrite a
 * super-admin's post, and an admin may not delete one.
 */
async function assertCanActOnPost(
  actorId: number,
  post: { owner_id: number },
  action: Extract<ACTIONS_TYPES, "update" | "delete">,
  db: QueryableDb,
): Promise<void> {
  if (actorId === post.owner_id) return;

  await checkRolePermissions(actorId, action, "post", db);
  await assertCanManageUser(
    actorId,
    post.owner_id,
    db,
    `You cannot ${action} a post owned by this user`,
  );
}
```

`assertCanManageUser` is the shared hierarchy helper introduced in
[Vulnerability 11](./11.session-revocation-and-peer-actions-lack-hierarchy-checks.md).
The `db` parameter is required by
[Vulnerability 08](./08.pool-starvation-from-permission-checks-inside-transactions.md).

### 3. Apply it in both controllers

```ts
// server/src/controllers/post/updatePost.ts -- replaces lines 38-40
await assertCanActOnPost(actorId, existingPost, "update", client);

// server/src/controllers/post/deletePost.ts -- replaces lines 44-80
await assertCanActOnPost(actorId, existingPost, "delete", client);
```

That deletes roughly forty lines from `deletePost` (the two role queries, the two
`sortRoleBasedOnRanks` calls, the two null checks and the explicit admin/
super-admin comparison) and replaces the missing check in `updatePost`. Move the
explanatory comment from the bottom of `deletePost.ts` onto the helper's JSDoc,
where it now describes both operations.

### 4. Decide the owner-delete question explicitly

Granting owners implicit delete rights is a **behaviour change**: today a `user`
cannot delete their own post, and after this fix they can. That is almost
certainly the intent — `create:post` without a corresponding delete is an odd
model — but it is a deliberate decision, not a refactor. If you would rather keep
deletion admin-only, drop the `if (actorId === post.owner_id) return;` line for
the delete case and pass `action` into that branch. Either is defensible;
choosing silently is not.

### 5. Decide `behalf_of` explicitly too

Either document that ghost-writers have no post-creation rights (the current de
facto behaviour), or add `|| actorId === post.behalf_of` to the owner check. The
schema already supports the question; the code should answer it.

## Interaction with other findings

- **[Vulnerability 11](./11.session-revocation-and-peer-actions-lack-hierarchy-checks.md)**
  is the same finding applied to sessions, and it defines `assertCanManageUser`.
  **Implement 11 first**; this becomes a small consumer of its helper. If you do
  this one first you will write the hierarchy comparison twice.
- **[Vulnerability 06](./06.role-rename-privilege-escalation.md)** decides whether
  rank comparison is `>` or `>=`, and whether ranks come from a map or a column.
  `assertCanActOnPost` inherits that decision — do not encode a separate rule here.
- **[Vulnerability 08](./08.pool-starvation-from-permission-checks-inside-transactions.md)**
  — passing `client` into the helper is what keeps the authorization read inside
  the transaction that holds the `FOR UPDATE` lock on the post row. That is
  strictly better than today, where `deletePost`'s role queries run on `client`
  but its `checkRolePermissions` runs on the bare pool.
- **[Suggestion 01](../suggestions/01.centralize-authorization-in-middleware.md)**
  — the capability half (`checkRolePermissions`) could move to route middleware,
  but the ownership half needs the loaded row and must stay in the controller.
  `assertCanActOnPost` is the right shape for that boundary; do not try to push
  all of it into middleware.
- **No contradiction** with [Vulnerability 02](./02.overpermissive-default-user-role.md),
  which changes which roles hold `view:post` and `create:post`. This finding is
  about the ownership dimension, which is orthogonal to the capability set.

## What you already got right here

- **`deletePost`'s rules are documented in the file.** The comment block at the
  bottom is why this finding exists as a clear "these two disagree" rather than a
  vague "authorization feels inconsistent". Writing the rule down is what made
  its absence elsewhere visible. Keep doing that.
- **`updatePost` already grants owners an implicit bypass**, which is the correct
  ownership instinct — it just needs the non-owner branch tightened rather than
  the owner branch changed.
- **The `check_behalf_not_self` constraint**
  (`CHECK (behalf_of IS NULL OR behalf_of != owner_id)`) enforces at the database
  level that a ghost-written post cannot be self-attributed. That is a real
  integrity invariant expressed in the right place, and `createPostOnBehalf` also
  rejects `actorId === targetUserId` at the application layer with a helpful
  message. Defence in depth on a subtle rule.
- **`FOR UPDATE` on the post row** before both update and delete, so the
  authorization decision and the mutation see the same row state. The transaction
  structure is already correct; only the decision inside it needs aligning.
- **Both controllers audit with full before/after snapshots**, so even the
  unauthorized edit described above is fully reconstructible from `audit_logs`.
  The detection story is solid even where the prevention story is not.

## The finding

`auditDBMutation` is called from fifteen controllers. Grep for it in the auth
directory:

```
$ grep -rn "auditDBMutation" server/src/controllers/auth/
server/src/controllers/auth/registration.ts:6:import { auditDBMutation } from "@/utils/helper.ts";
server/src/controllers/auth/registration.ts:97:    await auditDBMutation({ ... });
server/src/controllers/auth/registration.ts:107:   await auditDBMutation({ ... });
server/src/controllers/auth/registration.ts:117:   await auditDBMutation({ ... });
```

Registration — the one auth event that happens at most once per deployment — is
audited three times. Everything else in the authentication lifecycle is audited
zero times:

| Event | Audited? | Where it would go |
| --- | --- | --- |
| Successful login | ❌ | `login.ts` |
| **Failed login** | ❌ | `login.ts`, both failure branches |
| Rate limit tripped (login / refresh / global) | ❌ | the limiter middlewares |
| Logout | ❌ | `logout.ts` |
| Token refresh | ❌ | `refreshToken.ts` |
| **Refresh token reuse / mismatch** | ❌ | `refreshToken.ts` |
| Session evicted by the row cap | ❌ | `session.util.ts` |
| Permission denied (403 from `checkRolePermissions`) | ❌ | `helper.ts` |
| Bootstrap registration | ✅ ×3 | `registration.ts` |
| User / role / permission / post / session mutations | ✅ | all controllers |

The schema itself blocks these events even if you wanted to log them.
`action_type` and `resource_type` are constrained by `CHECK` to the existing enums:

```sql
-- server/src/config/db.setup.ts
action_type   VARCHAR(50) NOT NULL CHECK (action_type IN
  ('view','create','update','assign','revoke','delete','createOnBehalf')),
resource_type VARCHAR(50) NOT NULL CHECK (resource_type IN
  ('permission','role','user','post','audit_log','session','migration')),
resource_id   INT NOT NULL,
```

There is no `login` action and no `authentication` resource. And `resource_id` is
`NOT NULL`, so an event that is not about a specific row cannot be represented at
all.

`actor_id INT REFERENCES users(id)` also means a **failed** login — where there
may be no such user — cannot record who was attempted.

## Why it matters

This is the difference between an audit log and a change log. What you have is an
excellent change log. What an IAM system needs is an audit log, and the
distinction is precisely the events listed above.

**Concretely, none of these questions can be answered from your data:**

- "Was this account's credential brute-forced before the compromise?" — no failed
  login records exist.
- "When did this session start, and from where?" — `user_sessions.created_at` and
  `device_info` exist, but only for the **two** most recent sessions, because
  `MAX_SESSION_ROWS_PER_USER = 2` deletes older rows outright rather than marking
  them. Login history is destroyed by design.
- "Did someone replay a stolen refresh token?" — the CAS miss in
  `refreshToken.ts` throws a 400 and records nothing. This is the single
  highest-signal security event the system can generate and it is discarded (see
  [Vulnerability 05](./05.refresh-token-rotation-without-reuse-detection.md)).
- "Which accounts were probed during the incident window?" — rate limit trips are
  `console.warn` to stdout with no correlation to anything.
- "Who tried to access what they were not allowed to?" — every 403 from
  `checkRolePermissions` vanishes. Repeated 403s from one account is the classic
  signature of a compromised low-privilege credential being explored, and it is
  invisible here.

There is a second-order effect worth naming: the mutation audit trail is only
*trustworthy* if you can establish that the actor was really the actor. Without
authentication events, an entry saying `actor_id: 3 deleted user 7` cannot be
corroborated against "user 3 logged in from this address at this time". The
existing log's evidentiary value is capped by the missing one.

## The fix

### 1. Extend the enums so authentication events are representable

```sql
-- migrations/<timestamp>_add-auth-audit-events.sql
-- Up Migration
ALTER TABLE audit_logs DROP CONSTRAINT IF EXISTS audit_logs_action_type_check;
ALTER TABLE audit_logs ADD CONSTRAINT audit_logs_action_type_check
  CHECK (action_type IN (
    'view','create','update','assign','revoke','delete','createOnBehalf',
    'login','login_failed','logout','refresh','refresh_reuse',
    'rate_limited','access_denied'
  ));

ALTER TABLE audit_logs DROP CONSTRAINT IF EXISTS audit_logs_resource_type_check;
ALTER TABLE audit_logs ADD CONSTRAINT audit_logs_resource_type_check
  CHECK (resource_type IN (
    'permission','role','user','post','audit_log','session','migration',
    'authentication'
  ));

-- Authentication events are not always about a specific row.
ALTER TABLE audit_logs ALTER COLUMN resource_id DROP NOT NULL;

-- A failed login has no user to attribute to; keep the attempted identity in
-- metadata instead, hashed if you would rather not store raw addresses.
ALTER TABLE audit_logs ADD COLUMN ip_address INET;
ALTER TABLE audit_logs ADD COLUMN user_agent TEXT;

CREATE INDEX idx_audit_logs_action_time ON audit_logs(action_type, created_at DESC);
CREATE INDEX idx_audit_logs_ip_time     ON audit_logs(ip_address, created_at DESC);

-- Down Migration
DROP INDEX IF EXISTS idx_audit_logs_ip_time;
DROP INDEX IF EXISTS idx_audit_logs_action_time;
ALTER TABLE audit_logs DROP COLUMN IF EXISTS user_agent;
ALTER TABLE audit_logs DROP COLUMN IF EXISTS ip_address;
-- (restore the original constraints; omitted for brevity)
```

**Important:** `ACTIONS_LIST` in
[others/constants.ts](../../server/src/others/constants.ts) is shared between the
`permissions` table's `CHECK` constraint and the `audit_logs` one, and it drives
`PermissionActionSchema` in the OpenAPI contract. Do **not** add `login` to
`ACTIONS_LIST` — that would create bogus assignable permissions like
`login:post`. Introduce a separate `AUDIT_ACTIONS_LIST` that is a superset:

```ts
// server/src/others/constants.ts
const ACTIONS_LIST = ["view","create","update","assign","revoke","delete","createOnBehalf"] as const;

/** Audit actions include every permission action plus non-permission events. */
const AUDIT_ACTIONS_LIST = [
  ...ACTIONS_LIST,
  "login","login_failed","logout","refresh","refresh_reuse","rate_limited","access_denied",
] as const;

const AUDIT_RESOURCES_LIST = [...RESOURCES_LIST, "authentication"] as const;
```

Then widen `AuditDBMutationInput` to use the audit enums and make `resourceId`
nullable, while `checkRolePermissions` keeps using the narrower `ACTIONS_TYPES`.
This keeps the permission surface unchanged — which matters, because
[Vulnerability 12](./12.rbac-self-destruct-via-role-and-permission-deletion.md)
and the `permissions_action_check` constraint both depend on it.

### 2. Log the events

```ts
// server/src/utils/audit.util.ts -- a thin wrapper so call sites stay short
const auditAuthEvent = async ({
  actionType, actorId, req, metadata = null, db = pool,
}: {
  actionType: "login" | "login_failed" | "logout" | "refresh" | "refresh_reuse"
            | "rate_limited" | "access_denied";
  actorId: number | null;
  req: Request;
  metadata?: Record<string, unknown> | null;
  db?: QueryableDb;
}) =>
  db.query(
    `INSERT INTO audit_logs
       (actor_id, action_type, resource_type, resource_id, metadata, ip_address, user_agent)
     VALUES ($1, $2, 'authentication', NULL, $3, $4, $5)`,
    [actorId, actionType, metadata, getTrustedClientIp(req), req.get("user-agent") ?? null],
  );
```

Call sites:

```ts
// login.ts -- success, inside the existing transaction, before COMMIT
await auditAuthEvent({ actionType: "login", actorId: user.id, req, db: client,
  metadata: { sessionId } });

// login.ts -- failure, in registerFailedLoginAttempt
await auditAuthEvent({ actionType: "login_failed", actorId: user?.id ?? null, req,
  metadata: { emailHash: hashSha256(normalizedEmail) } });

// refreshToken.ts -- the reuse branch from Vulnerability 05
await auditAuthEvent({ actionType: "refresh_reuse", actorId: userId, req, db: client,
  metadata: { sessionId, revokedSessionIds } });

// helper.ts -- inside checkRolePermissions, before throwing 403
await auditAuthEvent({ actionType: "access_denied", actorId, req,
  metadata: { action, resource } });
```

**Store `emailHash`, not the raw email.** A failed-login log full of plaintext
addresses is itself a target, and the hash still lets you correlate attempts
against the same identity. This mirrors what `buildLoginFailureKey` already does.

### 3. Never let audit failure break authentication

Mutation audits belong inside the transaction — if the mutation rolls back, so
should its record. Authentication audits are different: a failed `INSERT` must
not prevent a legitimate user from logging in.

```ts
const auditAuthEventSafely = (input: Parameters<typeof auditAuthEvent>[0]) =>
  auditAuthEvent(input).catch((error) => {
    console.error("Failed to write authentication audit event", error);
  });
```

Use the safe variant for `login_failed`, `rate_limited` and `access_denied`
(which run outside transactions); use the strict variant for `login` success and
`refresh_reuse` (which run inside one and should roll back with it).

### 4. Watch the volume

`access_denied` on every 403 will be your highest-volume event by far, and a
misbehaving client can generate thousands. Two mitigations: only log the *first*
denial per actor per minute (a Redis `SET NX EX 60` — you already have the
primitives), and add a retention policy. `audit_logs` has no pruning today; a
partitioned table or a scheduled `DELETE FROM audit_logs WHERE created_at < NOW()
- INTERVAL '1 year'` is worth adding before this grows unbounded.

## What you already got right here

- **`auditDBMutation` is called inside the transaction, on the same client**, in
  every mutation controller that has a transaction. So a rolled-back change never
  leaves a phantom audit entry, and a committed change always has one. That is the
  hard part of audit logging and you got it right by construction.
- **Before-and-after snapshots.** `old_values` / `new_values` as `JSONB` gives you
  a real diff for every mutation, not just "user 3 changed something". Combined
  with `sanitizeUserRecord` stripping password hashes from every snapshot, this
  is a well-designed table.
- **`actor_id ... ON DELETE SET NULL`** rather than `CASCADE`. Deleting a user
  preserves their audit history with a null actor instead of erasing the record
  of what they did. That is a deliberate, correct, security-aware choice and it is
  the opposite of what a naive schema would do.
- **`idx_audit_logs_resource_lookup (resource_type, resource_id, created_at DESC)`**
  — a composite index shaped for the actual query pattern ("show me the history of
  this object"), with the timestamp descending so the common ordering is
  index-ordered. That is thoughtful indexing.
- The `metadata` column already carries human-readable context on role
  assignments (`"${actorId} assigned role ${roleName} to user ${userId}"`), which
  shows you were already thinking about the log as something a human reads during
  an investigation.

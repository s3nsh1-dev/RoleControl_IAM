# 19 — Nested session routes run `checkCookieSignature` and the rate limiter twice per request

|              |                                                                       |

## The finding

Two routers are mounted on overlapping paths:

```ts
// server/src/app.ts
app.use("/api/users", userRouter);                          // line 74
app.use("/api/roles", roleRouter);
app.use("/api/permissions", permissionRouter);
app.use("/api/user-roles", userRolesRouter);
app.use("/api/role-permissions", rolePermissionsRouter);
app.use("/api/posts", postRouter);
app.use("/api/users/:userId/sessions", userSessionRouter);  // line 80
```

Both attach the same middleware at router level:

```ts
// server/src/routes/user.route.ts
userRouter.use(checkCookieSignature);
userRouter.use(authenticatedRateLimiting);
userRouter.route("/").get(listUsers).post(createUser);
userRouter.route("/:userId").get(viewUser).put(updateUser).delete(deleteUser);
```

```ts
// server/src/routes/session.route.ts
const userSessionRouter: Router = Router({ mergeParams: true });
userSessionRouter.use(checkCookieSignature);
userSessionRouter.use(authenticatedRateLimiting);
userSessionRouter.route("/").get(listUserSessions);
userSessionRouter.route("/revoke-all").put(revokeAllUserSessions);
```

`router.use(fn)` with no path matches **every** path beneath the mount point. So a
request to `GET /api/users/5/sessions` does this:

1. Matches `app.use("/api/users", userRouter)` — the prefix matches.
2. `userRouter` runs `checkCookieSignature` (JWT verify #1).
3. `userRouter` runs `authenticatedRateLimiting` (**token #1 consumed**).
4. `userRouter.route("/")` — no match. `userRouter.route("/:userId")` — no match
   either, since `/5/sessions` has an extra segment.
5. The router exhausts and calls `next()`, returning control to the app.
6. `app.use("/api/users/:userId/sessions", userSessionRouter)` matches.
7. `userSessionRouter` runs `checkCookieSignature` (JWT verify #2).
8. `userSessionRouter` runs `authenticatedRateLimiting` (**token #2 consumed**).
9. `listUserSessions` finally runs.

Every request to `GET /api/users/:userId/sessions` and
`PUT /api/users/:userId/sessions/revoke-all` costs **two** rate-limit tokens and
**two** JWT verifications.

## Why it matters

The security impact is nil — running an authentication check twice is not
dangerous, just wasteful. The impact is on **correctness of the rate accounting**,
which matters because rate limits are a security control whose effectiveness
depends on the numbers meaning what you think they mean.

With `RATE_LIMIT_USER_LIMIT=60` per minute, these two endpoints effectively have a
budget of **30 requests per minute**, not 60. That is invisible from the
configuration, undocumented, and inconsistent with every other endpoint.

Concretely, the client's sessions area is exactly the place that hits this. The
"User sessions" page (`UserSessionsLookup`) polls `GET /api/users/:id/sessions`,
and `RevokeAllSessionsForm` follows a revoke with a refetch. An operator working
through a list of users during an incident — look up sessions, revoke all, look
up the next user — burns tokens at double rate against a budget they were told
was 60. They hit `429 Too many requests. Please slow down.` at what looks like
half the configured limit, during an incident, with no explanation.

There is a second, quieter cost: **two Redis round trips and two `ZADD`s per
request** where one would do, plus two `jwt.verify` calls. Small individually,
but it is pure waste on a hot path, and it will get worse once
[Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md)
adds a database session lookup to `checkCookieSignature` — that becomes **two
database queries per request** for these routes.

Also worth noting: the double-execution means `req.user` is assigned twice. Today
that is idempotent. If `checkCookieSignature` ever gains a side effect — updating
a `last_seen_at`, incrementing a counter, writing an audit entry per
[Vulnerability 17](./17.no-authentication-audit-trail.md) — it will fire twice for
these routes only, producing subtly wrong data that is very hard to trace back to
a routing decision.

## Exploit walkthrough

Not an exploit; a reproduction.

```bash
# RATE_LIMIT_USER_LIMIT=60, RATE_LIMIT_USER_WINDOW_MS=60000
# A normal endpoint: 60 requests succeed, the 61st is limited.
for i in $(seq 1 61); do
  curl -s -o /dev/null -w '%{http_code} ' -b "access=$TOKEN" localhost:8000/api/users
done; echo
# 200 x60, then 429    <- correct

# The nested endpoint: limited at 30.
redis-cli DEL "rate:user:1" > /dev/null
for i in $(seq 1 31); do
  curl -s -o /dev/null -w '%{http_code} ' -b "access=$TOKEN" localhost:8000/api/users/1/sessions
done; echo
# 200 x30, then 429    <- half the configured budget

# Confirm the double count directly:
redis-cli DEL "rate:user:1" > /dev/null
curl -s -o /dev/null -b "access=$TOKEN" localhost:8000/api/users/1/sessions
redis-cli ZCARD "rate:user:1"
# (integer) 2          <- one request, two entries
```

## The fix

Three options. Take the first.

### Option A (recommended) — give the parent router a path-scoped mount

The cleanest fix is to stop `userRouter`'s middleware from matching paths it does
not handle. Move the middleware onto the route definitions' shared prefix:

```ts
// server/src/routes/user.route.ts
const userRouter: Router = Router();

// Scope the middleware to the exact paths this router serves, so it does not
// run for nested mounts like /api/users/:userId/sessions.
userRouter
  .route("/")
  .all(checkCookieSignature, authenticatedRateLimiting)
  .get(listUsers)
  .post(createUser);

userRouter
  .route("/:userId")
  .all(checkCookieSignature, authenticatedRateLimiting)
  .get(viewUser)
  .put(updateUser)
  .delete(deleteUser);

export { userRouter };
```

`.all()` on a `route()` runs for that exact path only, so `/5/sessions` never
triggers it. Slightly more verbose, entirely explicit.

### Option B — mount the nested router first and make it terminal

```ts
// server/src/app.ts -- nested mount BEFORE the parent
app.use("/api/users/:userId/sessions", userSessionRouter);
app.use("/api/users", userRouter);
```

Express matches mounts in registration order, so the more specific path wins and
`userSessionRouter` handles the request without `userRouter` ever seeing it.

This is a one-line change and it works, but it is **fragile**: it depends on
mount ordering that a future reader has no reason to preserve, and reordering the
lines silently reintroduces the bug. If you take this option, put a comment on it
explaining why the order matters.

### Option C — restructure so sessions are not nested under users

```ts
app.use("/api/sessions", sessionRouter);   // already exists
// sessionRouter.route("/").get(listSessions)                     -- all sessions
// sessionRouter.route("/user/:userId").get(listUserSessions)     -- one user's
// sessionRouter.route("/user/:userId/revoke-all").put(revokeAllUserSessions)
// sessionRouter.route("/:sessionId/revoke").patch(revokeSession)
```

One router, one mount, no overlap, no `mergeParams` needed. This is arguably the
better API design — sessions are their own resource, and `/api/users/5/sessions`
implies sessions are a sub-collection of users in a way that
`/api/sessions?userId=5` does not.

**But it is a breaking API change.** It requires updating
[services.ts](../../client/src/api/services.ts), the OpenAPI document, the
regenerated `client/src/api/schema.ts`, and the v2 integration tests. Only worth
it if you are already reshaping the API — see
[Suggestion 16](../suggestions/16.openapi-as-contract-source-of-truth.md).

### Verify with a test

Whichever option you take, lock it in:

```ts
// server/tests/v4-rate-limits/rate-limit.cases.ts
test("nested session routes consume exactly one rate-limit token", async () => {
  await redis.del(`rate:user:${userId}`);
  await http.get(`/api/users/${userId}/sessions`, { cookies: authCookies });
  assert.equal(await redis.zcard(`rate:user:${userId}`), 1);
});
```

## What you already got right here

- **`Router({ mergeParams: true })`** on `userSessionRouter` is exactly right and
  is the detail most people miss. Without it, `req.params["userId"]` would be
  `undefined` inside the nested router and `listUserSessions` would throw a
  confusing 400 from `parsePositiveInt`. You knew the nested-router parameter
  semantics.
- **The comment `// nested route app.ts line 80`** in `session.route.ts` shows you
  were tracking the coupling between the router definition and its mount point.
  That is the kind of note that makes a codebase navigable.
- **Router-level middleware rather than per-handler.** Every one of the eight
  routers applies `checkCookieSignature` and `authenticatedRateLimiting` at the
  top, which means no route can be added without protection — a genuinely good
  default. The nesting interaction is the one case where "matches everything
  below" is not what you wanted, and it is a subtle Express behaviour rather than
  a careless mistake.
- The rate-limit key is `rate:user:${userId}`, derived from the authenticated
  identity rather than the IP, so a shared-NAT office does not share a budget.
  Correct design; this finding is only about the count being off by a factor of two.

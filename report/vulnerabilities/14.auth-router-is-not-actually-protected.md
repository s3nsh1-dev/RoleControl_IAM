## The finding

Compare how every other router applies authentication with how the auth router
does it:

```ts
// server/src/routes/user.route.ts -- the pattern used by all seven other routers
const userRouter: Router = Router();
userRouter.use(checkCookieSignature);          // router-level, covers every route
userRouter.use(authenticatedRateLimiting);
userRouter.route("/").get(listUsers).post(createUser);
```

```ts
// server/src/routes/auth.route.ts:13
const authExemptRouter: Router = Router();
const authProtectedRouter: Router = Router();

authExemptRouter.route("/login").post(loginRateLimiting, authLogin);
authExemptRouter.route("/refresh").get(refreshRateLimiting, authTokenRefresh);

authProtectedRouter.route("/logout").post(authLogout);                 // <-- no guard
authProtectedRouter.route("/me").get(checkCookieSignature, authMe);    // <-- guarded inline
authProtectedRouter.route("/register").post(authRegistration);         // <-- no guard
```

There is **no `authProtectedRouter.use(checkCookieSignature)`**. The middleware is
attached inline to `/me` only. Two of the three routes on a router named
"protected" are fully anonymous.

There is also no `authenticatedRateLimiting` anywhere on this router, though the
mount order in [app.ts:71-73](../../server/src/app.ts#L71-L73) does put
`authProtectedRouter` below `app.use("/api", globalRateLimiting)`, so these routes
do get the 100/min/IP global budget.

## Why it matters

The immediate exploitability is limited, because both handlers happen to
self-guard — but they self-guard for *incidental* reasons, and the naming
guarantees this will eventually break.

### `POST /api/auth/logout` — anonymous, but harmless today

The handler derives everything from the `refresh` cookie and verifies it:

```ts
// server/src/controllers/auth/logout.ts
const refreshToken: string | undefined = req.cookies["refresh"];
if (!refreshToken) { clearAuthCookies(); /* 200 */ return; }
try {
  const refreshPayload = verifyToken<REFRESH_JWT_PAYLOAD_TYPE>(refreshToken);
  if (refreshPayload.type === "refresh") {
    await pool.query(`UPDATE user_sessions SET revoked_at = COALESCE(revoked_at, NOW())
                       WHERE id = $1 AND user_id = $2`, [refreshPayload.sId, refreshPayload.uId]);
  }
} catch { /* idempotent */ }
```

An anonymous caller with no cookies gets a 200 and nothing happens. A caller can
only revoke a session for which they already hold a valid, signed refresh token —
i.e. their own. **This is actually correct design**: logout should not require a
*valid access token*, because the whole point is that you may be logging out
precisely when your access token has expired. If `checkCookieSignature` guarded
this route, a user with an expired access token could not log out. The bug is the
naming, not the behaviour.

### `POST /api/auth/register` — anonymous by design, guarded by database state

```ts
// server/src/controllers/auth/registration.ts:52
const superAdminRole = await client.query(
  "SELECT id FROM roles WHERE name = $1 FOR UPDATE", ["super-admin"]);
// ...
const godExists = await client.query(
  `SELECT 1 FROM user_roles WHERE role_id = $1 LIMIT 1`, [superAdminRole.rows[0].id]);
if ((godExists.rowCount ?? 0) > 0) {
  throw AppError.forbidden("Registration is locked. App already initialized with a super-admin.");
}
```

So the door is open **exactly when no user holds the `super-admin` role**, and it
grants the caller `super-admin` + `user`. The `FOR UPDATE` on the role row
correctly serialises concurrent bootstrap attempts — only one can win.

The problem is that this is a **stateful, self-reopening** door:

| Event | Registration state |
| --- | --- |
| Fresh database, seeded, no users | 🔓 **Open** — anyone who reaches the port becomes super-admin |
| First registration completes | 🔒 Locked |
| Last super-admin deleted (`DELETE /api/users/:id` — blocked by the last-super-admin guard) | 🔒 Locked |
| Last super-admin's role revoked (`DELETE /api/user-roles/:id` — **no guard**, see [Vulnerability 12](./12.rbac-self-destruct-via-role-and-permission-deletion.md)) | 🔓 **Reopens** |
| Database restored from a pre-bootstrap backup | 🔓 **Reopens** |
| `user_roles` truncated during a botched migration | 🔓 **Reopens** |

The deployment window is the sharpest version: between `pnpm db:setup && pnpm
db:seed` and the operator's first registration, the endpoint is a
**public super-admin factory**. If the API binds a public interface before that
first request lands — and `HOST` defaults to `0.0.0.0` in
[envHelper.ts:19](../../server/src/utils/envHelper.ts#L19) — the race is
winnable by anyone scanning for it. A registration also produces three audit
entries whose `actor_id` is the *newly created attacker*, so the log shows a
legitimate-looking bootstrap.

And the comment on the route says the opposite of what the code does:

```ts
// this router is taken only when we want to create a super-admin for the very first time,
// when done close the router as super-admin will have access to create another user
```

"When done, close the router" describes a manual step that nothing enforces and
that no deployment procedure documents.

## Exploit walkthrough

```bash
# Scenario: a fresh deployment, or any deployment where the last super-admin's
# role was revoked (Vulnerability 12 shows revokeRole has no last-admin guard).

curl -s -X POST http://target:8000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"fullname":"Site Reliability","email":"sre@attacker.example","password":"hunter2!"}'
# -> 201 {"success":true,
#         "message":"Super-Admin registered successfully. Please login.",
#         "data":{"user":{...},"roles":["super-admin","user"]}}

curl -s -X POST http://target:8000/api/auth/login -c jar.txt \
  -H 'Content-Type: application/json' \
  -d '{"email":"sre@attacker.example","password":"hunter2!"}'
# -> 200, full super-admin cookies. Total system compromise.
```

Probing costs one request and the response distinguishes the two states
unambiguously (`201` vs `403 "Registration is locked"`), so an attacker can poll
cheaply and pounce the moment the door opens.

## The fix

### 1. Make the router name honest

```ts
// server/src/routes/auth.route.ts
const authRouter: Router = Router();

// --- No access token required. Each route self-guards on its own credential. ---
authExemptRouter.route("/login").post(loginRateLimiting, authLogin);
authExemptRouter.route("/refresh").get(refreshRateLimiting, authTokenRefresh);
// Logout must work with an expired access token -- it validates the refresh
// cookie itself. Deliberately not behind checkCookieSignature.
authExemptRouter.route("/logout").post(authLogout);
authExemptRouter.route("/register").post(registrationRateLimiting, authRegistration);

// --- Requires a valid access token. ---
authProtectedRouter.use(checkCookieSignature);
authProtectedRouter.use(authenticatedRateLimiting);
authProtectedRouter.route("/me").get(authMe);
```

Now the router names describe reality, `/me` picks up the per-user rate limiter
it currently lacks, and the deliberate exemptions carry a comment explaining
*why* — so the next person does not "fix" logout by adding a guard that breaks it.

### 2. Rate-limit registration

It is currently unthrottled except by the global 100/min/IP budget. Add a
dedicated limiter mirroring the login one, so the polling attack above is
expensive:

```ts
// server/src/middleware/registrationRateLimiting.middleware.ts
const registrationRateLimiting = asyncMiddleware(async (req, res) => {
  await enforceRateLimit(res, `rate:register:ip:${getTrustedClientIp(req)}`,
    env.RATE_LIMIT_REGISTER_IP_LIMIT, env.RATE_LIMIT_REGISTER_IP_WINDOW_MS,
    { failureMode: "closed", message: "Too many registration attempts. Please try again later." });
});
```

(`enforceRateLimit` and `failureMode` come from
[Vulnerability 07](./07.rate-limiters-fail-open.md).)

### 3. Close the bootstrap door with a key, not with database state

Database state is the wrong lock because it is restorable, truncatable and
revocable. Use an out-of-band secret:

```ts
// server/src/utils/envHelper.ts
BOOTSTRAP_TOKEN: z.string().optional()
  .describe("One-time secret required to bootstrap the first super-admin. Unset = bootstrap disabled."),
```

```ts
// server/src/controllers/auth/registration.ts -- before any database work
if (!env.BOOTSTRAP_TOKEN) {
  throw AppError.forbidden("Registration is disabled.");
}
const presented = req.get("x-bootstrap-token") ?? "";
const expected = env.BOOTSTRAP_TOKEN;
// Constant-time compare; both sides hashed first so lengths always match.
if (!timingSafeEqual(Buffer.from(hashSha256(presented), "hex"),
                     Buffer.from(hashSha256(expected), "hex"))) {
  throw AppError.forbidden("Registration is disabled.");
}
// ...then the existing FOR UPDATE + godExists check as a second layer.
```

Deployment procedure becomes: set `BOOTSTRAP_TOKEN`, start, register, **unset it
and restart**. The door is closed by configuration, not by hoping nobody deletes
a row. Both guards should remain — defence in depth.

Note the identical `x-bootstrap-token` mechanism is proposed in
[Vulnerability 12](./12.rbac-self-destruct-via-role-and-permission-deletion.md)
as the *recovery* path. Implement it once; it serves both.

### 4. Consider dropping the endpoint entirely

The strongest option: delete the route and make bootstrap a CLI script
(`pnpm run bootstrap:super-admin --email=... --name=...`) that talks to the
database directly. An endpoint that must exist exactly once in a deployment's
lifetime does not belong in the HTTP surface. This removes the attack rather than
guarding it. The client's `/register` page and `authApi.register` would go too —
they are already only reachable by typing the URL, since nothing links to them.

## What you already got right here

- **The `authExemptRouter` / `authProtectedRouter` split itself.** Modelling
  "which routes need a token" as a routing concern rather than a per-handler `if`
  is the right structure. It is what makes this fix a five-line change.
- **`SELECT ... FOR UPDATE` on the super-admin role row** to serialise concurrent
  bootstrap requests. That is a real race — two simultaneous registrations both
  passing the `godExists` check — and you closed it with the correct primitive.
  Most bootstrap flows have this bug.
- **Reserving the user id up front** (`SELECT nextval(pg_get_serial_sequence(...))`)
  so the bootstrap user can be its own `created_by`. That is a neat solution to a
  genuine chicken-and-egg problem, and it keeps the `created_by` foreign key
  `NOT NULL`-clean without a nullable special case.
- **Logout is idempotent and never leaks.** `COALESCE(revoked_at, NOW())` means a
  double logout does not overwrite the original revocation timestamp, and the
  `catch {}` around token verification means a stale cookie still clears cleanly.
  Careful, deliberate work.
- The registration transaction writes **three** audit entries (user create, both
  role assignments) before committing. Bootstrap is fully attributed from the
  first moment the system exists.

# 15 — Login response time reveals whether an email address exists

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **5 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Category** | Information disclosure — user enumeration (OWASP A07)                 |
| **Files**    | [login.ts:74-90](../../server/src/controllers/auth/login.ts#L74-L90), [registration.ts:19-25](../../server/src/controllers/auth/registration.ts#L19-L25), [createUser.ts:34-40](../../server/src/controllers/users/createUser.ts#L34-L40) |

---

## The finding

The login handler branches before doing the expensive work:

```ts
// server/src/controllers/auth/login.ts:74
const userInfo = await pool.query("SELECT * FROM users WHERE email = $1", [normalizedEmail]);
if (userInfo.rows.length === 0) {
  await registerFailedLoginAttempt();
  throw AppError.unauthorized(INVALID_LOGIN_MESSAGE);      // <-- returns in ~2 ms
}
const user = userInfo.rows[0];

const isPasswordValid = await compareHashStrings(unencryptedPassword, user.password);
if (!isPasswordValid) {
  await registerFailedLoginAttempt();
  throw AppError.unauthorized(INVALID_LOGIN_MESSAGE);      // <-- returns in ~80-120 ms
}
```

For an unknown email, the request costs one indexed lookup. For a known email, it
additionally costs a bcrypt comparison at `SALT_ROUNDS=10` — deliberately
expensive, by design, roughly 50–150 ms depending on hardware.

The **message** is identical (`INVALID_LOGIN_MESSAGE = "Invalid email or
password"`), which is correct and clearly intentional. The **timing** is not, and
the gap is one to two orders of magnitude — far above measurement noise, even
over a network.

### The secondary, louder oracle

`registration` and `createUser` both leak membership directly, with no timing
analysis required:

```ts
// server/src/controllers/auth/registration.ts:19
const existingUser = await pool.query("SELECT 1 FROM users WHERE email = $1", [email]);
if ((existingUser.rowCount ?? 0) > 0) {
  throw AppError.badRequest("User already exists with this email");
}
```

`createUser` requires `create:user` so it is not anonymous, but `registration` is
[completely unauthenticated](./14.auth-router-is-not-actually-protected.md) — and
while it is normally locked by the `godExists` check, that check runs *after* this
one. So on a bootstrapped system, `POST /api/auth/register` is a free, anonymous
email-existence oracle that returns a distinguishable 400 before it ever reaches
the lock.

## Why it matters

Enumeration is a force multiplier, not a breach. Its value is that it converts a
credential-stuffing attack from "spray 10 million leaked credentials at the
endpoint" into "confirm which 400 of these emails exist here, then spray only
those" — a 25,000× reduction in the volume that has to get past your rate
limiter. Given that the limiter
[fails open when Redis is unavailable](./07.rate-limiters-fail-open.md) and that
the password floor is [four characters](./18.weak-password-policy.md), that
reduction matters here more than it would in a hardened system.

It is also a privacy leak in its own right. For an IAM console, confirming *"this
person has an account on this system"* can be sensitive independent of any
password — it discloses organisational membership.

Honest severity framing: this ranks 5, not higher, because
[Vulnerability 02](./02.overpermissive-default-user-role.md) already lets **any
authenticated account** dump every email address in the system via
`GET /api/users`. Against an attacker who has any foothold, timing analysis is
redundant. This finding matters for the fully-anonymous attacker, and it matters
*after* finding 02 is fixed — at which point it becomes the remaining enumeration
path. Fix 02 first; then this one stops being redundant and starts being the
front door.

## Exploit walkthrough

```bash
# Anonymous. Measure total request time for a known-good vs random address.
probe () {
  curl -s -o /dev/null -w '%{time_total}\n' -X POST localhost:8000/api/auth/login \
    -H 'Content-Type: application/json' \
    -d "{\"email\":\"$1\",\"password\":\"wrong-password-here\"}"
}

probe "definitely-not-a-user-9f3a@nowhere.example"   # 0.004
probe "definitely-not-a-user-1c7b@nowhere.example"   # 0.003
probe "admin@corp.example"                            # 0.118   <-- exists
probe "alice@corp.example"                            # 0.109   <-- exists
```

The signal is unambiguous with a single sample. No statistics needed.

The registration oracle is even simpler:

```bash
curl -s -X POST localhost:8000/api/auth/register -H 'Content-Type: application/json' \
  -d '{"fullname":"Probe Name","email":"admin@corp.example","password":"xxxx"}'
# -> 400 "User already exists with this email"          <-- exists

curl -s -X POST localhost:8000/api/auth/register -H 'Content-Type: application/json' \
  -d '{"fullname":"Probe Name","email":"nobody@nowhere.example","password":"xxxx"}'
# -> 403 "Registration is locked. App already initialized with a super-admin."   <-- does not exist
```

## The fix

### 1. Always pay the bcrypt cost

Compare against a fixed dummy hash when the user is not found, so both branches
do identical work:

```ts
// server/src/utils/encryptStrings.ts
// A real bcrypt hash of a value nobody will ever submit. Generated once with
// SALT_ROUNDS matching production, so the comparison cost matches a real one.
const DUMMY_PASSWORD_HASH =
  "$2b$10$N9qo8uLOickgx2ZMRZoMy.Mrq4pXwEeuMcHiLTBqRoBhLBP0V0Sf6";

/**
 * Always performs a full bcrypt comparison, even when there is no user, so the
 * response time does not reveal whether the account exists.
 */
async function verifyPasswordConstantTime(
  candidate: string,
  storedHash: string | undefined,
): Promise<boolean> {
  const hash = storedHash ?? DUMMY_PASSWORD_HASH;
  const matches = await compareHashStrings(candidate, hash);
  return storedHash !== undefined && matches;
}
```

```ts
// server/src/controllers/auth/login.ts -- restructured
const userInfo = await pool.query("SELECT * FROM users WHERE email = $1", [normalizedEmail]);
const user = userInfo.rows[0];   // may be undefined

const isPasswordValid = await verifyPasswordConstantTime(unencryptedPassword, user?.password);

// Both the missing-user and wrong-password cases converge here, having done the
// same work. The is_active check joins them (see Vulnerability 03).
if (!isPasswordValid || !user.is_active) {
  await registerFailedLoginAttempt();
  throw AppError.unauthorized(INVALID_LOGIN_MESSAGE);
}
```

`DUMMY_PASSWORD_HASH` must be regenerated if `SALT_ROUNDS` changes, or the cost
diverges again. Better: derive it at startup —
`await bcrypt.hash(randomUUID(), env.SALT_ROUNDS)` — one hash on boot, always in
step with the configured cost, and not a constant sitting in source. Do this in a
module-level `await` in `encryptStrings.ts`.

### 2. Close the registration oracle

Move the existence check *after* the bootstrap lock, and collapse the two failure
modes into one message:

```ts
// server/src/controllers/auth/registration.ts
// 1. Bootstrap lock first -- an anonymous caller must not get past this line
//    for any reason, including "that email is taken".
if (!env.BOOTSTRAP_TOKEN /* ...or the godExists check... */) {
  throw AppError.forbidden("Registration is disabled.");
}
// 2. Only now does the existence check run, and only for a caller who has
//    already proven they may bootstrap.
```

With [Vulnerability 14](./14.auth-router-is-not-actually-protected.md)'s
`BOOTSTRAP_TOKEN` in place this resolves itself — an anonymous caller never
reaches the existence check at all.

For `createUser` (which requires `create:user`), leaving the explicit
"User already exists" message is fine and good UX: the caller is a trusted
administrator who legitimately needs to know. Do not over-apply this fix.

### 3. Accept what you cannot fix

Two residual oracles are not worth closing:

- **The `23505` unique-violation path.** If two registrations race, the database
  constraint fires and `errorHandler` returns `409 "Record already exists."` That
  is correct behaviour and only reachable by an authorised caller.
- **Password-reset flows**, if you add them later, must return the same
  "if an account exists, we sent an email" response regardless. Worth noting now
  so the pattern is established.

## Interaction with other findings

- **[Vulnerability 03](./03.deactivated-users-can-still-log-in.md)** — the
  `is_active` check **must** go inside the same converged branch shown above,
  after the bcrypt call. If you put it before `verifyPasswordConstantTime` "to
  avoid pointless hashing", you create a new timing oracle that distinguishes
  suspended accounts from nonexistent ones. **These two findings can contradict
  each other; the code above is the reconciled version.** Implement them together.
- **[Vulnerability 14](./14.auth-router-is-not-actually-protected.md)** — its
  `BOOTSTRAP_TOKEN` fix closes the registration oracle for free. Sequence 14
  first and step 2 here becomes a no-op verification.
- **[Vulnerability 02](./02.overpermissive-default-user-role.md)** — must be
  fixed first or this fix is cosmetic; any authenticated user can still just
  `GET /api/users`.
- **[Vulnerability 07](./07.rate-limiters-fail-open.md)** — enumeration plus an
  unbounded guessing rate is the full attack. Neither fix alone is sufficient.
- **No contradiction** with [Vulnerability 18](./18.weak-password-policy.md); the
  fixes are independent and compound.

## What you already got right here

- **`INVALID_LOGIN_MESSAGE` is a named constant** used identically in both failure
  branches. You explicitly recognised that the two cases must be
  indistinguishable to the caller — the intent is unmistakable in the code, and
  it is only the timing channel that betrays it. That is a much better starting
  point than code that says *"user not found"* in one branch.
- **`registerFailedLoginAttempt()` is called on both branches**, so the
  brute-force counter increments for unknown emails too. Many implementations only
  count failures against real accounts, which lets an attacker probe for free.
- **The failure key is `sha256(email|ip)`**, so the rate limiter can distinguish
  per-account attacks without storing email addresses in Redis. Privacy-preserving
  and correct.
- **Email normalisation before lookup** (`parseEmail` lowercases and trims), so
  `Admin@Corp.Example` and `admin@corp.example` share one rate-limit bucket rather
  than giving an attacker free extra attempts through case variation.
- `clearRateLimitKey(loginFailureKey)` on success — the failure counter resets
  once the user proves who they are. Correct, and easy to forget.

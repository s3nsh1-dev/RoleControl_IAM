## The finding

`auditDBMutation` takes an optional `db` that defaults to the pool:

```ts
// server/src/utils/helper.ts:137
const auditDBMutation = async ({
  actorId, actionType, resourceType, resourceId,
  oldValues = null, newValues = null, metadata = null,
  db = pool,                                            // <-- silent default
}: AuditDBMutationInput) => {
  const auditLogResult = await db.query<{ id: number }>(
    `INSERT INTO audit_logs (...) VALUES ($1,...,$7) RETURNING id`, [...]);
  if ((auditLogResult.rowCount ?? 0) !== 1) {
    throw AppError.internal("Failed to create audit log entry");
  }
  return auditLogResult.rows[0];
};
```

Thirteen of the fifteen call sites pass `db: client`. Two do not:

```ts
// server/src/controllers/permission/createPermission.ts:29
// No transaction at all -- straight pool queries.
const result = await pool.query(
  `INSERT INTO permissions (action, resource, description)
     VALUES ($1, $2, $3) RETURNING id, action, resource, description`,
  [action, resource, description],
);
if (result.rowCount === 0) throw AppError.badRequest("Permission not created");

await auditDBMutation({                    // <-- defaults to `pool`
  actorId, actionType: "create", resourceType: "permission",
  resourceId: result.rows[0].id, newValues: result.rows[0],
});
```

```ts
// server/src/controllers/permission/removePermission.ts:32
const deletedPermission = await pool.query(
  `DELETE FROM permissions WHERE id = $1
     RETURNING id, action, resource, description`, [permissionId]);
if ((deletedPermission.rowCount ?? 0) === 0) throw AppError.notFound("Permission not found");

await auditDBMutation({                    // <-- defaults to `pool`
  actorId, actionType: "delete", resourceType: "permission",
  resourceId: deletedPermission.rows[0].id,
  oldValues: deletedPermission.rows[0], newValues: null,
});
```

Neither controller opens a transaction. The mutation and its audit entry are two
independent auto-committed statements, possibly on two different pooled
connections.

### The related, subtler case

`assignPermission` and `revokePermission` *do* pass `db: client` and *do* run in a
transaction — but they call `checkRolePermissions` **before** `BEGIN`, on the bare
pool:

```ts
// server/src/controllers/role_permissions/assignPermission.ts:33
const client = await pool.connect();
try {
  await checkRolePermissions(actorId, "assign", "permission");   // pool, outside the txn
  await client.query("BEGIN");
```

That is the connection-acquisition problem covered in
[Vulnerability 08](./08.pool-starvation-from-permission-checks-inside-transactions.md).
Mentioned here because it is the same root cause — a helper that silently reaches
for the global pool instead of taking the caller's connection.

## Why it matters

An audit log's value rests on one property: **every mutation has exactly one
entry, and every entry corresponds to a real mutation.** These two controllers
can violate it in both directions.

**Direction 1 — a mutation with no audit entry.** If the `INSERT INTO audit_logs`
fails after the permission `INSERT`/`DELETE` has already committed, the mutation
stands and the record does not. `auditDBMutation` throws
`AppError.internal("Failed to create audit log entry")`, the client sees a 500,
and the operator's reasonable conclusion is "it failed, nothing happened." The
permission is gone. Nothing in the log says who removed it.

Realistic triggers: pool exhaustion (very plausible given
[Vulnerability 08](./08.pool-starvation-from-permission-checks-inside-transactions.md)),
the `audit_logs_action_type_check` constraint rejecting a value, a connection
dropped between the two statements, or the process being killed in the gap.

**Direction 2 — an audit entry for a phantom mutation.** Less likely here, but the
inverse hazard exists whenever the two writes are independent.

The specific operations affected make this worse than it sounds.
`removePermission` is exactly the endpoint that can
[brick the RBAC system](./12.rbac-self-destruct-via-role-and-permission-deletion.md),
because `ON DELETE CASCADE` strips the permission from every role at once. Losing
the audit entry for *that* is losing the only record of the most destructive
single request the API accepts.

There is also an inconsistency cost, which is the reason this is worth fixing even
though the window is small: thirteen controllers establish the pattern "mutations
run in a transaction and audit on the same client", and two silently do not. A
reader cannot tell which convention is intended. The `db = pool` default is what
makes the deviation invisible — nothing at the call site announces it.

## Exploit walkthrough

Not attacker-triggered; this is a reliability and forensics failure. Reproduce it
by making the audit insert fail:

```sql
-- Simulate a constraint the audit write violates.
ALTER TABLE audit_logs ADD CONSTRAINT tmp_block CHECK (resource_type <> 'permission');
```

```bash
curl -X DELETE localhost:8000/api/permissions/8 -b "access=$SUPER_ADMIN"
# -> 500 {"success":false,"status":"error","message":"Something went wrong!"}
```

```sql
SELECT id FROM permissions WHERE id = 8;
-- (0 rows)   <- the permission is gone

SELECT * FROM audit_logs WHERE resource_type = 'permission' ORDER BY id DESC LIMIT 1;
-- the deletion is absent

ALTER TABLE audit_logs DROP CONSTRAINT tmp_block;
```

The caller was told the request failed. The permission was deleted. There is no
record of who did it.

Compare with `deleteRole`, which does the same class of operation correctly — the
audit failure rolls the deletion back and the 500 is truthful.

## The fix

### 1. Wrap both controllers in transactions

```ts
// server/src/controllers/permission/removePermission.ts
const client = await pool.connect();
try {
  await client.query("BEGIN");

  await checkRolePermissions(actorId, "delete", "permission", client);

  const deletedPermission = await client.query(
    `DELETE FROM permissions WHERE id = $1
       RETURNING id, action, resource, description`,
    [permissionId],
  );
  if ((deletedPermission.rowCount ?? 0) === 0) {
    throw AppError.notFound("Permission not found");
  }

  await auditDBMutation({
    db: client,
    actorId,
    actionType: "delete",
    resourceType: "permission",
    resourceId: deletedPermission.rows[0].id,
    oldValues: deletedPermission.rows[0],
    newValues: null,
  });

  await client.query("COMMIT");

  new AppResponse(200, "Permission removed successfully", {
    permission: toPermission(deletedPermission.rows[0]),
  }).send(res);
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

Same shape for `createPermission`. This is the identical structure already used
in thirteen other controllers — you are not inventing a pattern, you are applying
the existing one.

### 2. Move the permission checks inside the transaction

In `assignPermission` and `revokePermission`, move `checkRolePermissions` to after
`BEGIN` and pass `client`:

```ts
const client = await pool.connect();
try {
  await client.query("BEGIN");
  await checkRolePermissions(actorId, "assign", "permission", client);   // inside
  // ...
```

This requires the `db` parameter from
[Vulnerability 08](./08.pool-starvation-from-permission-checks-inside-transactions.md).

### 3. Remove the silent default (the change that prevents recurrence)

The reason two call sites deviated is that omitting `db` is legal and invisible.
Make it explicit:

```ts
// server/src/types/commonTypes.ts
type AuditDBMutationInput = {
  db: QueryableDb;                    // <-- required, no default
  actorId: number | null;
  actionType: AUDIT_ACTIONS_TYPES;
  resourceType: AUDIT_RESOURCES_TYPES;
  resourceId: number | null;
  oldValues?: AuditPayloadType;
  newValues?: AuditPayloadType;
  metadata?: AuditPayloadType;
};
```

```ts
// server/src/utils/helper.ts
const auditDBMutation = async ({ db, actorId, /* ... */ }: AuditDBMutationInput) => { /* ... */ };
```

TypeScript now fails the build at every call site that omits it. A caller that
genuinely has no transaction writes `db: pool` deliberately, and a reviewer can
see it. With `strict: true` already on, this is a compile-time guarantee.

### 4. The durable version

[Suggestion 02](../suggestions/02.thread-transaction-client-through-helpers.md)
proposes a `withTransaction(fn)` wrapper:

```ts
const permission = await withTransaction(async (client) => {
  await checkRolePermissions(actorId, "delete", "permission", client);
  const deleted = await client.query(/* ... */);
  await auditDBMutation({ db: client, /* ... */ });
  return deleted.rows[0];
});
```

That removes the seventeen-line `try/catch/finally` boilerplate from fifteen
controllers and makes it impossible to forget the `ROLLBACK` or the `release()`.
If you are doing that suggestion, this finding is a free consequence of it.

## What you already got right here

- **Thirteen of fifteen call sites already pass `db: client`.** The convention is
  established, understood, and near-universal in this codebase. Two stragglers is
  a small deviation, not a misunderstanding.
- **The `QueryableDb` structural type** (`Pick<PoolClient | Pool, "query">`) is
  the correct abstraction that makes threading a client through helpers possible
  at all. You built the tool; this finding is about two places that did not reach
  for it.
- **`auditDBMutation` verifies `rowCount === 1` and throws on failure** rather
  than firing and forgetting. Inside a transaction that is exactly right — a
  failed audit write *should* abort the mutation. The behaviour is correct; only
  the transactional scope is missing in two places.
- **`try { BEGIN ... COMMIT } catch { ROLLBACK; throw } finally { release() }`** is
  reproduced faithfully in every transactional controller, including the `finally`
  release that prevents connection leaks. That consistency is why this fix is
  copy-and-adapt rather than design work.
- Both affected controllers are heavily commented with numbered steps
  (`// Step 5: insert the new permission row`), which makes the missing
  transaction boundary easy to see once you are looking for it.

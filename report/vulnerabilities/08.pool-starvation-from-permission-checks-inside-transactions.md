## The finding

`checkRolePermissions` is the only helper in `helper.ts` that does **not** accept
a `db` parameter. Compare it to its neighbours:

```ts
// server/src/utils/helper.ts:40
async function checkRolePermissions(
  actorId: number, action: ACTIONS_TYPES, resource: RESOURCES_TYPES,
): Promise<boolean> {
  const result = await pool.query(/* ... */);   // <-- hardcoded `pool`
  //                     ^^^^ no `db: QueryableDb = pool` parameter
}

async function getUserRoleNames(userId: number, db: QueryableDb = pool) { /* ... */ }
async function getUserEffectivePermissions(userId: number, db: QueryableDb = pool) { /* ... */ }
async function getHighestUserRole(userId: number, db: QueryableDb = pool) { /* ... */ }
```

Several controllers call it *after* checking out a client and opening a
transaction. `deletePost` is the clearest case:

```ts
// server/src/controllers/post/deletePost.ts:23
const client = await pool.connect();       // connection #1 checked out
try {
  await client.query("BEGIN");

  const existingPostQuery = await client.query(
    `SELECT ... FROM posts WHERE id = $1 FOR UPDATE`, [postId]);   // row lock held

  await checkRolePermissions(actorId, "delete", "post");
  //    ^^^ pool.query() -> transparently checks out connection #2,
  //        while connection #1 is still held with an open transaction
```

Same pattern in `createPost`, `createPostOnBehalf`, `updatePost`, `assignRole`,
`revokeRole`, `assignPermission`, `revokePermission`.

The pool is created with no options at all:

```ts
// server/src/config/db.connect.ts:7
const pool = new Pool({
  host: env.DB_HOST_NAME, port: env.DB_PORT, user: env.DB_USER,
  password: env.DB_PASSWORD, database: env.DB_NAME,
});
// node-postgres defaults: max = 10, connectionTimeoutMillis = 0 (wait forever)
```

**`connectionTimeoutMillis: 0` means an exhausted pool blocks forever, not for a
while.**

## Why it matters

This is a classic self-deadlock, and the default configuration turns it from a
latency spike into a permanent hang.

With `max: 10`, if ten requests reach the `checkRolePermissions` line
simultaneously, all ten connections are held inside open transactions and all ten
are waiting for an eleventh connection that will never be released. There is no
timeout. `pool.connect()` waits indefinitely. The process is up, the health check
(if there were one) passes, and **every subsequent database request queues behind
the deadlock until the process is restarted**.

Ten concurrent `DELETE /api/posts/:id` calls is not an exotic load. It is one
person clicking quickly, or the client's `rolePermissionsApi.listAll()` fan-out
pattern ([services.ts:158-176](../../client/src/api/services.ts#L158-L176)) which
already fires `Promise.all` over every page.

There is a second, quieter problem. The permission check runs on a **different
connection**, so it reads outside the transaction's snapshot and takes no part in
its locking. In `assignRole`:

```ts
await checkRolePermissions(actorId, "assign", "role");   // connection #2, no lock
await client.query("BEGIN");                             // connection #1
const actorHighestRole = await getHighestUserRole(actorId, client);  // correct
```

A concurrent `revokeRole` stripping the actor's `assign:role` permission can
commit between those two lines. The transaction proceeds on the strength of a
permission the actor no longer holds. It is a narrow window, but this is an IAM
system — narrow authorization windows are exactly what you do not want, and the
fix costs nothing.

Note the internal inconsistency: `getHighestUserRole(actorId, client)` on the very
next line is passed the transaction client. You already knew the right pattern.
`checkRolePermissions` was simply written before the `QueryableDb` convention
existed and never revisited.

## Exploit walkthrough

```bash
# Ten concurrent deletes against a pool of ten.
for i in $(seq 1 10); do
  curl -s -X DELETE "localhost:8000/api/posts/$i" -b "access=$SUPER_ADMIN" &
done
wait
# Requests never return. Every later request to any endpoint also hangs.
# The Node process is healthy; PostgreSQL shows 10 idle-in-transaction backends.
```

Verify from the database side:

```sql
SELECT pid, state, wait_event_type, query
  FROM pg_stat_activity
 WHERE state = 'idle in transaction';
-- ten rows, each parked after "SELECT ... FROM posts WHERE id = $1 FOR UPDATE"
```

No authentication above `create:post` is required to reach the `createPost`
variant of this, so any authenticated user can trigger it.

## The fix

Three changes. The first is the actual fix; the second and third stop this class
of bug from recurring.

### 1. Thread the transaction client through (the real fix)

```ts
// server/src/utils/helper.ts
async function checkRolePermissions(
  actorId: number,
  action: ACTIONS_TYPES,
  resource: RESOURCES_TYPES,
  db: QueryableDb = pool,          // <-- match every sibling helper
): Promise<boolean> {
  const result = await db.query(
    `SELECT 1
       FROM user_roles ur
       JOIN role_permissions rp ON rp.role_id = ur.role_id
       JOIN permissions p ON p.id = rp.permission_id
      WHERE ur.user_id = $1 AND p.action = $2 AND p.resource = $3
      LIMIT 1`,
    [actorId, action, resource],
  );

  if ((result.rowCount ?? 0) === 0) {
    throw AppError.forbidden(`You do not have permission to ${action} on ${resource}`);
  }
  return true;
}
```

Then at every call site inside a transaction, pass `client`:

```ts
// deletePost.ts, createPost.ts, createPostOnBehalf.ts, updatePost.ts,
// assignRole.ts, revokeRole.ts, assignPermission.ts, revokePermission.ts
await checkRolePermissions(actorId, "delete", "post", client);
```

The default parameter keeps the read-only list controllers (`listPosts`,
`listUsers`, `listSessions`, …) working unchanged — they legitimately have no
transaction and should keep using the pool.

### 2. Configure the pool so this fails loudly instead of hanging

```ts
// server/src/config/db.connect.ts
const pool = new Pool({
  host: env.DB_HOST_NAME,
  port: env.DB_PORT,
  user: env.DB_USER,
  password: env.DB_PASSWORD,
  database: env.DB_NAME,
  max: env.DB_POOL_MAX,                      // default 10
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000,            // never wait forever
  statement_timeout: 10_000,                 // no runaway query holds a connection
  idle_in_transaction_session_timeout: 15_000, // PostgreSQL reaps stuck transactions
});

pool.on("error", (error) => {
  console.error("Unexpected error on idle PostgreSQL client", error);
});
```

`connectionTimeoutMillis` alone converts this from "permanent outage requiring a
restart" to "a burst of 500s that recovers on its own". `idle_in_transaction_session_timeout`
means PostgreSQL cleans up after you even if the application misbehaves. These are
worth having regardless of change 1.

### 3. Make the pattern impossible to reintroduce

Once every authorization helper takes `db`, the safest next step is to stop
letting controllers call `pool` directly at all — that is
[Suggestion 02](../suggestions/02.thread-transaction-client-through-helpers.md)
(a `withTransaction(fn)` wrapper that hands the callback a client and makes the
bare pool inaccessible inside it). A lint rule banning `pool.query` in
`src/controllers/**` gets you 80% of the benefit for a few minutes of work.

## What you already got right here

- **`QueryableDb = Pick<PoolClient | Pool, "query">`** in
  [commonTypes.ts:31](../../server/src/types/commonTypes.ts#L31) is the exactly
  correct abstraction for this problem — a structural type that accepts both a
  pool and a client. You invented the right tool; `checkRolePermissions` is the
  one place it was not applied.
- **`try / catch ROLLBACK / finally client.release()`** appears in every
  transactional controller without exception. The `finally` release is the thing
  that most commonly gets forgotten and causes exactly this symptom by leaking
  connections; you never leak one.
- **`SELECT ... FOR UPDATE` before mutating** is used consistently
  (`deletePost`, `updatePost`, `updateUser`, `deleteUser`, `deleteRole`,
  `revokeSession`, `enforceSessionRowCapPerUser`). That is deliberate, correct
  pessimistic locking and it is why the concurrency story here is "one fixable
  bug" rather than "a pile of lost updates".
- `enforceSessionRowCapPerUser` takes a `PoolClient` explicitly rather than
  defaulting — the strictest version of the right pattern.

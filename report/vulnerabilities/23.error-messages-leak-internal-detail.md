# 23 — Auth failures concatenate internal error text into the 401 response

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **3 / 10**                                                            |

| **Files**    | [checkCookieSignature.middleware.ts:16-24](../../server/src/middleware/checkCookieSignature.middleware.ts#L16-L24), [jsonWebTokens.ts:16-22](../../server/src/utils/jsonWebTokens.ts#L16-L22), [errorHandler.middleware.ts:108-118](../../server/src/middleware/errorHandler.middleware.ts#L108-L118) |

## The finding

`checkCookieSignature` catches the verification error and appends its message to
the response:

```ts
// server/src/middleware/checkCookieSignature.middleware.ts:16
} catch (error) {
  const errorMessage =
    error instanceof Error ? error.message : "Token verification failed";
  throw AppError.unauthorized(
    "Invalid user session. Please login again. " + errorMessage,   // <-- concatenated
  );
}
```

`AppError.unauthorized` produces a 401 with `isOperational = true`, so
`errorHandler` passes the message through verbatim to the client:

```ts
// server/src/middleware/errorHandler.middleware.ts
message = err.isOperational ? err.message : "Something went wrong!";
```

What ends up in `errorMessage` depends on which layer threw. `verifyToken` wraps
most cases:

```ts
// server/src/utils/jsonWebTokens.ts:16
} catch (error) {
  throw AppError.unauthorized("Failed to verify JWT token, Please login again");
}
```

so the common response is the mildly redundant:

```json
{ "success": false, "status": "fail",
  "message": "Invalid user session. Please login again. Failed to verify JWT token, Please login again" }
```

But `verifyToken` throws `AppError.unauthorized("Invalid token payload")`
**outside** that `try` block — that check runs after `jwt.verify` succeeds:

```ts
const decoded = jwt.verify(token, env.JWT_SECRET, options);
if (typeof decoded !== "object" || decoded === null || !("uId" in decoded)) {
  throw AppError.unauthorized("Invalid token payload");     // inside try -- gets rewrapped
}
```

That one is inside the `try`, so it too gets flattened. The genuine leak is
narrower than it first appears: **`jwt.verify`'s own error types
(`TokenExpiredError`, `JsonWebTokenError`, `NotBeforeError`) never reach the
client**, because `verifyToken` swallows them.

So the accurate assessment is: the concatenation is a **latent** leak rather than
an active one. Any future refactor that lets a raw error through — removing
`verifyToken`'s try/catch, adding a database call to the middleware
([Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md)
does exactly this), or a `TypeError` from `req.cookies` being undefined — will
publish its message directly.

That last case is reachable today. If `cookieParser()` has not run for a route,
`req.cookies` is `undefined` and `req.cookies["access"]` throws:

```json
{ "message": "Invalid user session. Please login again. Cannot read properties of undefined (reading 'access')" }
```

### Two related, smaller items

**Stack traces in development are keyed on `NODE_ENV`, which defaults to
`development`:**

```ts
// server/src/middleware/errorHandler.middleware.ts:115
...(env.NODE_ENV === "development" && trace && { trace }),
```

The check is correct. The risk is that `NODE_ENV` defaults to `"development"` in
[envHelper.ts:20](../../server/src/utils/envHelper.ts#L20), so a deployment that
forgets to set it ships full stack traces — absolute file paths, dependency
versions, internal function names — on every 500.

**Zod validation errors are joined and returned in full:**

```ts
message = err.issues.map((issue) => issue.message).join(", ");
details = err.issues.map((issue) => ({ code: issue.code, path: issue.path.map(String), message: issue.message }));
```

This is correct and desirable for a client-facing API — the client's toast needs
it. Worth knowing it exposes your exact schema shape (field names, constraints),
which is already public via
[the OpenAPI document](./13.unauthenticated-openapi-and-docs-exposure.md) anyway.
No change needed.

## Why it matters

Low severity, and I want to be honest about why it is on the list at all.

**What it costs today:** very little. The messages that actually reach the client
are your own strings. The user-visible cost is a confusing double sentence in the
UI — `sonner` renders `error.message` directly in a toast
([client.ts:107-110](../../client/src/api/client.ts#L107-L110)), so users see
*"Invalid user session. Please login again. Failed to verify JWT token, Please
login again"*. That is a polish issue.

**Why fix it anyway:** the pattern `AppError.unauthorized(ourMessage + theirMessage)`
is a template. It says "attaching upstream error text to a client response is how
we do things here," and it will be copied. The three refactors most likely to
happen next to this file — adding a session lookup, adding audit logging, adding
a `type` claim check — all introduce error sources whose messages should not be
public. Fixing the two-line pattern now costs nothing; fixing it after it has
been copied into six places costs an afternoon.

There is also a small operational cost: because the internal detail goes to the
*client* and not to a log, an operator debugging a 401 storm has nothing to look
at. The information is being sent to exactly the wrong audience.

## The fix

### 1. Log internally, respond generically

```ts
// server/src/middleware/checkCookieSignature.middleware.ts
const checkCookieSignature = asyncMiddleware(async function (
  req: Request, _res: Response, _next: NextFunction,
) {
  const accessToken: unknown = req.cookies?.["access"];

  if (typeof accessToken !== "string" || accessToken.length === 0) {
    throw AppError.unauthorized("Invalid user session. Please login again.");
  }

  try {
    const userPayload = verifyToken<USER_JWT_PAYLOAD_TYPE>(accessToken);
    if (userPayload.type !== "access") {            // see Vulnerability 01
      throw AppError.unauthorized("Invalid user session. Please login again.");
    }
    req.user = userPayload;
  } catch (error) {
    // Detail goes to the operator, never to the caller.
    console.warn("Access token verification failed", {
      reason: error instanceof Error ? error.message : String(error),
      path: req.path,
    });
    throw AppError.unauthorized("Invalid user session. Please login again.");
  }
});
```

Three changes: `req.cookies?.` and the explicit type check remove the `TypeError`
path; the internal reason is logged rather than returned; the response is one
clean sentence.

### 2. Distinguish "expired" from "invalid" — carefully

Clients benefit from knowing a token merely expired, since that is the trigger for
a silent refresh rather than a redirect to login. Today
[client.ts](../../client/src/api/client.ts) treats every 401 identically and
attempts a refresh, which works but wastes a round trip on genuinely invalid
tokens.

If you want the distinction, express it as a **code**, not as a message:

```ts
// server/src/utils/jsonWebTokens.ts
import jwt, { TokenExpiredError } from "jsonwebtoken";

try {
  const decoded = jwt.verify(token, env.JWT_SECRET, options);
  // ...
} catch (error) {
  if (error instanceof TokenExpiredError) {
    throw new AppError(401, "Session expired. Please login again.", true, "TOKEN_EXPIRED");
  }
  throw new AppError(401, "Invalid user session. Please login again.", true, "TOKEN_INVALID");
}
```

This requires adding an optional `code` to `AppError` and surfacing it in
`errorHandler`'s response body. **Only do this if the client will act on it** —
otherwise it is a distinction that helps an attacker enumerate token states more
than it helps you. Given the client currently refreshes on any 401 and that works
correctly, the honest recommendation is: skip step 2 unless
[Suggestion 12](../suggestions/12.axios-refresh-interceptor-correctness.md) gives
you a concrete reason to want it.

### 3. Make production-mode stack suppression not depend on remembering `NODE_ENV`

```ts
// server/src/middleware/errorHandler.middleware.ts
const exposeStackTraces = env.NODE_ENV !== "production";
// ...
...(exposeStackTraces && trace ? { trace } : {}),
```

Inverting the condition means the *unsafe* behaviour requires an explicit
non-production value, rather than the safe behaviour requiring an explicit
production value. Combined with
[Vulnerability 09](./09.jwt-secret-and-credentials-default-to-placeholders.md)'s
startup validation (which should make `NODE_ENV` required, not defaulted), this
closes the "forgot to set it" case from both directions.

### 4. Log unexpected errors server-side

`errorHandler` currently returns 500s to the client but never logs the underlying
error for non-`AppError` cases, so an unexpected exception produces
`"Something went wrong!"` for the user and **nothing at all** for the operator:

```ts
// server/src/middleware/errorHandler.middleware.ts -- before the response
if (statusCode >= 500) {
  console.error("Unhandled error", {
    message: err instanceof Error ? err.message : String(err),
    stack: trace,
    method: _req.method,
    path: _req.path,
  });
}
```

This is arguably the most valuable change in this finding — it is the difference
between a debuggable 500 and an invisible one. Note `_req` will need renaming to
`req` since it is now used.

## Interaction with other findings

- **[Vulnerability 01](./01.jwt-token-confusion-and-session-revocation-bypass.md)**
  rewrites this exact middleware to add a `type` check and a session lookup. **Do
  both edits in one pass** — the code in step 1 already includes the `type` check
  so the two do not fight. The session lookup introduces a database error path,
  which is precisely the error source that must not be concatenated into a
  response.
- **[Suggestion 06](../suggestions/06.structured-logging-and-request-ids.md)** —
  steps 1 and 4 use `console.warn` / `console.error` as placeholders. That
  suggestion replaces the 40 existing `console.*` calls with a structured logger
  and a request id. **Write these log lines with that in mind** (structured
  objects, not string concatenation) so the migration is mechanical.
- **[Suggestion 12](../suggestions/12.axios-refresh-interceptor-correctness.md)**
  — the only reason to implement step 2. Decide there, not here.
- **[Suggestion 18](../suggestions/18.error-taxonomy-and-client-mapping.md)** —
  the `code` field in step 2 is that suggestion's core idea. If you do it, do it
  systematically across all error types rather than only for tokens.
- **No contradiction** with anything. Every change here is strictly narrowing what
  leaves the process.

## What you already got right here

- **`errorHandler` distinguishes operational from non-operational errors**
  (`err.isOperational ? err.message : "Something went wrong!"`). That single line
  is the correct core of safe error handling, and it means an
  `AppError.internal()` never leaks its message. You built the mechanism; this
  finding is about one call site routing around it.
- **Stack traces are already gated on `NODE_ENV`**, with a comment explaining
  why. The reasoning is right; only the default value undermines it.
- **PostgreSQL error codes are translated to safe, human-readable messages**
  (`23505` → "Record already exists.", `22001` → "One of the fields is longer than
  the database allows."). Raw `pg` errors — which contain table names, constraint
  names and sometimes column values — never reach the client. That is a genuinely
  well-designed piece of the error handler and it is the kind of thing that
  usually leaks.
- **`AppError` is a proper `Error` subclass** with `Object.setPrototypeOf`,
  `captureStackTrace`, and a clean set of static factories. The
  `statusCode >= 500 ? "error" : "fail"` derivation means the status field can
  never contradict the code.
- **`ZodError` is handled as a first-class case** with structured `details`,
  giving the client field-level paths rather than a flattened string. The client's
  `ApiClientError` carries that `details` array through. That is a
  well-considered contract on both ends.

## The finding

Every rate limiter in the system has the same two escape hatches, and both let
the request through:

```ts
// server/src/middleware/loginRateLimiting.middleware.ts:14
if (!isRedisRateLimitReady()) {
  console.warn("Redis is not ready. Bypassing login IP rate limiter.");
  return;                                    // <-- request proceeds
}

const ipCheck = await allowSlidingWindow(ipKey, limit, windowMs);

if (!ipCheck) {
  console.warn("Login IP rate limiter degraded. Bypassing request.");
  return;                                    // <-- request proceeds
}
```

`allowSlidingWindow` returns `null` on *any* Redis error:

```ts
// server/src/utils/rateLimit.util.ts:109
} catch (error) {
  console.error("Rate limiter Redis check failed, bypassing:", error);
  return null;
}
```

The same shape is repeated verbatim in the global, refresh, and authenticated
limiters, and inside `registerFailedLoginAttempt` in the login controller. There
are five independent copies of "if the limiter is unavailable, allow everything".

`redisClient` is configured with an unbounded reconnect loop
([redis.connect.ts:11-15](../../server/src/config/redis.connect.ts#L11-L15)), so
when Redis goes away the process stays up, logs a warning per request, and serves
traffic with **zero** rate limiting — indefinitely, silently, at whatever volume
the caller wants.

## Why it matters

Fail-open is a legitimate design choice for a *throughput* limiter, where the
limiter exists to protect your own capacity and dropping it degrades gracefully.
It is not a legitimate choice for an *authentication* limiter, where the limiter
is the only thing standing between an attacker and an offline-speed password
guessing loop against a live endpoint.

Your configuration makes the distinction stark:

| Limiter | Purpose | Correct failure mode |
| --- | --- | --- |
| `RATE_LIMIT_LOGIN_FAIL_LIMIT=5` per email+IP / 15 min | **Security control.** This is the credential-stuffing defence. | **Closed** |
| `RATE_LIMIT_LOGIN_IP_LIMIT=20` per IP / 15 min | Security control. | **Closed** |
| `RATE_LIMIT_REFRESH_*` | Security control (token-guessing, session abuse). | **Closed** |
| `RATE_LIMIT_GLOBAL_IP_LIMIT=100` / min | Capacity protection. | Open is defensible |
| `RATE_LIMIT_USER_LIMIT=60` / min | Capacity protection. | Open is defensible |

All five currently fail open.

The attacker does not need to compromise Redis, only to make it *unreachable from
the API process*. If Redis is on the same host, a memory-pressure OOM kill does
it. If it is a managed service, a maintenance failover window does it — for free,
on a published schedule. And because the bypass is logged with `console.warn` to
stdout with no metric and no alert, nobody finds out. There is no counter, no
health endpoint, and no readiness probe that reports "the security controls are
currently off" (see [Suggestion 07](../suggestions/07.health-readiness-and-graceful-shutdown.md)).

Worth being precise about the residual protection: bcrypt at
`SALT_ROUNDS=10` costs roughly 50–100 ms per attempt, and Node handles bcrypt on
the libuv threadpool (default 4 threads). That caps you at roughly 40–80 guesses
per second per instance — a real speed bump, but it is *incidental* CPU cost, not
a control. Against a weak password (and the schema permits **4-character**
passwords — see [Vulnerability 18](./18.weak-password-policy.md)) it is nowhere
near enough. It also means the attack doubles as a CPU exhaustion DoS.

## Exploit walkthrough

```bash
# Precondition: Redis is unavailable to the API. No privileged access required --
# a failover, an OOM kill, or a maintenance window is enough.

# Confirm the bypass (server logs "Redis is not ready. Bypassing..." per request):
for i in $(seq 1 500); do
  curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8000/api/auth/login \
    -H 'Content-Type: application/json' \
    -d "{\"email\":\"admin@corp.example\",\"password\":\"guess-$i\"}"
done | sort | uniq -c
#    500 401        <- not a single 429. The 5-attempt limit never engages.
```

Combined with `GET /api/users` leaking every email address in the system
([Vulnerability 02](./02.overpermissive-default-user-role.md)), the attacker
starts with a complete, accurate target list.

## The fix

Make the failure mode a **property of the limiter**, decided once at the call
site, instead of a hardcoded `return` repeated five times.

### 1. Give `allowSlidingWindow` an explicit policy

```ts
// server/src/utils/rateLimit.util.ts
type FailureMode = "open" | "closed";

type RateLimitDecision =
  | { outcome: "allowed"; remaining: number }
  | { outcome: "limited"; retryAfterMs: number }
  | { outcome: "unavailable" };

const consumeRateLimit = async (
  key: string,
  limit: number,
  windowMs: number,
): Promise<RateLimitDecision> => {
  if (!isRedisRateLimitReady()) return { outcome: "unavailable" };
  try {
    const [allowed, , remaining, retryAfterMs] = (await redisClient.eval(
      slidingWindowLuaScript, 1, key,
      String(limit), String(windowMs), String(Date.now()), makeRateLimitMember(),
    )) as [number, number, number, number];

    return Number(allowed) === 1
      ? { outcome: "allowed", remaining: Number(remaining) }
      : { outcome: "limited", retryAfterMs: Number(retryAfterMs) };
  } catch (error) {
    console.error("Rate limiter Redis check failed:", error);
    return { outcome: "unavailable" };
  }
};

const enforceRateLimit = async (
  res: Response,
  key: string,
  limit: number,
  windowMs: number,
  options: { failureMode: FailureMode; message: string },
) => {
  const decision = await consumeRateLimit(key, limit, windowMs);

  if (decision.outcome === "limited") {
    throwRateLimitError(res, decision.retryAfterMs, options.message);
  }

  if (decision.outcome === "unavailable") {
    rateLimiterUnavailable.inc();               // <-- see step 3
    if (options.failureMode === "closed") {
      throw AppError.internal(
        "Authentication is temporarily unavailable. Please try again shortly.",
      );
    }
    console.warn(`Rate limiter unavailable, failing open: ${key}`);
  }
};
```

Note the fail-closed response is a **503-shaped internal error, not a 429**.
`AppError.internal` is non-operational, so `errorHandler` returns a generic
message and does not leak that Redis is down. Do not use 429 here — that would
tell an attacker precisely when the limiter is degraded.

### 2. Declare the mode at each call site

```ts
// loginRateLimiting.middleware.ts
await enforceRateLimit(res, `rate:login:ip:${clientIp}`,
  env.RATE_LIMIT_LOGIN_IP_LIMIT, env.RATE_LIMIT_LOGIN_IP_WINDOW_MS,
  { failureMode: "closed", message: "Too many login attempts from this IP. Please try again later." });

// globalRateLimiting.middleware.ts
await enforceRateLimit(res, `rate:global:ip:${clientIp}`,
  env.RATE_LIMIT_GLOBAL_IP_LIMIT, env.RATE_LIMIT_GLOBAL_IP_WINDOW_MS,
  { failureMode: "open", message: "Too many requests. Please try again later." });
```

Login and refresh limiters (and `registerFailedLoginAttempt`) → `"closed"`.
Global and authenticated limiters → `"open"`.

Make the mode configurable if you want an operator escape hatch:

```ts
// envHelper.ts
RATE_LIMIT_AUTH_FAILURE_MODE: z.enum(["open", "closed"]).default("closed"),
```

Default closed. An operator who consciously accepts the risk during an incident
can flip it; nobody gets it by accident.

### 3. Make the degraded state visible

The single most valuable line in this fix is a counter. Even without a metrics
stack, expose it on the health endpoint from
[Suggestion 07](../suggestions/07.health-readiness-and-graceful-shutdown.md):

```ts
// GET /healthz
{ "status": "degraded", "redis": "disconnected", "rateLimitersEnforcing": false }
```

"The security controls are off right now" must be answerable without grepping
stdout.

## Interaction with other findings

- **[Vulnerability 18](./18.weak-password-policy.md)** — a 4-character minimum
  password and a bypassable rate limiter are the same attack from two ends. Fixing
  either one raises the bar; fixing both is what actually closes it.
- **[Vulnerability 02](./02.overpermissive-default-user-role.md)** — supplies the
  attacker's email list. Independent fixes, compounding benefit.
- **[Vulnerability 22](./22.trust-proxy-misconfiguration-enables-limit-bypass.md)**
  — the *other* way to defeat these limiters, by spoofing the key rather than
  removing the check. Both must be fixed; neither substitutes for the other.
- **[Suggestion 07](../suggestions/07.health-readiness-and-graceful-shutdown.md)**
  — step 3 depends on it. Sequence 07-suggestion first or fold it in.
- **Contradiction to watch:** fail-closed on login means **Redis becomes a hard
  dependency for authentication**. That is a real availability trade, and it is
  the correct one for an IAM system — but it means
  [Suggestion 05](../suggestions/05.postgres-and-redis-production-config.md)
  (Redis connection tuning, timeouts, and a bounded retry strategy) stops being
  optional. Land them together, or you will trade a security bug for an outage.

## What you already got right here

- **The sliding-window Lua script is genuinely well done.** Doing
  `ZREMRANGEBYSCORE` + `ZCARD` + conditional `ZADD` + `PEXPIRE` atomically in one
  `EVAL` is the correct implementation. It avoids the burst artefacts of fixed
  windows and the race conditions of a read-then-write from the app. Most
  hand-rolled limiters get this wrong.
- **Layered keys**: per-IP *and* per-email+IP for login, per-IP *and* per-session
  for refresh, plus a global and a per-user tier. That is a thoughtful model, not
  a single blunt counter.
- **`hashSha256(email|ip)` as the failure key** avoids writing raw email
  addresses into Redis — a nice privacy-preserving touch that also gives you
  fixed-length keys.
- **`clearRateLimitKey` on successful login** so a legitimate user who fumbles
  their password four times is not penalised afterwards. Correct and frequently
  forgotten.
- The bypass is *logged*. The behaviour is wrong, but it was a deliberate,
  documented decision rather than an oversight — which makes it a five-line fix
  instead of an investigation.

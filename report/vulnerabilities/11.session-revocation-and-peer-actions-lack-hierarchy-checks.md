# 11. An admin can revoke a super-admin's sessions; no session endpoint checks the hierarchy

|              |                                                                       |
| ------------ | --------------------------------------------------------------------- |
| **Rank**     | **6 / 10**                                                            |
| **Side**     | **Server**                                                            |
| **Category** | Broken access control — missing function-level authorization (OWASP A01) |
| **Files**    | [revokeSession.ts:16-19](../../server/src/controllers/sessions/revokeSession.ts#L16-L19), [revokeAllUserSessions.ts:14-17](../../server/src/controllers/sessions/revokeAllUserSessions.ts#L14-L17), [updatePost.ts:38-40](../../server/src/controllers/post/updatePost.ts#L38-L40), [helper.ts:23-38](../../server/src/utils/helper.ts#L23-L38) |

## The finding

Most of this codebase applies **two** authorization layers to privileged
operations: a capability check (`checkRolePermissions`) and a hierarchy check
(`canActorManageRole`). `deleteUser` is the model:

```ts
// server/src/controllers/users/deleteUser.ts
await checkRolePermissions(actorId, "delete", "user");           // layer 1: capability
// ...
const actorHighestRole  = await getHighestUserRole(actorId, client);
const targetHighestRole = await getHighestUserRole(targetUserId, client);
if (targetHighestRole && !canActorManageRole(actorHighestRole, targetHighestRole)) {
  throw AppError.forbidden("You cannot delete this user");       // layer 2: hierarchy
}
```

`assignRole`, `revokeRole`, `createUser`, `updateUser`, `deleteRole` and
`updateRole` all do this. The session controllers and `updatePost` do **only
layer 1**:

```ts
// server/src/controllers/sessions/revokeSession.ts:16
const actorId   = parsePositiveInt(req.user.uId, "actorId");
const sessionId = parsePositiveInt(req.params["sessionId"], "sessionId");
await checkRolePermissions(actorId, "revoke", "session");
// ...then straight to the UPDATE. The session's owner is never consulted.
```

```ts
// server/src/controllers/sessions/revokeAllUserSessions.ts:14
const targetUserId = parsePositiveInt(req.params["userId"], "userId");
await checkRolePermissions(actorId, "delete", "session");
// ...targetUserId is used only as a WHERE clause. No hierarchy check.
```

`revoke:session` is granted to **`admin`** in
[hierarchy.ts:40](../../server/src/config/hierarchy.ts#L40). So the gap is
directly reachable by a role that the hierarchy otherwise deliberately keeps
below super-admin.

`updatePost` has the same shape of omission:

```ts
// server/src/controllers/post/updatePost.ts:38
if (actorId !== existingPost.owner_id) {
  await checkRolePermissions(actorId, "update", "post");
}
// -> any holder of update:post may edit any post, including a super-admin's.
```

Contrast with `deletePost`, which explicitly reasons about the owner's rank:

```ts
// server/src/controllers/post/deletePost.ts:74
if (highestActorRole === "admin" && highestOwnerRole === "super-admin") {
  throw AppError.forbidden("Admin cannot delete a post owned by a super-admin");
}
```

Delete is guarded. Update is not. The rule was written down in one place and not
the other.

## Why it matters

Your hierarchy encodes an intent: *admins manage editors and users; only
super-admins manage admins and super-admins.* Two endpoints let an admin act
directly on a super-admin, which makes the hierarchy advisory rather than
enforced.

**Lockout is the real risk.** An admin can:

```bash
# Discover the super-admins (Vulnerability 02 makes this free)
curl -s -b "access=$ADMIN" 'localhost:8000/api/users?pageSize=100' \
  | jq -r '.data.users[] | select(.roleNames | index("super-admin")) | .id'
# -> 1

# Enumerate their sessions
curl -s -b "access=$ADMIN" 'localhost:8000/api/users/1/sessions' \
  | jq -r '.data.sessions[] | select(.is_active) | .id'
# -> 17, 18

# Kill them
curl -s -X PATCH -b "access=$ADMIN" localhost:8000/api/sessions/17/revoke
curl -s -X PATCH -b "access=$ADMIN" localhost:8000/api/sessions/18/revoke
```

The super-admin can log in again — this is a nuisance, not a permanent lockout —
but an admin who can repeat it in a loop can keep a super-admin out of their own
system during the window when the super-admin is trying to demote them. That is
a meaningful escalation of an insider's leverage.

`updatePost` is lower impact (content tampering, not privilege) but the
*inconsistency* is the finding: two controllers over the same resource disagree
about whether ownership rank matters, and a reader cannot tell which is intended.

### The `>=` problem underneath this

`canActorManageRole` returns `true` for equal ranks:

```ts
// server/src/utils/helper.ts:29
if (actorHighestRole === "super-admin") return true;   // including target = super-admin
```

So even where the hierarchy check *is* applied, one super-admin can delete,
demote or update another. `deleteUser` guards the specific case of deleting the
*last* super-admin, but `revokeRole` has no equivalent guard — a super-admin can
strip `super-admin` from every peer, one at a time, and there is no
"last super-admin" check on that path.

## The fix

### 1. Add the missing hierarchy checks

```ts
// server/src/controllers/sessions/revokeSession.ts -- after loading existingSession
const actorHighestRole  = await getHighestUserRole(actorId, client);
const targetHighestRole = await getHighestUserRole(existingSession.user_id, client);

if (!actorHighestRole) {
  throw AppError.forbidden("Actor does not have an assigned role");
}
// Revoking your own session is always allowed.
if (
  existingSession.user_id !== actorId &&
  targetHighestRole &&
  !canActorManageRole(actorHighestRole, targetHighestRole)
) {
  throw AppError.forbidden("You cannot revoke sessions for this user");
}
```

Note the self-exemption. Without it, an admin cannot log themselves out of a
stale device, which is a legitimate and common need.

Apply the identical block in `revokeAllUserSessions` using `targetUserId`.

For `updatePost`, mirror what `deletePost` already does:

```ts
// server/src/controllers/post/updatePost.ts
if (actorId !== existingPost.owner_id) {
  await checkRolePermissions(actorId, "update", "post", client);

  const actorHighestRole = await getHighestUserRole(actorId, client);
  const ownerHighestRole = await getHighestUserRole(existingPost.owner_id, client);
  if (!actorHighestRole) throw AppError.forbidden("Actor does not have an assigned role");
  if (ownerHighestRole && !canActorManageRole(actorHighestRole, ownerHighestRole)) {
    throw AppError.forbidden("You cannot update a post owned by this user");
  }
}
```

(The `client` fourth argument comes from
[Vulnerability 08](./08.pool-starvation-from-permission-checks-inside-transactions.md).)

### 2. Decide the peer-management semantics, once

`canActorManageRole` needs an explicit answer to "may a super-admin manage
another super-admin?". Both answers are defensible; leaving it implicit is not.

**Recommended:** strict rank comparison, with the last-super-admin invariant
enforced separately.

```ts
// after Vulnerability 06 / Suggestion 03 introduce a numeric rank
function canActorManageRole(actor: ActorRole, target: ActorRole): boolean {
  return actor.rank > target.rank;      // strict
}
```

Under strict `>`, super-admins cannot act on each other at all — no peer
demotion, no peer session revocation, no peer deletion. That is simple to reason
about and to test. The cost: a compromised super-admin can only be removed by
direct database access. If that is unacceptable, keep `>=` for super-admins only
and add a `SELECT COUNT(*) ... WHERE r.name = 'super-admin'` guard to
`revokeRole`, matching the one already in `deleteUser`.

Whichever you choose, **write it in one place** and make the session controllers,
post controllers, role controllers and user controllers all defer to it.

### 3. Extract the repeated block

The five-line "load both ranks, compare, throw" appears in eight controllers with
small variations. That variation is where the two omissions came from.

```ts
// server/src/utils/helper.ts
async function assertCanManageUser(
  actorId: number,
  targetUserId: number,
  db: QueryableDb,
  message = "You cannot perform this action on this user",
): Promise<void> {
  if (actorId === targetUserId) return;         // self-actions bypass hierarchy

  const [actorRole, targetRole] = await Promise.all([
    getHighestUserRole(actorId, db),
    getHighestUserRole(targetUserId, db),
  ]);

  if (!actorRole) throw AppError.forbidden("Actor does not have an assigned role");
  if (targetRole && !canActorManageRole(actorRole, targetRole)) {
    throw AppError.forbidden(message);
  }
}
```

Every call site becomes one line, and the next controller someone adds gets the
check for free.

## Interaction with other findings

- **[Vulnerability 06](./06.role-rename-privilege-escalation.md)** owns the
  `>` vs `>=` decision and the migration to numeric ranks. **Decide it there,
  apply it here.** If you implement this finding with string comparisons and then
  do finding 06, you rewrite `assertCanManageUser`. Sequence 06 first.
- **[Vulnerability 02](./02.overpermissive-default-user-role.md)** is the read
  side of the same problem — that finding stops an attacker *finding* the
  super-admins and their session ids; this one stops them *acting* on them. Fix
  both; each alone leaves half the attack.
- **[Vulnerability 08](./08.pool-starvation-from-permission-checks-inside-transactions.md)**
  — `assertCanManageUser` takes `db` for exactly the reason described there. Do
  not write it without the parameter.
- **[Suggestion 01](../suggestions/01.centralize-authorization-in-middleware.md)**
  — hierarchy checks need the *target row*, which middleware does not have. They
  must stay in controllers. The middleware handles the capability layer only;
  this finding is why that boundary exists.
- **No contradiction** with [Vulnerability 04](./04.password-change-does-not-revoke-sessions.md):
  the session revocation triggered by a password change is a *system* action, not
  an actor-on-target action, and should bypass `assertCanManageUser` entirely.

## What you already got right here

- **The two-layer model itself.** Separating "does this role have this capability"
  from "may this actor act on this specific target" is the correct decomposition,
  and you applied it in eight of ten places. The finding is about coverage, not
  design.
- **`deleteUser`'s last-super-admin guard**
  ([deleteUser.ts:46-56](../../server/src/controllers/users/deleteUser.ts#L46-L56))
  is a genuinely thoughtful invariant. Most people discover the need for it after
  locking themselves out of production.
- **Self-action guards** — `"You cannot delete yourself"`, `"You cannot assign
  roles to yourself"`, `"You cannot revoke roles from yourself"` — prevent the
  most common self-inflicted lockouts, and they are consistently phrased.
- **`deletePost`'s explicit admin-vs-super-admin rule**, complete with a comment
  block at the bottom of the file spelling out the intended semantics. That
  comment is what made this finding easy to spot: you documented the rule, so its
  absence in `updatePost` is visible rather than hidden.

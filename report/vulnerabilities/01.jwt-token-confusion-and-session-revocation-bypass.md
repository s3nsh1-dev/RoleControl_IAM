# 01. Refresh token works as an access token, and revoking a session does not log anyone out

## The finding

This is really two defects that combine into one much larger one. I am reporting
them together because fixing only one of them leaves the attack fully intact.

### Defect A: the access token has no `type` claim

`createUserPayload` builds two different payload shapes:

```ts
// server/src/utils/helper.ts:111
const createUserPayload = <T extends object>(user: any, type: "access" | "refresh"): T => {
  if (type === "refresh") {
    return {
      uId: parsePositiveInt(user.id, "user.id"),
      sId: parsePositiveInt(user.sessionId, "user_session.id"),
      type: "refresh",          // <-- refresh tokens are labelled
    } as T;
  }
  return {
    uId: parsePositiveInt(user.id, "user.id"),
    email: parseEmail(user.email, "user.email"),
                                 // <-- access tokens are NOT labelled
  } as T;
};
```

Both tokens are then signed with the **same secret**, the **same algorithm**, the
**same `issuer`** (`s3nsh1-dev`) and the **same `audience`** (`RBAC-users`)
([jsonWebTokens.ts:26-35](../../server/src/utils/jsonWebTokens.ts#L26-L35)).

The only thing `verifyToken` asserts about the payload is that `uId` exists:

```ts
// server/src/utils/jsonWebTokens.ts:14
if (typeof decoded !== "object" || decoded === null || !("uId" in decoded)) {
  throw AppError.unauthorized("Invalid token payload");
}
```

A refresh token contains `uId`. Therefore **a refresh token is a structurally
valid access token.** `checkCookieSignature` will happily accept it:

```ts
// server/src/middleware/checkCookieSignature.middleware.ts:13
const accessToken: string = req.cookies["access"];
const userPayload = verifyToken<USER_JWT_PAYLOAD_TYPE>(accessToken);
req.user = userPayload;
```

The refresh flow *does* check the direction (`if (refreshPayload.type !== "refresh")`
in [refreshToken.ts:37](../../server/src/controllers/auth/refreshToken.ts#L37)), so
an access token cannot be used as a refresh token. The check simply does not exist
in the other direction.

### Defect B: `checkCookieSignature` never consults the session table

The middleware verifies a signature and stops. It never asks:

- Does `user_sessions` still have a live row for this user?
- Was that session revoked?
- Does the user still exist / is the user still active?

Session state lives entirely in the database, and the access path never reads it.

## Why it matters

Your session management is built around a `user_sessions` table with
`revoked_at`, a `revokeSession` endpoint, a `revokeAllUserSessions` endpoint, and
a whole Sessions area in the UI. **None of it can actually terminate access.**

- Revoking a session sets `revoked_at`, `expires_at = NOW()` and
  `refresh_token_hash = 'REVOKED'`. That blocks *future refreshes* only.
- The already-issued access token keeps working until its own `exp`
  (`ACCESS_TOKEN_EXPIRES_IN=20m`).
- And because of Defect A, an attacker who holds the **refresh** token does not
  need to refresh at all. They paste it into the `access` cookie and get
  **`REFRESH_TOKEN_EXPIRES_IN` = 7 days** of authenticated API access that no
  admin action in your system can stop.

So the honest description of the current behaviour is: *"Revoke session" is a
label on a button that delays an attacker by at most 20 minutes, and by zero
minutes if they were clever about which cookie to reuse.* For an IAM product,
that is the single most damaging thing on this list.

## Exploit walkthrough

1. Attacker obtains a victim's cookies (XSS on a sibling subdomain, a stolen
   laptop, a shared machine, a proxy log — the usual). Both cookies are
   `httpOnly`, so this requires cookie-jar access rather than JS, but that is a
   normal threat model for a 7-day credential.
2. Admin notices, opens the Sessions page, clicks **Revoke** on the victim's
   session. The audit log records a clean `revoke:session` entry. The admin
   believes the incident is closed.
3. Attacker sends:
   ```
   GET /api/users HTTP/1.1
   Cookie: access=<the victim's REFRESH token>
   ```
4. `verifyToken` succeeds (valid signature, valid iss/aud, `uId` present, not
   expired for 7 days). `req.user.uId` is set to the victim's id.
5. Every downstream `checkRolePermissions(actorId, ...)` call reads the victim's
   *current* roles from the database and grants them. The attacker has the
   victim's full privileges for a week, with no session row backing it and no way
   for an operator to cut it off short of deleting the user or rotating
   `JWT_SECRET` globally.

## The fix

Three changes. Do all three; each closes a different door.

### 1. Label the access token and enforce the label

```ts
// server/src/utils/helper.ts
const createUserPayload = <T extends object>(
  user: any,
  type: "access" | "refresh",
): T => {
  if (type === "refresh") {
    return {
      uId: parsePositiveInt(user.id, "user.id"),
      sId: parsePositiveInt(user.sessionId, "user_session.id"),
      type: "refresh",
    } as T;
  }
  return {
    uId: parsePositiveInt(user.id, "user.id"),
    sId: parsePositiveInt(user.sessionId, "user_session.id"), // see change 2
    email: parseEmail(user.email, "user.email"),
    type: "access",
  } as T;
};
```

Add `type: "access"` to `USER_JWT_PAYLOAD_TYPE` in
[commonTypes.ts:15-18](../../server/src/types/commonTypes.ts#L15-L18), then reject
mismatches at the door:

```ts
// server/src/middleware/checkCookieSignature.middleware.ts
const userPayload = verifyToken<USER_JWT_PAYLOAD_TYPE>(accessToken);
if (userPayload.type !== "access") {
  throw AppError.unauthorized("Invalid user session. Please login again.");
}
```

> Prefer this over "use two different secrets". Two secrets also works, but a
> `type` claim is self-describing, survives a secret rotation, and is what the
> refresh path already does — so you end up with one consistent rule instead of
> two mechanisms.

### 2. Bind the access token to its session row

Put `sId` in the access payload (shown above) and pass `sessionId` when minting
it in [login.ts:113-116](../../server/src/controllers/auth/login.ts#L113-L116) and
[refreshToken.ts:98-101](../../server/src/controllers/auth/refreshToken.ts#L98-L101)
— both already have `sessionId` in scope.

### 3. Validate the session on every authenticated request

```ts
// server/src/middleware/checkCookieSignature.middleware.ts
const session = await pool.query(
  `SELECT us.id
     FROM user_sessions us
     JOIN users u ON u.id = us.user_id
    WHERE us.id = $1
      AND us.user_id = $2
      AND us.revoked_at IS NULL
      AND us.expires_at > NOW()
      AND u.is_active = TRUE`,
  [userPayload.sId, userPayload.uId],
);
if (session.rowCount !== 1) {
  throw AppError.unauthorized("Session is no longer valid. Please login again.");
}
```

**On the cost of change 3:** this adds one indexed primary-key lookup to every
request. That is the correct trade for an IAM system — you are choosing
*revocable* over *stateless*, and revocability is the entire point of the
Sessions feature you built. If you later want the throughput back, cache the
"session is live" answer in Redis with a short TTL (10–30s) and delete the key in
`revokeSession` / `revokeAllUserSessions`; you already have Redis wired up and a
clean `clearRateLimitKey` helper to model it on. Do **not** solve it by shortening
the access token lifetime alone — that reduces the window, it does not close it.

## Interaction with other findings

- **Vulnerability 03** (`is_active` never enforced) is fixed by the same query in
  change 3 — that is why the `JOIN users u ... AND u.is_active = TRUE` clause is
  in there. Implement them together.
- **Vulnerability 04** (password change does not revoke sessions) becomes
  *enforceable* only after this is fixed. Before this fix, revoking sessions on
  password change would still not lock the attacker out.
- **Vulnerability 05** (refresh reuse detection) depends on this: reuse detection
  revokes the session family, which only matters if revocation works.
- **Suggestion 01** (centralised authorization middleware) is the natural place
  for change 3 to live long-term.
- **No contradiction** with Suggestion 05 (pool configuration) — but note that
  adding a per-request query makes pool sizing matter more, so land them in the
  same pass.

## What you already got right here

- Refresh tokens are stored **hashed** (`bcrypt(sha256(token))`) rather than in
  plaintext — [encryptStrings.ts:31-40](../../server/src/utils/encryptStrings.ts#L31-L40).
  Most learning projects store the raw token. You did not.
- The refresh direction *is* type-checked. You clearly understood the concept;
  it just was not applied symmetrically.
- `verifyToken` pins `algorithms: ["HS256"]`, which correctly closes the classic
  `alg: none` / algorithm-confusion attack. That is a detail plenty of production
  codebases miss.
- Rotation-on-refresh with a compare-and-swap guard
  (`WHERE ... AND refresh_token_hash = $5`) is genuinely good instinct — see
  Vulnerability 05 for how to finish that thought.

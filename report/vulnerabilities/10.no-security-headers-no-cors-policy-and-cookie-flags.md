## The finding

Four related gaps in the HTTP layer.

### A. No security headers at all

`app.ts` mounts `express.json`, `express.urlencoded`, `cookieParser`, the routers,
and the error handlers. There is no `helmet`, and nothing sets headers manually.
Every response therefore ships with:

- No `Strict-Transport-Security` — a downgrade to plaintext HTTP is not prevented.
- No `X-Content-Type-Options: nosniff` — MIME sniffing is live.
- No `Content-Security-Policy` — nothing constrains what the Swagger UI page at
  `/api/docs` may load or execute.
- No `Referrer-Policy`, no `X-Frame-Options` / `frame-ancestors`.
- **`X-Powered-By: Express`** on every response, which Express adds by default
  and which is free reconnaissance.

```bash
curl -sI localhost:8000/api/openapi.json
# HTTP/1.1 200 OK
# X-Powered-By: Express        <-- volunteered
# Content-Type: application/json; charset=utf-8
# ... and nothing else of interest
```

### B. No CORS policy — which means the API works *only* behind the Vite proxy

There is no `cors` middleware and no `Access-Control-Allow-Origin` header
anywhere. The application functions today purely because
[vite.config.ts](../../client/vite.config.ts) proxies `/api` to
`http://localhost:8000`, making every request same-origin from the browser's
point of view:

```ts
server: { proxy: { '/api': { target: 'http://localhost:8000', changeOrigin: true } } }
```

The axios instance uses **relative** URLs (`url: '/api/auth/login'`) with
`withCredentials: true` and no `baseURL`, which is consistent with that model.

This is fine for development. It means the first real deployment where the client
is served from a different origin than the API will fail every request with a
CORS error, and the reflex fix — `app.use(cors())` with no arguments — is
**dangerous here**: bare `cors()` emits `Access-Control-Allow-Origin: *`, and a
wildcard origin is incompatible with `withCredentials: true`, so the next reflex
is `cors({ origin: true, credentials: true })`, which reflects *any* origin and
turns every authenticated endpoint into a cross-origin free-for-all. Deciding the
policy now, deliberately, is much cheaper than deciding it under deployment
pressure.

### C. Cookie flags are hardcoded and incomplete

```ts
// server/src/others/constants.ts:31
const httpOptions = { httpOnly: true, secure: true, sameSite: "strict" } as const;
```

- **`secure: true` unconditionally.** This happens to work in local development
  because browsers exempt `http://localhost` from the secure-cookie restriction.
  It will *silently* stop working on any non-localhost plaintext origin — a LAN IP
  during testing, a staging box on `http://`. The browser drops the cookie with no
  error visible to the application; you get an infinite "logged out immediately"
  loop with a 200 on `/login`. Correct value, but hardcoding it means the
  behaviour is accidental rather than chosen.
- **No `maxAge` / `expires`.** Both cookies are *session cookies*, deleted when
  the browser closes. This is a genuine mismatch: `REFRESH_TOKEN_EXPIRES_IN=7d`
  says "remember this user for a week", but the cookie carrying that token dies
  when the browser does. Every browser restart forces a re-login regardless of
  the token's real lifetime.
- **No `path`.** Both cookies are sent to every path including `/api/docs`. The
  `refresh` cookie is only needed at `/api/auth/refresh` and `/api/auth/logout`.
- **`sameSite: "strict"` is a good default** but note it also suppresses the
  cookie on top-level navigation *into* the app from an external link — a user
  clicking a link in an email lands logged-out even with a valid session, then
  gets logged in on the next in-app navigation. `"lax"` is the usual compromise;
  `"strict"` is defensible for an admin console. Just make it a decision.

### D. No body size limit is set explicitly

`express.json()` defaults to `100kb`, which is a reasonable ceiling, so this is
not currently exploitable. It is worth making explicit so a future
`express.json({ limit: '50mb' })` for a file-upload feature does not silently
apply to the auth endpoints too.

## Why it matters

None of these is individually an exploit. Together they are the difference
between "an app that happens to work on one developer's laptop" and "an app that
can be deployed". The specific risks:

- **Missing HSTS + `secure` cookies** — an attacker on the network path strips
  TLS on the first plaintext request; the browser then refuses to send the
  `secure` cookies over the plaintext connection, which is *safe* but produces a
  confusing logged-out state rather than a clear failure. With HSTS the downgrade
  is refused outright.
- **Missing CSP on `/api/docs`** — Swagger UI is a large third-party bundle
  rendering attacker-influenceable schema content. It is served unauthenticated
  (see [Vulnerability 13](./13.unauthenticated-openapi-and-docs-exposure.md)) and
  has no CSP constraining it. That is a lot of attack surface for a page nobody
  is monitoring.
- **The CORS decision made under pressure** is how permissive origin reflection
  ends up in production. `sameSite: "strict"` is currently your entire CSRF
  defence; a hasty `cors({ origin: true, credentials: true })` combined with a
  future relaxation to `sameSite: "lax"` would remove it.

## The fix

### 1. Add `helmet`, disable `x-powered-by`

```bash
pnpm --dir server add helmet
```

```ts
// server/src/app.ts -- immediately after `const app: Application = express();`
import helmet from "helmet";

app.disable("x-powered-by");
app.use(
  helmet({
    // The API returns JSON; the only HTML it serves is Swagger UI, which needs
    // inline styles. Scope the relaxation to that route rather than globally.
    contentSecurityPolicy: {
      directives: {
        defaultSrc: ["'self'"],
        scriptSrc: ["'self'"],
        styleSrc: ["'self'", "'unsafe-inline'"],
        imgSrc: ["'self'", "data:"],
        connectSrc: ["'self'"],
        frameAncestors: ["'none'"],
        objectSrc: ["'none'"],
      },
    },
    hsts: env.NODE_ENV === "production"
      ? { maxAge: 31_536_000, includeSubDomains: true, preload: true }
      : false,
    referrerPolicy: { policy: "no-referrer" },
  }),
);
```

### 2. An explicit, allow-listed CORS policy

```bash
pnpm --dir server add cors && pnpm --dir server add -D @types/cors
```

```ts
// server/src/utils/envHelper.ts
CORS_ALLOWED_ORIGINS: z
  .string()
  .default("")
  .describe("Comma-separated exact origins allowed to call the API with credentials"),
```

```ts
// server/src/app.ts
import cors from "cors";

const allowedOrigins = env.CORS_ALLOWED_ORIGINS.split(",")
  .map((origin) => origin.trim())
  .filter(Boolean);

app.use(
  cors({
    origin: (origin, callback) => {
      // No Origin header = same-origin, curl, or the Vite proxy. Allow.
      if (!origin) return callback(null, true);
      if (allowedOrigins.includes(origin)) return callback(null, true);
      return callback(new Error("Origin not allowed by CORS policy"));
    },
    credentials: true,
    methods: ["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
    allowedHeaders: ["Content-Type"],
    maxAge: 86_400,
  }),
);
```

Empty by default means development behaviour is unchanged (the Vite proxy sends
no `Origin`), and production requires an explicit list. **Never** `origin: true`.

### 3. Make cookie options environment-aware and complete

```ts
// server/src/others/constants.ts
import env from "../utils/envHelper.ts";

const MINUTE = 60 * 1000;
const DAY = 24 * 60 * MINUTE;

const baseCookieOptions = {
  httpOnly: true,
  secure: env.NODE_ENV === "production",
  sameSite: "strict",
} as const;

const accessCookieOptions = {
  ...baseCookieOptions,
  path: "/api",
  maxAge: 20 * MINUTE,          // keep in step with ACCESS_TOKEN_EXPIRES_IN
} as const;

const refreshCookieOptions = {
  ...baseCookieOptions,
  path: "/api/auth",            // only sent where it is needed
  maxAge: 7 * DAY,              // keep in step with REFRESH_TOKEN_EXPIRES_IN
} as const;
```

Then in `login.ts`, `refreshToken.ts` and `logout.ts` use the specific options.
**Two constraints you must not violate:**

1. `res.clearCookie` must be called with the *same* `path` and `sameSite` used to
   set the cookie, or the browser ignores it and logout silently fails. Check
   [logout.ts:10-13](../../server/src/controllers/auth/logout.ts#L10-L13).
2. Deriving `maxAge` from a literal is a duplication hazard — the source of truth
   is `ACCESS_TOKEN_EXPIRES_IN` / `REFRESH_TOKEN_EXPIRES_IN`. Better: compute
   `maxAge` from the token's own `exp` claim, which login already extracts via
   `getTokenExpirationDate`.

### 4. Pin the body limit

```ts
app.use(express.json({ limit: "100kb" }));
app.use(express.urlencoded({ extended: true, limit: "100kb" }));
```

## Interaction with other findings

- **[Vulnerability 13](./13.unauthenticated-openapi-and-docs-exposure.md)** — the
  CSP above is the mitigation for Swagger UI's attack surface; that finding
  handles who may reach the page at all. Complementary.
- **[Vulnerability 22](./22.trust-proxy-misconfiguration-enables-limit-bypass.md)**
  — both are "the deployment topology is not modelled". If you add a reverse
  proxy for TLS termination (which HSTS implies), you must set `TRUST_PROXY`
  correctly at the same time. **Do these two together or you will fix one and
  break the other.**
- **[Suggestion 13](../suggestions/13.environment-config-and-secret-management.md)**
  — `CORS_ALLOWED_ORIGINS` is a new environment variable and belongs in the same
  config pass.
- **[Suggestion 14](../suggestions/14.docker-compose-and-reproducible-dev-env.md)**
  — a compose setup that serves the client from nginx makes the CORS policy load-
  bearing immediately. Land CORS **before** the compose work, not after.
- **Watch for contradiction:** if you ever relax `sameSite` to `"lax"` for the
  email-link UX reason, you must add CSRF tokens, because `sameSite: "strict"` is
  currently the *only* CSRF defence in the system. Do not change that flag in
  isolation.

## What you already got right here

- **`httpOnly: true` on both cookies.** JavaScript cannot read the tokens, which
  is why the XSS-to-account-takeover path is closed. This is the single most
  important cookie flag and you set it.
- **`sameSite: "strict"`.** This is why there is no CSRF finding in this report —
  a genuinely strong default that many projects skip in favour of a bolted-on
  token scheme.
- **Tokens in cookies rather than `localStorage`.** The client stores only a
  boolean `isAuthenticated` flag; no credential ever touches web storage. That is
  the right architecture and it is what makes `httpOnly` meaningful.
- **Relative URLs + Vite proxy** rather than a hardcoded `http://localhost:8000`
  baseURL. It keeps the browser same-origin in development and means the
  production build needs no code change, only a proxy in front.
- `trust proxy` is already parsed from configuration rather than hardcoded — the
  scaffolding for a correct deployment story is there, it just needs the rest of
  the headers to join it.

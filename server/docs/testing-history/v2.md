## Important Finding From V2

While implementing `v2`, the suite exposed a real refresh-token replay weakness:

- refresh tokens were stored with bcrypt directly
- bcrypt only uses the first 72 bytes of input
- long JWT refresh tokens can share that prefix
- that made old and new refresh tokens compare as valid against the same stored hash

This was fixed by hashing refresh tokens through SHA-256 before bcrypt storage/comparison in the refresh-token path.
